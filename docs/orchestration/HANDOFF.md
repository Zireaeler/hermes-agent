# orchestra 当前接手说明

> 本文件只记录当前状态和下一步，不重复顶层设计。稳定原则见 [`orchestra-design.md`](orchestra-design.md)，首版行为见 [`v1/design.md`](v1/design.md)，具体实施见 [`v1/implementation.md`](v1/implementation.md)。

## 当前结论

orchestra 是运行在项目决策边界上的间歇式战略代理：

- 每轮使用全新会话；
- 从当前人类意图、项目状态、最新结果和按需证据重新组装上下文；
- 单轮内允许完整代理循环；
- 跨轮不继承旧对话、推理过程和策略辩护；
- 只选择一个当前任务；
- 任务内部交给完整 worker 自治；
- 长期连续性属于可直接重写的项目状态，不属于任何长期模型会话。

首版严格一对一：任何时刻只有一个活动 worker。多 worker 是后续独立研究，不进入首版。

## 已确定的边界

- 不重新验证单 worker 长期维持宏大目标会发生注意力涣散；Hermes 历史已经提供了足够工程证据。
- 不构造覆盖所有设计点的综合演示。
- 不建立规划、编码、测试、评审固定角色。
- 不管理 worker 内部子代理。
- 不建设目标合同、进展账本、执行图、图修订、检查点和恢复协议。
- 不把两段式上下文写成首版强制流程。
- orchestra 默认只读检查业务代码，只更新项目状态与 worker 推进说明。
- 同一明确任务继续使用原 worker 会话；实质不同的新任务默认使用新 worker 会话。
- 项目状态最多是一份可整体重写的自由格式 Markdown，不做字段校验、版本、迁移、兼容和自动修复。

## 首个真实目标

当前首选目标是多供应商视频任务能力：

> 把现有视频任务能力演进为可持续扩展的多供应商服务。用户仍通过统一接口创建和查询任务，系统能在已配置渠道中选择和切换实际供应商，并保持任务身份、状态查询、失败处理和计量语义一致。后续接入新的供应商时，不应反复修改上层业务流程。

正式运行前需要在目标仓库核实当前调度、Volc 透传、任务查询、计量和 ecloud 接入现实。不要把讨论中的初步结构直接当成已确认事实。

第二候选是可信的请求计量与运营统计；第三候选是 Hermes 的 Windows 原生日常可用性。它们不与首个目标并行运行。

## 下一步实施

按 [`v1/implementation.md`](v1/implementation.md) 执行：

1. 先手工跑通两到三个完整决策轮；
2. 确认项目状态、worker 推进说明和结果材料的边界；
3. 实现薄的 `decide` 启动器，直接创建全新的 `AIAgent`；
4. 只接入一个当前稳定的 Codex 或 Claude Code worker 后端；
5. 连成由人类显式触发的一对一闭环；
6. 只根据真实重复问题增加最小能力。

首版不要先实现守护进程、自动边界检测、通用 worker 适配、多 worker、数据库或状态协议。

## 首版需要持续观察的问题

- 精简项目状态是否足以让全新的 orchestra 恢复项目局面；
- 哪些事实需要直接输入，哪些只需提供引用；
- orchestra 是否过度依赖 worker 自述；
- orchestra 的代码检查是否过深，开始变成第二个 worker；
- 项目决策边界是否过早或过晚；
- worker 推进说明是否过细或过粗；
- 新任务是否仍被旧 worker 会话中的局部叙事污染；
- 项目状态是否开始形成自己的格式兼容和维护责任；
- 人类在连续运行后是否逐渐只需处理真正的方向与价值选择。

这些问题用于调试接口，不用于继续扩建新的运行时机制。
