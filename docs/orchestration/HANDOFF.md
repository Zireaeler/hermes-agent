# 接手说明

这份文档是给下一个 AI（或人）读的。它解释这个项目在做什么、为什么这么做、现在走到哪、
以及下一步该做什么。读完这份和 `orchestra-design.md`，你就有了完整的上下文。

---

## 1. 这个项目要解决什么问题

现有的 coding agent（Codex、Claude Code 等）在单个明确任务上表现良好。把它们接成一个
自动循环也不难：任务完成后让它写一份阶段总结，据此生成下一个任务，如此往复。**这个循环
确实能自动跑下去——但它只有前进档，没有方向盘和刹车。**

没有否定能力的循环会：

- 持续做加法，每个新增机制单独看合理，累积起来没人能理解
- 在错误路线上越砌越厚，而不是换路
- 偏离最初意图，但因为一切看起来都在「正常推进」，没有任何信号

这就是 `hermes-agent-runtime-kernel` 项目本身的命运：一个 codex session 一路做下来，
每个 phase 都被「完成」了，但整体方向持续漂移，最终变成一堆作者自己也看不懂的机制。

**目标是建设一个编排层**，在成熟 coding agent 之上提供长期方向控制，使项目可以在
少量人工介入下持续推进。

## 2. 核心设计决定（已定稿，不需要重新讨论）

完整设计在 `orchestra-design.md`。以下是几个最关键的、最容易被误解的决定，附带理由。

### 否定是唯一的核心能力

orchestra 存在的理由不是「更聪明的推进」，而是在正确的时刻说「停、回退、砍掉、换方向」。
worker 已经足够强，推进不是瓶颈。瓶颈是没有东西能做否定。

一个从未否定过任何东西的 orchestra 等于不存在。这是最重要的健康指标。

### Orchestra 不受代码约束

orchestra 是一个 agent，约束它的手段是注入上下文的原则说明（prompt / md），不是代码
规则。用 validator 去裁决它的判断——Hermes 旧设计里做了这件事——会把它从判断者降级为
受限组件。这个方向是根本性错误的。

### Orchestra 的大脑直接用现成 cc/codex

不要重造决策引擎。orchestra 和 worker 在「单体智能」上没有区别，也不该有。区别在拓扑
和时间：orchestra 被接上持久判断记忆、处在监管位；worker 是被监管的一次性执行体。同样
的大脑，不同的位置和记忆。

### 代码层只记账，不裁决

DB 可以拒绝写入结构非法的数据（schema 不合法、引用悬空、重复入账），不可以拒绝一个
它认为不明智的决策。Hermes 旧设计里 validator 做了判断——这是错的。

### 多轮循环是人为制造的，不是自然发生的

一个有能力的 worker 一个 goal 内就能做完整个调度器。「轮」必须被设计成：每轮给一个
新的需求扩展，worker 在同一个代码库上叠加。这样膨胀自然发生，不是被逼出来的。

### 深审触发器必须外生

用命名实体数量（新增了多少个需要人理解的有名字的东西）触发，不用周期边界。原因：
周期由 orchestra 自己定义，用它触发等于让被审计者自己决定何时接受检查。

## 3. 为什么先做实验，而不是先建系统

这个设计的全部价值压在一个能力上：定期深审能否真的砍掉不该存在的东西。这个能力
**不需要任何基础设施就能测**——一个循环脚本加一份 prompt 即可。

如果不先测就往下建，会重复 Hermes 本身的失败路径：建了大量机制，核心假设一次都没
验证过。

**廉价实验的主问题是二元的**：加了深审的自动循环，到底会不会真的砍掉东西？这个问题
n=1 就能回答。

实验细节见 `cheap-experiment.md`。

## 4. 现在走到哪

### 已定稿

- `orchestra-design.md`：完整设计，涵盖角色、能力、两种模式、并行策略、上下文机制、
  唤醒节奏、终止条件、成功度量、防膨胀约束
- `deep-review-prompt.md`：深审用的 prompt，附实证依据和可靠性边界说明
- `cheap-experiment.md`：验证计划，7 轮迭代扩展序列，两组对比

### 未做

**第一优先：跑实验。** `cheap-experiment.md` 里有完整的执行清单，从预注册到结果判读。
没跑完实验之前，不要建任何基础设施。

实验之后，根据结果决定：

- 如果 B 砍了且砍对了：按 `orchestra-design.md` 往下建
- 如果深审从未触发：先执行清单第 3 步（校准阈值），然后重跑
- 如果 B 一次没砍但 A 明显膨胀：改 prompt 再试，参见 §5 的 prompt 调优方向
- 其他情况：见 `cheap-experiment.md` §8

### 还有五个未决问题（见 `orchestra-design.md` §11）

1. 人的升级通道（如何叫醒人、等待期间系统做什么）
2. 预算与成本治理
3. 模型选型（orchestra 用最强、worker 用执行力强、核实用便宜的）
4. 意图捕获（从人那里得到足够好的原始意图，尤其是探索模式起点）
5. Orchestra 自监管（判断记录已经是基础材料，需要设计成能力）

这五个都在实验之后处理，现在动它们是在绕开最重要的验证步骤。

## 5. Prompt 调优方向（实验失败时参考）

如果实验结果是「B 一次没砍，但 A 明显膨胀」，说明深审 prompt 失效。最可能的原因和
对应调整：

**原因 A：审计表的依据门槛太低，worker 擅长填合理理由。**
调整：把「意图追溯」改成「指向原始意图里的哪一句原文」，强制精确匹配而非宽泛对应。

**原因 B：模型认出了自己的风格，自我偏好偏高。**
调整：换一个不同家族的模型做深审（研究显示 Claude 系在评审时倾向低估自己家族，
对否定任务有利）。

**原因 C：第二步的形状检查六个问题里，2/5/6 是纯判断，模型倾向给过。**
调整：强化第一步的机械查找，削弱第二步的权重；或者把 2/5/6 改成「如果有，列出
具体名称」的格式，不让模型给一个「未发现」的笼统回答。

**原因 D：硬性禁止里「不得提出任何新机制」被遵守，但模型用「改进」绕过去了。**
调整：在硬性禁止里加一条「不得建议任何结构上的改动，包括用'优化'/'重构'/'合并'
包装的建议，除非它已在移除清单里」。

## 6. Hermes 旧设计里什么值得保留

如果实验成功、决定往下建，旧设计里这些部分是对的：

- **DB 作事实源**：event log、跨进程 resume、attempt-patch 幂等捕获。这是执行底座，
  和「谁来编排」无关，任何方向都用得上。
- **执行节点必须关联目标**：这条规则是对的，可以保留在 validator 里——但注意它属于
  「数据完整性」而不是「判断裁决」，两者有本质区别。

旧设计里这些部分应该丢弃：

- Decision Provider、decision session / segment / checkpoint / compaction 整套
- 4G11-4G16 的协调协议（为并行协作式 worker 设计，而我们的结论是协作式并行默认不用）
- 围绕 Decision Provider 的修复子系统（checkpoint repair、receipt repair、
  quarantine/promotion）——它们是为一个错误的核心假设服务的

## 7. 这份文档本身的维护规则

和 `orchestra-design.md` 一样，不要按阶段追加新的规范文档。有新结论就修改现有文件，
不新建。一份份叠加的文档会形成只增不减的棘轮，这是 Hermes 本身的失败机制之一。

本文档（HANDOFF.md）专门用于接手说明：背景、决定、现状、下一步。它应该保持可以在
10 分钟内读完。如果它开始变成一份详细的技术规范，说明它的内容应该去 `orchestra-design.md`，
而不是留在这里。
