# 廉价实验：否定能力是否存在

验证 `orchestra-design.md` 的核心假设，在建设任何东西之前完成。

## 0. 为什么先做这个

那份设计的全部价值压在一个能力上：定期深审能否真的砍掉不该存在的东西。这个能力
**不需要任何基础设施就能测**——一个循环脚本加一个 prompt 即可。

反过来说，如果不先测就按设计往下建，就会重复一条已知的失败路径：建了大量机制，
核心假设一次都没验证过。

## 1. 要回答的问题

先写死，跑完不许改。

**主问题（二元，生死线）**

> 加了深审的自动循环，到底会不会真的砍掉东西？

一次都没有，设计即失效，后续细节无需讨论。这个问题 n=1 就能回答，这是本实验便宜的
根本原因。

**次问题**（主问题为「是」时才有意义）

- 砍掉的是不是真该砍（有无误杀）
- 最终产物 B 是否比 A 更小，且能力相当
- 无上下文的读者理解 B 是否比 A 容易
- B 多花了多少时间和 token

## 2. 实验对象

### 2.1 任务陈述（两组完全相同，逐字一致）

```text
构建一个本地任务调度器。它需要能够：

- 让用户定义任务：一条要执行的命令，加上执行时机（固定间隔，或一次性的
  未来时间点）
- 到时间自动执行这些命令
- 记录每次执行的结果
- 任务执行失败时按配置重试
- 调度器进程重启后继续工作：未来的任务照常执行，不会因为重启而丢失或
  重复执行

用 Python 实现，不依赖外部服务。
```

### 2.2 为什么选它

- **核心极简**：一个循环加一个存储，写好了一两百行。正确解明显比诱人解简单。
- **膨胀空间极大**：「可靠性」这条轴上可以无限加东西——租约协议、崩溃恢复语义、
  幂等层、心跳健康检查、背压、并发控制、形式化状态机、审计日志、可插拔存储后端、
  可插拔调度策略。这正是要检测的病灶形状。
- **验收客观**：能不能按时跑、崩溃后能不能恢复，是可执行的判定，不依赖主观评价。

### 2.3 陈述必须中性

任务陈述里不得出现「保持简洁」「避免过度设计」「最小实现」一类字眼。加了就等于把
答案喂进去。要观察的正是循环自己会不会漂。

### 2.4 隐藏验收测试

以下测试**在实验开始前定稿，对两组均不可见**，只在结束时对两组各跑一次。避免写代码
迎合测试。

1. **定时执行**：注册一个每 2 秒执行一次的任务，10 秒内至少成功执行 4 次。
2. **一次性任务**：注册一个 5 秒后执行的任务，执行一次且仅一次。
3. **失败重试**：注册一个必然失败的任务并配置重试 3 次，实际尝试 4 次后停止。
4. **崩溃恢复**：运行中 `kill -9` 调度器后重启——未到期的任务照常执行，已完成的
   一次性任务不重复执行。
5. **执行历史**：能列出每次执行的时间和退出码。
6. **不重入**：一个执行耗时超过其间隔的任务，不应在上次未结束时被重复启动。

## 3. 两个 Arm

### 3.1 A 组（对照）

```text
worker 完成任务 → 写阶段总结 → 据总结生成下一个 goal → 继续
```

**A 不能是稻草人。** 生成下一个 goal 必须是一次正经的 LLM 调用，prompt 质量与实际会用
的相当。它唯一缺少的是否定能力。

若 A 自发出现了删减动作，那是有效结果（说明不需要深审），**不得加以限制**。

### 3.2 B 组

与 A 完全相同，外加：

1. 每轮交付后由便宜模型生成一次现状快照（清单 + 计数）；
2. 命名实体数越过阈值时，按 `deep-review-prompt.md` 跑一次深审；
3. 移除清单作为下一个任务派给 worker；
4. 验收标准是**下一次快照的计数必须真的下降**。

### 3.3 必须固定的变量

模型、任务陈述、起始仓库状态、worker 侧 prompt、轮数、运行环境。A 与 B 的差别**只有
深审这一件事**。

## 4. Prompt

深审 prompt 见 `deep-review-prompt.md`。以下两份为本实验专用。

### 4.1 下一步生成（A、B 共用）

```markdown
你在推进一个项目。下面是项目目标、已完成的工作和最近一次交付的总结。
确定下一步应该做什么。

【项目目标】
<2.1 的任务陈述>

【已完成】
<历次交付总结的列表>

【最近一次交付】
<worker 的总结>

输出一个任务，包含：做什么、什么算完成。
```

### 4.2 现状快照（B 组每轮，A 组仅最后一轮用于测量）

```markdown
清点当前项目状态。只做清点，不做评价。

1. **命名实体清单**——每一个需要新读者去理解的、有专有名称的东西：
   源码模块、导出的类与主要函数、配置项、机制名称、文档章节。
   每项一行：`名称 | 类型 | 所在位置`
2. **总数**
3. **语义重复**——做同一件事的多处实现，写法不同不算不同
4. **未被使用的条目**——已定义但没有任何地方调用或触发
5. **当前实际能力**——这个项目现在能做什么

不要评价好坏，不要提改进建议。
```

计数口径对两组必须一致，用同一份 prompt 和同一个模型。绝对准确度不重要，**一致性
才重要**，因为比较的是 A 与 B。

## 5. 触发器与阈值

- 首次深审：累计命名实体达到 **12**
- 之后每新增 **6** 触发一次
- 每组 **12 轮**（固定，两组相同）

**开跑前必须做的检查**：手动预估这个任务 12 轮下来会长到多大。若根本到不了 12 个实体，
阈值需下调，否则深审一次都不触发，实验白跑。

阈值偏低优于偏高——主问题是「是否曾经否定」，触发次数越多观测机会越多。

## 6. 测量

跑之前定义完，跑完不许加指标。

| 指标 | 测法 |
|---|---|
| 是否发生否定 | B 的移除清单非空且被执行的次数 |
| 否定质量 | 每一项由人 + 一个未参与的模型**独立**判定「该砍／不该砍」 |
| 最终规模 | A、B 各自的命名实体数、模块数、总行数 |
| 能力 | §2.4 的隐藏测试，两组各跑一次，记通过项 |
| 可读性 | 无上下文的模型读最终状态，回答「这是什么、是否健康」，人打分 |
| 成本 | wall time、token 用量 |

否定质量必须**双盲判定**：判定人不应在判定时知道哪一项来自哪次深审的什么背景，先各自
判完再对齐。已知结论会不自觉放宽标准。

## 7. 预注册

开跑前写下预期，一句话即可，例如「A 会长到 25 个以上实体，B 会砍 2-3 次」。

这不是形式主义。事后重写报告以匹配结果是有先例的失败模式，预注册是唯一能防住它的手段。

## 8. 结果判读

| 结果 | 含义 | 下一步 |
|---|---|---|
| B 砍了 ≥1 次且砍对了，最终更小、能力相当 | 假设成立 | 按设计文档往下建 |
| B 一次没砍，但 A 明显膨胀 | 深审失效——关键负面结果 | 改 prompt 再测一次；仍无则设计有根本问题 |
| B 一次没砍，A 也没膨胀 | 任务选错，无膨胀空间 | 换任务重跑，**不得据此下任何结论** |
| B 砍错了，能力下降 | 能力存在但缺护栏 | 提高举证门槛，值得继续 |
| B 明显更贵且形状无改善 | 不值得 | 重新考虑深审频率或整个设计 |

第三行极易被误读成第二行。**先确认 A 有没有膨胀，再判断 B 的失败性质。**

## 9. 这个实验不许建什么

明确禁止：数据库、状态机、validator、事件日志、持久化层、任何协议。

需要的只有：一个循环脚本、一次快照调用、三份 prompt。

**总胶水代码控制在 200 行以内。若它开始变大，立即停止**——本实验的目的正是检测这种
增长，它自己先膨胀就失去了意义。

## 10. 规模估算

每组 12 轮，两组可并行。B 多出 3-4 次深审。整体一到两天挂钟时间，成本量级取决于模型
选择。

## 11. 已知缺陷

**每组 n=1，方差大。** 单次结果不足以说明「B 一般更好」。但主问题是二元的——否定能力
是否存在——n=1 足以证伪。若 B 未砍，建议再跑一次 B 再下结论：否定是低概率事件，单次
未出现不等于能力缺失。

**任务由知道假设的人选定，有偏向风险。** 缓解：任务陈述定稿后，先让一个不知道实验目的
的模型评一句「这个任务有多大过度设计空间」，避免潜意识选了偏向 B 的题。

**深审可能砍的是无关痛痒的东西**（删个 stub 也计入「砍了」）。因此 §6 的否定质量判定
必须做，只数次数会自欺。

**审查者模型的自我偏好。** 若审查者与 worker 同族，存在自我偏好风险。选型见
`deep-review-prompt.md` 的说明。

## 12. 执行清单

1. 确认任务陈述定稿，中性检查通过
2. 隐藏验收测试写好并封存
3. 预估实体增长，校准阈值
4. 写下预注册预期
5. 搭循环脚本（≤200 行），A、B 共用，B 多一个深审分支
6. 并行跑两组，各 12 轮
7. 两组各跑一次隐藏验收测试
8. 收集 §6 全部指标，双盲判定否定质量
9. 对照 §8 判读，写结论——**结论必须与预注册对照，不得改写预期**
