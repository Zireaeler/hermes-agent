# 廉价实验：负向回顾有没有实际价值

## 1. 要验证什么

只验证一个问题：

> 在同一段连续开发中，相比普通独立 review，只允许 `keep / remove / merge /
> simplify / doubt` 的独立负向回顾，能否在不损害已有能力的情况下，让后续维护更容易？

这不是完整 Orchestra 的验证。它不回答长期记忆、路线选择、自动停止或多 worker 编排是否有效。

如果负向回顾没有稳定收益，或收益抵不过 review 本身的成本，就停止，不建设更大的系统。

## 2. 实验任务

两组从同一个空目录开始，用相同的 Worker 完成相同的七轮本地任务调度器需求。

### R1

```text
构建一个本地任务调度器。需要支持：

- 注册一条 shell 命令，加上执行间隔（秒）
- 到时间自动执行
- 记录每次执行的时间和退出码

用 Python，不依赖外部服务。
```

### R2

```text
调度器重启后，已注册的任务不丢失，继续按原计划执行。
不需要额外依赖。
```

### R3

```text
除了固定间隔任务，还支持「在某个具体时间点执行一次」的任务。
执行完成后自动移除，不再触发。
```

### R4

```text
任务执行失败时（非零退出码），按配置的最大次数重试。
重试之间有固定间隔。记录每次尝试的结果。
```

### R5

```text
多个任务到期时同时执行，不互相等待。
同一个任务的上次执行未结束时，不重复启动。
```

### R6

```text
提供一个方式查看当前所有任务的状态：名称、下次执行时间、
最近一次结果、累计执行次数。
```

### R7

```text
不重启调度器的情况下，能够暂停某个任务、恢复它，以及删除某个任务。
```

每轮只给当前新需求，不提示保持简单，也不引导使用某种架构。

## 3. 两组怎么跑

### 普通 Review 组

在 R2、R4、R6 完成并通过当轮测试后，由一个没有参与实现的 reviewer 检查当前项目。它可以建议：

- 修复真实问题；
- 普通重构；
- 增加确实缺失的实现；
- 删除、合并或简化已有结构；
- 不做修改。

### 负向回顾组

在相同的 R2、R4、R6 后运行独立 reviewer，但它只能输出：

- `keep`
- `remove`
- `merge`
- `simplify`
- `doubt`

它不能增加产品能力、设计替代架构，或把一个发现扩展成新的流程和基础设施。

### 共同流程

```text
完成当前需求
→ 运行当轮测试
→ 独立 reviewer 检查
→ 相同配置的 executor 执行 reviewer 建议
→ 再次运行测试
→ 继续下一轮需求
```

Reviewer 输出 no-op 完全合法。Review 和 cleanup 不得替代 R1–R7 中的任何需求。

两组保持一致的内容：

- 起始目录和运行环境；
- R1–R7 原文；
- Worker、reviewer 和 executor 的模型与 reasoning effort；
- review 发生的轮次；
- reviewer 能看到的材料；
- 每次 review 和执行可用的大致时间与 token；
- 公开测试、最终能力测试和后续维护任务。

唯一有意改变的是 reviewer 可以提出什么类型的动作。

## 4. Reviewer 能看到什么

两组 reviewer 都只看：

- 已经给出的 R1–当前轮需求；
- 当前代码和文档；
- 当前公开测试结果；
- 实际引用、调用和运行情况；
- 用户明确给出的安全边界。

Reviewer 不看：

- 另一组的代码和结论；
- 此前 reviewer 的辩护；
- 作者为什么采用当前设计；
- 实验希望哪一组更简单。

依赖、调用和测试结果是事实；“语义重复”“概念太多”“架构不健康”是 reviewer 的判断，必须回到代码和行为验证。

具体 prompt 见 `deep-review-prompt.md`。

## 5. 怎么判断能力有没有受损

两组最终都运行相同测试：

1. 间隔任务在预期时间内重复执行；
2. 一次性任务只执行一次；
3. 失败任务按配置次数重试；
4. 调度器被强制终止后重启，未完成任务继续，已完成的一次性任务不重复；
5. 每次尝试的时间和退出码可查询；
6. 长任务不会发生同任务重入；
7. 多任务可以并行；
8. 暂停、恢复和删除不影响其他任务。

测试在两组运行前写好，运行过程中不根据某组实现修改。测试结果不回灌给 Worker 继续刷题。

负向组只要损坏核心能力，就不能用“代码更少”抵消。

## 6. 怎么判断后续维护是否更容易

R7 完成后，从每个成品分别复制两份，让全新的维护 agent 完成相同的后续任务。原 Worker 和 reviewer 都不参与。

### 维护任务一：增加执行超时

```text
每个任务可以配置执行超时。超过时间后终止该次进程，记录为超时；
后续重试、执行历史、持久化和不重入行为继续正确工作。
```

### 维护任务二：删除失败重试能力

```text
删除失败自动重试能力及只为它存在的实现和配置。
保留间隔任务、一次性任务、并发、不重入、持久化、状态查询、暂停、恢复和删除。
```

两个维护任务在各自独立副本上执行，互不影响。记录：

- 是否正确完成并通过对应测试；
- wall time 和 token；
- 失败尝试次数；
- 修改涉及多少文件和模块；
- 是否引入与任务无关的机制；
- 是否造成已有能力回归。

这比统计类数、文件数或命名实体数更接近真正的结构负担。LOC、文件数和实体数可以记录，但只作旁证。

## 7. 模型和子代理

- 普通分析、review 和实现默认使用 `terra-high` 及以下。
- 简单查找、清点和机械核验可以使用 Luna。
- Sol 只在多个独立 Terra 对一个会改变实验结论的问题发生冲突，而且测试无法裁决时使用。
- Worker 可以按任务需要调用任意数量的子代理，但每个子代理必须承担不同且有用的工作，不能为了显得充分重复调用。
- 不要求两组子代理数量相同；记录两组实际消耗的总 token、wall time 和未采用工作。
- 每次运行记录 provider 实际返回的模型 ID。如果模型路由没有按请求生效，两组改用同一个实际模型，不把路由差异混进结果。

## 8. 先跑多大

先跑两对完整实验，共四条轨迹。

- 如果两对都显示负向组能力不差且维护任务明显更容易，说明值得再换任务验证。
- 如果两对方向相反，再补一对，判断差异是否只是运行波动。
- 如果负向组能力下降、没有维护收益，或 review 成本超过收益，停止。

这只能说明该方法在这个任务上是否有价值，不能直接证明一般软件项目都适用。

## 9. 不要为实验建设什么

不建设数据库、状态机、事件协议、ledger、snapshot 系统、validator、审批流程或实验平台。

需要的只有：

- 两个工作目录；
- 七条需求；
- 两份 reviewer prompt 和一份 executor prompt；
- 测试；
- 一份简单运行记录。

能手工完成的步骤先手工完成。只有重复操作已经实际妨碍运行时，才写很薄的脚本。
