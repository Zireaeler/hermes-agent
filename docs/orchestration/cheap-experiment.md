# 第一对实验：scheduler 负向回顾

> 状态：已完成。本文保留实验协议和结果，不是当前 Runtime 方案。三次实验的最终综合判断见 `orchestra-design.md` 和 `HANDOFF.md`。

## 1. 要验证什么

只验证一个问题：

> 在同一段连续开发中，相比普通独立 review，只允许 `keep / remove / merge /
> simplify / doubt` 的独立负向回顾，能否在不损害已有能力的情况下，让后续维护更容易？

这不是完整 Orchestra 的验证。它不回答长期记忆、路线选择、自动停止或多 worker 编排是否有效。

如果负向回顾没有稳定收益，或收益抵不过 review 本身的成本，就停止，不建设更大的系统。

## 2. 实验任务

两组从同一个空目录开始，用相同的 Worker 完成相同的七轮本地任务调度器需求。

### R1

```text
构建一个本地任务调度器。需要支持：

- 注册一条 shell 命令，加上执行间隔（秒）
- 到时间自动执行
- 记录每次执行的时间和退出码

用 Python，不依赖外部服务。
```

### R2

```text
调度器重启后，已注册的任务不丢失，继续按原计划执行。
不需要额外依赖。
```

### R3

```text
除了固定间隔任务，还支持「在某个具体时间点执行一次」的任务。
执行完成后自动移除，不再触发。
```

### R4

```text
任务执行失败时（非零退出码），按配置的最大次数重试。
重试之间有固定间隔。记录每次尝试的结果。
```

### R5

```text
多个任务到期时同时执行，不互相等待。
同一个任务的上次执行未结束时，不重复启动。
```

### R6

```text
提供一个方式查看当前所有任务的状态：名称、下次执行时间、
最近一次结果、累计执行次数。
```

### R7

```text
不重启调度器的情况下，能够暂停某个任务、恢复它，以及删除某个任务。
```

每轮只给当前新需求，不提示保持简单，也不引导使用某种架构。

### 统一使用方式

为了让两组能运行相同测试，只规定最小 CLI，不规定内部结构：

```text
python scheduler.py add-interval <name> <seconds> -- <command...>
python scheduler.py add-once <name> <iso-time> -- <command...>
python scheduler.py run
python scheduler.py history <name>
python scheduler.py list
python scheduler.py pause <name>
python scheduler.py resume <name>
python scheduler.py delete <name>
```

允许增加必要参数，例如状态文件路径和 retry 次数，但上述操作在两组中必须可用。除此之外，模块、类、存储格式、并发方式和目录结构都由 Worker 决定。

## 3. 两组怎么跑

### 普通 Review 组

在 R3、R5、R7 完成并通过当轮测试后，由一个没有参与实现的 reviewer 检查当前项目。它可以建议：

- 修复真实问题；
- 普通重构；
- 增加确实缺失的实现；
- 删除、合并或简化已有结构；
- 不做修改。

### 负向回顾组

在相同的 R3、R5、R7 后运行独立 reviewer，但它只能输出：

- `keep`
- `remove`
- `merge`
- `simplify`
- `doubt`

它不能增加产品能力、设计替代架构，或把一个发现扩展成新的流程和基础设施。

### 共同流程

```text
完成当前需求
→ 运行当轮公开测试
→ 若失败，由当前 Worker 修到通过
→ 在 R3、R5、R7 交给独立 reviewer
→ 相同配置的 executor 执行 reviewer 建议
→ 再次运行当轮公开测试
→ 继续下一轮需求
```

只有当当前公开测试已经通过时才进入 review。Reviewer 不负责修复已知测试失败，避免普通组获得额外的纠错机会。Reviewer 输出 no-op 完全合法。Review 和 cleanup 不得替代 R1–R7 中的任何需求。

两组保持一致的内容：

- 起始目录和运行环境；
- R1–R7 原文；
- Worker、reviewer 和 executor 的模型与 reasoning effort；
- review 发生的轮次；
- reviewer 能看到的材料；
- 每次 review 和执行可用的大致时间与 token；
- 公开测试、最终能力测试和后续维护任务。

唯一有意改变的是 reviewer 可以提出什么类型的动作。

## 4. Reviewer 能看到什么

两组 reviewer 都只看：

- 已经给出的 R1–当前轮需求；
- 当前代码和文档；
- 当前公开测试结果；
- 实际引用、调用和运行情况；
- 用户明确给出的安全边界。

Reviewer 不看：

- 另一组的代码和结论；
- 此前 reviewer 的辩护；
- 作者为什么采用当前设计；
- 实验希望哪一组更简单。

依赖、调用和测试结果是事实；“语义重复”“概念太多”“架构不健康”是 reviewer 的判断，必须回到代码和行为验证。

具体 prompt 见 `deep-review-prompt.md`。

## 5. 怎么判断能力有没有受损

### 每轮公开测试

R1–R7 各有一小组公开测试，只检查截至当前轮已经提出的行为。每轮测试通过后才继续，避免把早期实现错误带到后续 review。

测试通过统一 CLI 从外部运行，不依赖某组内部类名和模块结构。时间相关用例使用短间隔和宽松容差，例如 0.2 秒间隔、在 1.2 秒内观察至少 4 次执行；不为测试引入 fake clock 或专用时间框架。

### 最终未公开测试

两组最终运行相同的未公开变体：

1. 使用不同间隔和命令检查重复执行；
2. 一次性任务只执行一次；
3. 失败任务按不同配置次数重试；
4. 调度器被强制终止后重启，未完成任务继续，已完成的一次性任务不重复；
5. 每次尝试的时间和退出码可查询；
6. 长任务不会发生同任务重入；
7. 多任务可以并行；
8. 暂停、恢复和删除不影响其他任务。

公开测试和最终测试在两组运行前写好，不根据某组实现修改。最终测试只用于评分，结果不回灌给 Worker 继续修复。

负向组只要损坏核心能力，就不能用“代码更少”抵消。

## 6. 怎么判断后续维护是否更容易

R7 完成后，从每个成品分别复制两份，让全新的维护 agent 完成相同的后续任务。原 Worker 和 reviewer 都不参与。

### 维护任务一：增加执行超时

```text
每个任务可以配置执行超时。超过时间后终止该次进程，记录为超时；
后续重试、执行历史、持久化和不重入行为继续正确工作。
```

### 维护任务二：删除失败重试能力

```text
删除失败自动重试能力及只为它存在的实现和配置。
保留间隔任务、一次性任务、并发、不重入、持久化、状态查询、暂停、恢复和删除。
```

两个维护任务在各自独立副本上执行，互不影响。记录：

- 是否正确完成并通过对应测试；
- wall time 和 token；
- 失败尝试次数；
- 修改涉及多少文件和模块；
- 是否引入与任务无关的机制；
- 是否造成已有能力回归。

这比统计类数、文件数或命名实体数更接近真正的结构负担。LOC、文件数和实体数可以记录，但只作旁证。

## 7. 模型、隔离和子代理

第一对实验统一使用 GPT-5.6 Sol、`high` reasoning effort，避免模型差异混入结果。每次运行记录 provider 实际返回的模型 ID。

所有 Worker、reviewer、executor 和维护 agent 使用独立工作目录、独立会话和干净上下文。它们不得读取宿主机的全局 `AGENTS.md`、`CLAUDE.md`、memory、skills、历史 session、Orchestra 文档或另一组结果；只传入当前角色需要的需求、代码、测试和 prompt。认证与 provider 配置可以传入，但不能附带用户工作指令。

Worker 可以按任务需要调用任意数量的子代理，但每个子代理必须承担不同且有用的工作，不能为了显得充分重复调用。不要求两组子代理数量相同；记录两组实际消耗的总 token、wall time 和未采用工作。

每个 agent turn 都是单次有限任务，不自动重试、不自动继续 review，也不在后台生成下一轮需求。超时或持续没有实质进展时直接终止并记录，不建设恢复系统。

## 8. 原定样本规模（已完成）

原协议先跑一对完整实验，共两条轨迹。

- 如果负向组能力不差且维护任务明显更容易，再补一对确认是否能复现；
- 如果两组都很直接、没有维护差异，这本身说明当前环境下不需要额外负向回顾；
- 如果第一对结果有信号但原因不清，再补一对；
- 如果负向组能力下降、没有维护收益，或 review 成本超过收益，停止。

只有前两对方向冲突时才考虑第三对。这只能说明该方法在这个任务上是否有价值，不能直接证明一般软件项目都适用。

## 9. 不要为实验建设什么

不建设数据库、状态机、事件协议、ledger、snapshot 系统、validator、审批流程或实验平台。

需要的只有：

- 两个工作目录；
- 七条需求；
- 两份 reviewer prompt 和一份 executor prompt；
- 测试；
- 一份简单运行记录。

能手工完成的步骤先手工完成。只有重复操作已经实际妨碍运行时，才写很薄的脚本。

## 10. 第一对结果和第二对

第一对 scheduler 实验已经完成：

- 两组 R1–R7 公开能力均通过；
- 最终有效隐藏行为维度均通过；
- 负向组成品在“增加执行 timeout”和“删除 retry”两个维护任务中均正确完成，合计 wall time 少约 38%，成本少约 56%；
- 负向 review 主轨迹本身并不更便宜，收益主要出现在后续维护；
- 一对轨迹不足以作因果结论，两组从 R1 起的 JSON/SQLite 架构差异和项目内测试策略是明显混杂因素。

因此按第 8 节规则补跑第二对。第二对改用完全确定、无持久状态、无真实时间和无并发的 JSON 决策规则解释器，检查信号能否跨问题类型复现。具体规格见 `rule-interpreter-experiment.md`。
