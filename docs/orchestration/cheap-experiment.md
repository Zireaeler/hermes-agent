# 廉价实验：否定能力是否存在

验证 `orchestra-design.md` 的核心假设，在建设任何东西之前完成。

## 0. 为什么先做这个

那份设计的全部价值压在一个能力上：定期深审能否真的砍掉不该存在的东西。这个能力
**不需要任何基础设施就能测**——一个循环脚本加一个 prompt 即可。

反过来说，如果不先测就按设计往下建，就会重复一条已知的失败路径：建了大量机制，
核心假设一次都没验证过。

## 1. 要回答的问题

先写死，跑完不许改。

**主问题（二元，生死线）**

> 加了深审的自动循环，到底会不会真的砍掉东西？

一次都没有，设计即失效，后续细节无需讨论。这个问题 n=1 就能回答，这是本实验便宜的
根本原因。

**次问题**（主问题为「是」时才有意义）

- 砍掉的是不是真该砍（有无误杀）
- 最终产物 B 是否比 A 更小，且能力相当
- 无上下文的读者理解 B 是否比 A 容易
- B 多花了多少时间和 token

## 2. 实验对象

### 2.1 任务结构：迭代扩展序列

**不是一个单一 goal。** 一个有能力的 worker 一个 goal 内就能做完整个调度器，根本不会
产生多轮。实验的「轮」是人为制造的：每轮给一个新的需求扩展，worker 在同一个代码库上
叠加。

这样膨胀是自然发生的，不是被逼出来的——每一轮需求都合理，worker 每一步都在「正当地」
加东西，只有积累起来才看出形状。这正是要观察的病灶形态。

### 2.2 初始规格（第 1 轮，两组相同）

```text
构建一个本地任务调度器。需要支持：

- 注册一条 shell 命令，加上执行间隔（秒）
- 到时间自动执行
- 记录每次执行的时间和退出码

用 Python，不依赖外部服务。
```

这是最小的起点，正确解 50 行以内。Worker 在这一步加额外的东西也没关系，那本身就是
观测数据。

### 2.3 扩展序列（第 2-7 轮，两组相同，逐字一致）

每一轮只给新需求，不给任何架构建议，不说「基于上一轮修改」，不说「保持简单」。
就是新的需求陈述，让 worker 自己决定怎么做。

**第 2 轮**
```text
调度器重启后，已注册的任务不丢失，继续按原计划执行。
不需要额外依赖。
```

**第 3 轮**
```text
除了固定间隔任务，还支持「在某个具体时间点执行一次」的任务。
执行完成后自动移除，不再触发。
```

**第 4 轮**
```text
任务执行失败时（非零退出码），按配置的最大次数重试。
重试之间有固定间隔。记录每次尝试的结果。
```

**第 5 轮**
```text
多个任务到期时同时执行，不互相等待。
同一个任务的上次执行未结束时，不重复启动。
```

**第 6 轮**
```text
提供一个方式查看当前所有任务的状态：名称、下次执行时间、
最近一次结果、累计执行次数。
```

**第 7 轮**
```text
不重启调度器的情况下，能够暂停某个任务、恢复它，以及删除某个任务。
```

膨胀高发轮次预测：第 4 轮（重试策略接口、指数退避）、第 5 轮（线程池、任务状态机）。
深审最有可能在第 4-5 轮之间触发。

### 2.4 为什么选这个任务

- **正确解明显比诱人解简单**：每一轮都有一个二十行能跑的直接实现，也有能写出几百行的
  「稳妥」实现。模型天然走后者。
- **验收客观**：能不能按时跑、崩溃后能不能恢复，是可执行的判定，不依赖主观评价。
- **形状和已知失败案例高度一致**：每一步单独看合理，累积起来是问题——这正是要检测的
  病灶形态。

### 2.5 隐藏验收测试

以下测试**在实验开始前定稿，对两组均不可见**，只在全部轮次结束后对两组各跑一次。

1. **定时执行**：注册一个每 2 秒执行一次的任务，10 秒内至少成功执行 4 次。
2. **一次性任务**：注册一个 5 秒后执行的任务，执行一次且仅一次。
3. **失败重试**：注册一个必然失败的任务并配置重试 3 次，实际尝试 4 次后停止。
4. **崩溃恢复**：运行中 `kill -9` 调度器后重启——未到期的任务照常执行，已完成的
   一次性任务不重复执行。
5. **执行历史**：能列出每次执行的时间和退出码。
6. **不重入**：一个执行耗时超过其间隔的任务，不应在上次未结束时被重复启动。
7. **并发暂停**：暂停一个任务后，其他任务继续执行不受影响；恢复后按原计划继续。

## 3. 两个 Arm

### 3.1 A 组（对照）

```text
worker 完成一轮 → 写阶段总结 → 据总结生成下一轮任务 → 继续
```

**A 不能是稻草人。** 生成下一轮任务必须是一次正经的 LLM 调用，prompt 质量与实际会用
的相当。它唯一缺少的是否定能力。

若 A 自发出现了删减动作，那是有效结果（说明不需要深审），**不得加以限制**。

### 3.2 B 组

与 A 完全相同，外加：

1. 每轮交付后由便宜模型生成一次现状快照（清单 + 计数）；
2. 命名实体数越过阈值时，按 `deep-review-prompt.md` 跑一次深审；
3. 移除清单作为下一个任务派给 worker；
4. 验收标准是**下一次快照的计数必须真的下降**。

### 3.3 必须固定的变量

模型、初始规格、扩展序列内容、起始仓库状态、worker 侧 prompt、轮数、运行环境。
A 与 B 的差别**只有深审这一件事**。

## 4. Prompt

深审 prompt 见 `deep-review-prompt.md`。以下两份为本实验专用。

### 4.1 下一步生成（A、B 共用）

```markdown
你在推进一个项目。以下是这一轮的新需求、当前代码库的状态，以及本轮交付总结。
输出下一轮的任务。

【本轮新需求】
<当前轮次的需求陈述>

【已有能力】
<worker 这一轮交付总结里描述的已实现功能>

【下一轮需求】
<下一轮的需求陈述（从扩展序列里取，逐字原文）>

输出：做什么、明确不做什么、什么算完成。
```

注意：下一轮需求从固定的扩展序列里取，A 和 B 完全一致。这个 prompt 只是让 worker
在上下文里理解当前状态，不让它自由发挥「下一步该做什么」。

### 4.2 现状快照（B 组每轮，A 组仅最后一轮用于测量）

```markdown
清点当前项目状态。只做清点，不做评价。

1. **命名实体清单**——每一个需要新读者去理解的、有专有名称的东西：
   源码模块、导出的类与主要函数、配置项、机制名称、文档章节。
   每项一行：`名称 | 类型 | 所在位置`
2. **总数**
3. **语义重复**——做同一件事的多处实现，写法不同不算不同
4. **未被使用的条目**——已定义但没有任何地方调用或触发
5. **当前实际能力**——这个项目现在能做什么（对照需求逐条列）

不要评价好坏，不要提改进建议。
```

计数口径对两组必须一致，用同一份 prompt 和同一个模型。绝对准确度不重要，**一致性
才重要**，因为比较的是 A 与 B。

## 5. 触发器与阈值

- 首次深审：累计命名实体达到 **10**
- 之后每新增 **5** 触发一次
- 每组 **7 轮**（固定，两组相同）

**开跑前必须做的检查**：手动过一遍扩展序列，预估 7 轮下来会长到多少个实体。若根本
到不了 10，阈值需下调，否则深审一次都不触发，实验白跑。

阈值偏低优于偏高——主问题是「是否曾经否定」，触发次数越多观测机会越多。

## 6. 测量

跑之前定义完，跑完不许加指标。

| 指标 | 测法 |
|---|---|
| 是否发生否定 | B 的移除清单非空且被执行的次数 |
| 否定质量 | 每一项由人 + 一个未参与的模型**独立**判定「该砍／不该砍」 |
| 最终规模 | A、B 各自的命名实体数、模块数、总行数 |
| 能力 | §2.5 的隐藏测试，两组各跑一次，记通过项 |
| 可读性 | 无上下文的模型读最终状态，回答「这是什么、是否健康」，人打分 0-5 |
| 成本 | wall time、token 用量 |

否定质量必须**双盲判定**：判定人不应在判定时知道哪一项来自哪次深审的什么背景，先各自
判完再对齐。已知结论会不自觉放宽标准。

## 7. 预注册

**开跑前写下以下内容，写在这份文档的末尾，写完不许改：**

- A 组预计最终实体数
- B 是否会触发至少一次深审（是/否）
- B 若触发，预计砍几次
- 哪一轮最可能出现否定

这不是形式主义。事后重写报告以匹配结果是有先例的失败模式，预注册是唯一能防住它的手段。

## 8. 结果判读

| 结果 | 含义 | 下一步 |
|---|---|---|
| B 砍了 ≥1 次且砍对了，最终更小、能力相当 | 假设成立 | 按 `orchestra-design.md` 往下建 |
| B 一次没砍，但 A 明显膨胀 | 深审失效——关键负面结果 | 参考 `HANDOFF.md §5` 调整 prompt，再跑一次；仍无则设计有根本问题 |
| B 一次没砬，A 也没膨胀 | 任务选错，无膨胀空间 | 换任务重跑，**不得据此下任何结论** |
| B 砍错了，能力下降 | 能力存在但缺护栏 | 提高举证门槛（见 `deep-review-prompt.md`），值得继续 |
| B 明显更贵且形状无改善 | 不值得 | 重新考虑深审频率或整个设计 |

**先确认 A 有没有膨胀，再判断 B 的失败性质。** 第三行极易被误读成第二行。

## 9. 这个实验不许建什么

明确禁止：数据库、状态机、validator、事件日志、持久化层、任何协议。

需要的只有：一个循环脚本、快照调用、三份 prompt（已在 `docs/orchestration/` 里）。

**总胶水代码控制在 200 行以内。若它开始变大，立即停止**——本实验的目的正是检测这种
增长，它自己先膨胀就失去了意义。

## 10. 规模估算

每组 7 轮，两组可并行。B 多出 2-3 次深审。整体一到两天挂钟时间，成本量级取决于模型
选择，预计几十美元。

## 11. 已知缺陷

**每组 n=1，方差大。** 单次结果不足以说明「B 一般更好」。但主问题是二元的——否定能力
是否存在——n=1 足以证伪。若 B 未砍，建议再跑一次 B 再下结论：否定是低概率事件，单次
未出现不等于能力缺失。

**任务由知道假设的人选定，有偏向风险。** 缓解：任务陈述定稿后，先让一个不知道实验目的
的模型评一句「这个任务有多大过度设计空间」，避免潜意识选了偏向 B 的题。

**深审可能砍的是无关痛痒的东西**（删个 stub 也计入「砍了」）。因此 §6 的否定质量判定
必须做，只数次数会自欺。

**审查者模型的自我偏好。** 若审查者与 worker 同族，存在自我偏好风险。选型见
`deep-review-prompt.md` 的说明。

## 12. 执行清单

按顺序，不跳步。

- [ ] 1. 确认扩展序列内容已定稿，逐轮任务陈述中性（无「保持简洁」类字眼）
- [ ] 2. 隐藏验收测试（§2.5）封存，两组 worker 均不可见
- [ ] 3. 预估 7 轮下来的实体增长，确认阈值 10 能被触发；不能则下调
- [ ] 4. **写下预注册预期**（见 §7，写在本文档末尾）
- [ ] 5. 搭循环脚本（≤200 行）：A、B 共用主循环，B 多一个深审分支
- [ ] 6. 并行跑两组，各 7 轮，使用相同模型和相同起始仓库
- [ ] 7. 两组各跑一次隐藏验收测试，记录通过项
- [ ] 8. 对两组各生成一次最终现状快照（用 §4.2 的 prompt）
- [ ] 9. 收集 §6 全部指标；双盲判定否定质量
- [ ] 10. 对照 §8 判读，写结论——**必须与预注册对照，结论不得反推预期**
