# orchestra 首版实施设计

> 本文把 [`design.md`](design.md) 的行为设计落到 Hermes 现有能力上。目标是让实现者可以直接开始写首版，而不是继续补充抽象架构。

## 0. 实施结论

首版只实现一个很薄的外层驱动：

```text
当前项目事实与人类变化
        │
        ▼
全新的 orchestra 会话
        │  检查事实、更新项目状态、生成一个 worker 任务
        ▼
一个当前活动 worker
        │  在明确任务内完整执行
        ▼
worker 最终结果
        │
        └────────→ 下一次全新的 orchestra 会话
```

首版不实现新的多代理运行时，不实现执行图、任务数据库、消息队列、自动决策边界、状态校验器或多 worker 调度。

需要新增的代码只有：

```text
一个薄 Python 启动器
少量固定提示词
四份可整体覆盖的本地材料
对现有 orchestra / worker 会话的启动和恢复调用
```

## 1. 直接复用 Hermes 的能力

### 1.1 orchestra 直接使用 `AIAgent`

Hermes 的 `run_agent.AIAgent` 已经具备：

- 模型调用；
- 工具循环；
- 多轮会话；
- 工具选择；
- 会话标识；
- 上下文文件与记忆开关；
- 推理强度与最大轮数；
- 错误处理和现有日志。

首版不再包装第二套代理循环。每次 orchestra 决策轮直接创建一个新的 `AIAgent`。

建议的关键参数：

```python
AIAgent(
    session_id=<每轮新生成的标识>,
    ephemeral_system_prompt=<orchestra 固定职责>,
    skip_context_files=True,
    skip_memory=True,
    load_soul_identity=False,
    enabled_toolsets=<首版检查工具>,
    max_iterations=<允许完成一次完整检查的上限>,
)
```

这些参数的含义是：

- 每轮使用全新会话标识；
- 不加载上一轮 orchestra 对话；
- 不加载项目外的记忆、人格和普通上下文文件；
- 不继承父会话；
- 只提供当前决策所需的检查工具；
- 单轮内仍允许完整代理循环。

首版不启用 orchestra 子代理，不启用旧 Kanban 工具，也不调用旧运行时内核。

### 1.2 worker 直接使用现有成熟实现

worker 继续使用已经稳定的 Codex、Claude Code 或 Hermes 现有编码代理入口。

首版只选择一个实际可用的 worker 后端，不先设计通用 worker 接口。启动器只需支持：

```text
启动一个新 worker 会话
恢复当前任务的 worker 会话
向 worker 投递推进说明
取得 worker 最终结果
取消当前 worker
```

worker 内部如何规划、调用子代理、压缩上下文、运行测试和修复错误，不属于首版外层代码。

### 1.3 直接复用现有安全和进程能力

首版沿用 Hermes 已有的：

- 工具审批；
- 终端安全检查；
- 进程管理；
- 隔离环境；
- 模型配置；
- 使用量记录；
- 会话持久化。

不要因为 orchestra 新增第二套权限系统、进程恢复系统或审计协议。

## 2. 首版本地材料

首版在 Hermes 主目录下为每个目标项目保存一个控制目录：

```text
$HERMES_HOME/orchestra/<project-key>/
├── state.md
├── task.md
├── result.md
└── worker-session.txt
```

`project-key` 可以由仓库绝对路径的稳定摘要产生，也可以在首版由人类显式指定。不要为它设计注册中心。

### 2.1 `state.md`

唯一长期持久的项目语义材料。

它包含当前有效的人类意图、项目事实、承重假设、收敛缺口、重要停止路线和当前决定残留。它每次整体覆盖，不追加运行日志。

它不是固定格式。实现不得：

- 校验章节是否齐全；
- 给文件增加版本号；
- 为旧格式编写迁移；
- 自动合并多个版本；
- 因缺少某个小节拒绝运行；
- 要求 worker 读取或维护它。

### 2.2 `task.md`

当前 worker 推进说明。每次 orchestra 选择新任务或修正当前任务后整体覆盖。

它只包含 worker 当前需要知道的项目事实和边界，不包含完整 `state.md`，也不包含 orchestra 推理过程。

### 2.3 `result.md`

最近一次 worker 最终结果。每次 worker 结束当前执行后整体覆盖。

首版可以直接保存 worker 的最终回答，不要求 worker 返回版本化结构。提示词只要求它尽量说明：

- 实际改变了什么；
- 证据在哪里；
- 哪些内容没有完成；
- 是否发现会改变项目方向的新事实；
- 是否有承重假设失效。

下一轮 orchestra 必须把 worker 自述视为线索，而不是自动确认的事实。

### 2.4 `worker-session.txt`

只保存当前任务的 worker 会话标识。它是机械运行信息，不是项目状态。

新任务启动新 worker 后覆盖；当前任务继续时复用。文件损坏或丢失时，可以人工重新启动 worker，不建设恢复协议。

## 3. 首版命令边界

建议新增一个薄脚本：

```text
scripts/orchestra_v1.py
```

首版只需要三个入口：

```text
python scripts/orchestra_v1.py decide --project <path>
python scripts/orchestra_v1.py worker --project <path>
python scripts/orchestra_v1.py status --project <path>
```

可以额外接受一段人类变化：

```text
--human "本轮新增方向或约束"
--human-file <path>
```

不要在首版加入守护进程、后台轮询、自动任务队列或网络接口。

### 3.1 `decide`

`decide` 完成一次全新的 orchestra 决策轮：

1. 定位目标仓库和控制目录；
2. 读取 `state.md`；
3. 读取最近的 `task.md` 与 `result.md`；
4. 读取本轮人类变化；
5. 收集少量机械项目事实；
6. 创建全新的 `AIAgent` 会话；
7. 让 orchestra 按需检查仓库；
8. 保存新的 `state.md` 与 `task.md`；
9. 记录本轮决定是继续当前任务、新任务、等待、询问人类或停止；
10. 结束 orchestra 会话。

### 3.2 `worker`

`worker` 根据最新决定运行当前 worker：

- 继续当前任务：恢复 `worker-session.txt` 指向的会话；
- 新任务：启动新的 worker 会话并覆盖会话标识；
- 等待、询问人类或停止：不启动 worker；
- worker 结束后，把最终回答保存为 `result.md`。

首版始终只有一个活动 worker。

### 3.3 `status`

`status` 只显示：

- 当前项目路径；
- 当前决定；
- 当前 worker 会话标识；
- `state.md`、`task.md`、`result.md` 的更新时间；
- 是否存在活动 worker 进程。

它不解释项目状态，不计算进展，不判断是否完成。

## 4. 每轮输入怎样组装

启动器不总结整个仓库，只组装最小机械输入。

### 4.1 稳定前缀

稳定前缀只包含：

- orchestra 的职责；
- orchestra 与 worker 的边界；
- 禁止继承旧策略叙事；
- 禁止把代理自建机制自动升级为目标；
- 默认只读检查业务代码；
- 一次只选择一个当前任务；
- 输出要求。

稳定前缀可以命中模型前缀缓存，但不能包含上一轮 orchestra 生成的消息。

### 4.2 当前项目材料

直接放入：

- `state.md`；
- 最近 `task.md`；
- 最近 `result.md`；
- 本轮人类变化。

`result.md` 必须明确标注为 worker 自述，不能与已确认事实混合。

### 4.3 机械项目事实

启动器可以直接附加：

```text
项目绝对路径
当前分支
当前提交
git status --short
git diff --stat
最近少量提交标题
```

这些内容只帮助 orchestra 定位当前仓库状态。不要由启动器推断项目含义，也不要生成代码库全量摘要。

### 4.4 按需证据

其余代码、差异、测试、日志和运行结果由 orchestra 在本轮内按需读取。

首版不预先把以下内容塞入请求：

- 完整仓库；
- 完整 worker 对话；
- 旧 orchestra 会话；
- 历史调试记录；
- 所有旧任务结果；
- 全局记忆和通用技能材料；
- 旧运行时内核文档，除非本轮问题直接需要。

## 5. orchestra 的固定职责提示词

首版固定提示词应保持短且稳定，可以采用下面的内容作为起点：

```text
你是项目级 orchestra，不是编码 worker。

你只在项目决策边界工作。你的任务是从当前人类意图、项目状态、
最新结果和真实仓库证据中，重新判断项目现在为什么还没有成立，
并选择一个当前最有价值、可由完整 worker 独立完成的任务。

不要继承上一轮 orchestra 的叙事。旧决定和 worker 总结只是线索，
不是事实。重要判断应尽量由代码、测试、运行结果或人类输入支持。

不要替 worker 设计文件、类、实现步骤和子代理分工。不要因为代码中
已经存在某个机制、测试、待办或恢复责任，就把继续完善它当成项目目标。

一次只选择一个任务。普通实现选择、测试失败和局部调试留给 worker。
只有项目方向、承重假设、外部承诺、不可逆风险和真正的人类价值选择
属于你的判断范围。

默认只读检查业务代码。你只更新当前项目状态和 worker 推进说明。
项目状态可以直接重写和删除，不要把它扩建成协议、账本或运行时系统。
```

首版实际运行后，可以调整措辞，但每次只修改一个主要问题，不不断累加规则。

## 6. orchestra 输出约定

为了让薄启动器保存结果，首版只约定三个 Markdown 一级标题：

```markdown
# 当前决定

# 项目状态

# worker 推进说明
```

### 6.1 当前决定

第一行使用一个简单动作：

```text
继续当前任务
启动新任务
等待
询问人类
停止
```

后面可以用自然语言说明原因。

启动器只读取第一行决定是否运行或恢复 worker。不要为动作建立版本号、复杂状态机或校验流程。

### 6.2 项目状态

这里必须给出下一轮使用的完整 `state.md` 内容，而不是差异修订。

如果 orchestra 没有可靠依据改变某项判断，应保留不确定性，而不是补齐看似完整的事实。

### 6.3 worker 推进说明

只有“继续当前任务”或“启动新任务”时才需要。建议包含：

```markdown
## 期望项目变化

## 为什么现在做

## 相关事实

## 当前工作假设

## 自主决策范围

## 必须保留

## 所需证据

## 何时提前上报
```

这些标题是给 worker 阅读的写作提示，不是字段协议。缺少不相关小节不应阻止运行。

### 6.4 输出解析失败

如果模型没有按三个一级标题输出：

- 保留原始回答；
- 由人类在首版调试中手工整理；
- 记录这是提示词或上下文问题；
- 不自动重试多轮；
- 不新增解析修复器、校验器或兼容层。

## 7. orchestra 的工具与代码权限

### 7.1 默认检查能力

首版 orchestra 需要：

- 读取文件；
- 搜索文件与内容；
- 查看 Git 状态和差异；
- 运行只为判断项目事实所需的测试或命令；
- 查看必要日志和已有产物。

不需要：

- 写业务代码；
- 提交 Git；
- 安装或升级依赖；
- 修改数据库；
- 发布和部署；
- 启动长期后台服务；
- 调用子代理。

### 7.2 首版机械约束

优先通过现有 Hermes 工具选择和审批能力限制写操作。若当前工具配置无法完全只读，首版至少做到：

1. 决策轮开始前记录仓库状态；
2. 提示词明确禁止业务修改；
3. 决策轮结束后检查业务文件是否变化；
4. 若发生变化，不接受这些修改，把它作为 orchestra 越界问题处理。

不要为了这一点建设新的通用沙箱。已有隔离能力足够时直接复用。

## 8. worker 输入与结果

### 8.1 worker 只接收当前任务

worker 默认接收：

- `task.md`；
- 当前仓库；
- 与任务直接相关的人类补充；
- 现有 worker 会话中的局部上下文，仅限继续同一任务时。

worker 默认不接收：

- 完整 `state.md`；
- orchestra 的完整输出；
- orchestra 推理过程；
- 旧 worker 会话；
- 历史调试记录。

任务所需的项目事实必须已经写入 `task.md`。

### 8.2 worker 固定补充说明

可以在 worker 任务前附加：

```text
完整负责当前任务的调查、实现、测试和修复，并自行决定是否使用内部子代理。
不要替项目选择完成本任务之后的长期路线。

若发现推进说明中的承重假设失效、任务目标需要实质改写、必须改变外部承诺，
或当前任务已不再是一个连贯问题，停止扩大范围并明确上报该项目级事实。

完成时说明实际变化、可复核证据、未完成部分和可能影响下一轮项目判断的新事实。
```

### 8.3 worker 会话边界

```text
同一任务的调查、实现、测试、修复和补充验证
→ 恢复当前 worker 会话

仅补充证据或澄清同一完成结果
→ 恢复当前 worker 会话

期望项目变化、承重假设或自主决策范围实质改变
→ 启动新 worker 会话
```

新会话不读取旧 worker 对话。与新任务有关的事实必须由 `task.md` 重新提供。

## 9. 项目决策边界

首版由人类或主会话显式触发 `decide`。典型情况：

- 当前 worker 完成任务；
- worker 发现承重假设失效；
- worker 因项目级问题阻塞；
- 人类改变重大方向；
- 关键外部实验产生结果；
- 当前任务开始不断扩大为新的项目；
- 连续工作没有产生有效项目变化；
- 即将作出大范围或不可逆决定；
- 项目可能已经满足长期目的。

普通测试失败、局部设计变化、worker 内部子代理结果和普通提交不触发 orchestra。

首版不自动识别这些边界。只有实际运行表明手工触发成为稳定重复负担后，才考虑最小自动化。

## 10. 失败处理

### 10.1 orchestra 调用失败

- 保持原 `state.md`、`task.md` 和 worker 会话不变；
- 使用新的 orchestra 会话重新运行；
- 不恢复失败的 orchestra 对话；
- 不把失败输出并入项目状态。

### 10.2 orchestra 判断错误

调试期间由人类直接修正 `state.md` 或 `task.md`，然后继续。

不要建立回滚协议、冲突合并或判断仲裁系统。Git 和普通文件备份已经足够。

### 10.3 worker 进程失败

若仍是同一任务，优先恢复同一 worker 会话或按现有 worker 能力重试。若无法恢复，由人类决定是否以同一 `task.md` 启动新会话。

### 10.4 worker 上下文达到硬上限

这是同一任务内部的执行连续性问题。首版可以让旧 worker 生成一次局部任务交接，再以相同 `task.md` 和该交接启动新 worker。

该能力属于 worker 适配，不改变项目状态，也不触发多 worker 设计。

### 10.5 结果缺少证据

下一轮 orchestra 将其视为未确认结果，按需检查或要求 worker 补充同一任务。不要让启动器根据关键词自动认定任务完成。

### 10.6 人类中途改变方向

- 只澄清当前任务：直接补充给当前 worker；
- 改变项目方向、完成结果或外部边界：暂停当前 worker，启动新的 orchestra 决策轮。

## 11. 首版实现顺序

### 第一步：人工跑通两到三个决策轮

不写脚本，直接按文档：

1. 手工准备 `state.md`；
2. 启动全新 Hermes 会话扮演 orchestra；
3. 手工保存 `task.md`；
4. 启动一个实际 worker；
5. 手工保存 `result.md`；
6. 再启动全新 orchestra。

目的只是确认材料边界，不验证体系优越性。

### 第二步：实现 `decide`

只自动完成：

- 读取材料；
- 组装请求；
- 创建全新 `AIAgent`；
- 保存原始输出；
- 拆出三个一级标题；
- 覆盖 `state.md` 和 `task.md`。

### 第三步：接入一个 worker 后端

选择当前最稳定的 Codex 或 Claude Code 入口，直接实现新建、恢复、取消和取得最终结果。

不要同时接两个后端，也不要先建立通用适配框架。

### 第四步：连成一对一闭环

把决定动作和 worker 会话边界连通，但仍由人类显式运行 `decide` 与 `worker`。

### 第五步：只补真实暴露的缺口

例如：

- 状态材料缺少某类事实；
- worker 结果无法支撑下一轮判断；
- 任务边界经常判断错误；
- orchestra 检查过深或过浅；
- 人工触发点稳定后值得做一个简单提醒。

没有真实重复问题，不增加能力。

## 12. 首版完成标准

首版实现可以被认为可用，当它能够在一个真实项目中连续运行若干自然任务，并满足：

- 每个 orchestra 决策轮确实是全新会话；
- 下一轮不注入旧 orchestra 对话和推理；
- `state.md` 足以让新的 orchestra 恢复项目级判断；
- orchestra 能按需检查仓库，而不是只复述摘要；
- orchestra 不修改业务代码；
- 每次只产生一个当前任务；
- 同一任务可以恢复 worker，新任务默认新建 worker；
- worker 能自行使用内部子代理并完整完成任务；
- worker 结果能被下一轮作为线索重新核实；
- 人类可以直接改写状态和任务，不受格式约束；
- 没有新增数据库、执行图、版本协议、校验器或多 worker 系统。

这里没有要求一次项目演示覆盖所有失败模式，也不以任务数量、模型调用次数或文档完整度证明成功。

## 13. 首版明确不做

- orchestra 长期会话；
- 多 worker；
- worker 间通信；
