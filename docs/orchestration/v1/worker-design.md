# Orchestra v1 worker 设计

> 本文定义一对一 Orchestra 中成熟 worker 的上下文边界、任务执行方式、子代理使用、验证停止条件和结果返回方式。它补充 [`design.md`](design.md)，不把 Codex、Claude Code 等现有编码代理重新实现成一套新的工作流。

## 0. 设计结论

worker 不是一个被外层逐步控制的函数，也不是只执行单个文件修改的临时工具。它是一个在**当前明确任务**内保持连续上下文、能够自行调查、规划、调用子代理、实现、测试和修复的完整编码代理。

```text
orchestra
  负责决定当前项目为什么还没有成立，以及下一项完整任务是什么

worker
  负责把这一项完整任务做完，并对局部实现和验证结果负责

worker 内部子代理
  负责隔离能够独立回答的局部问题，由父 worker 统一核对和整合
```

worker 的长期性止于当前任务。任务完成、被证伪或被实质重新定义后，项目方向回到新的 orchestra 决策轮，不由 worker 自行选择下一阶段。

核心原则：

```text
任务内连续，任务间重新判断。
保留局部执行上下文，不继承项目级路线权力。
允许内部并行，不把同一任务再次拆成外层角色流水线。
验证足以支持结论即可，不把普通不确定性扩大为审计工程。
详细过程留在仓库，返回给 orchestra 的结果保持精简。
```

## 1. worker 接收什么

每次 worker 运行由三类材料共同约束，优先级如下：

```text
当前 task.md 与本轮固定 worker 约束
        > 当前仓库中的 AGENTS.md / CLAUDE.md
        > 当前工作区事实与测试结果
        > 旧 worker 会话中的计划、推断和实现叙事
```

旧会话的上下文只用于保存代码理解、调试状态和已完成的局部调查，不能覆盖新的任务说明、项目规则或当前工作区事实。

worker 不直接读取或维护 orchestra 的 `state.md`。它不需要掌握整个项目的长期判断，只接收完成当前任务所需的项目级事实、承重假设、边界和证据要求。

### 1.1 推进说明应提供的内容

任务应说明：

- 希望项目现实发生什么变化；
- 为什么现在值得做；
- 当前已经确认的相关事实；
- 当前工作依赖的承重假设，以及什么会证明它失效；
- worker 可以自主决定的范围；
- 不能破坏的能力和边界；
- 完成后需要哪些可复核结果；
- 哪些发现需要停止扩大范围并报告。

任务不应预先规定：

- 完整文件清单；
- 类和函数的具体设计；
- worker 内部步骤；
- 子代理数量；
- 固定的规划、编码、测试、评审阶段；
- 为未来需求准备的扩展接口。

只有当现有接口、文件或命令本身就是需要保持的项目事实时，推进说明才应点名它们。

## 2. 新任务、继续任务与上下文恢复

### 2.1 同一任务继续使用原会话

下列情况默认恢复同一个 worker 会话：

- 仍在调查、实现、测试或修复同一个可观察结果；
- orchestra 只是补充证据、澄清边界或指出同一结果中的明确缺口；
- 主要承重假设和自主决策范围没有改变；
- 原会话中的代码理解和调试状态仍直接有用。

### 2.2 实质不同的任务使用新会话

下列情况默认启动新的 worker 会话：

- 希望产生的项目变化已经改变；
- 核心承重假设被推翻；
- 产品含义或正确性标准被重新定义；
- 原任务已经完成，下一步进入新的产品方向；
- 旧会话持续维护已经失效的实现叙事；
- 需要真正独立的判别或核验视角。

新会话不是惩罚，也不是放弃此前代码，而是防止旧任务的局部叙事继续主导新的问题。

### 2.3 恢复或压缩后必须重新锚定

恢复旧 thread 或完成上下文压缩后，在继续业务执行前必须重新提供：

- 当前完整 `task.md`；
- 当前仓库的 `AGENTS.md` 约束；
- 当前工作区的关键变化；
- 最近一次与当前任务直接相关的验证状态。

worker 应先重新确认：

```text
当前要产生的可观察结果是什么？
哪些边界仍然有效？
哪些旧计划只是历史，不再具有约束力？
工作区现实是否已经使旧假设失效？
```

不要求 worker生成新的计划文档，也不保存完整重锚定过程。目的只是让当前权威材料重新压过旧会话中的惯性。

## 3. 开始实现前先识别不确定性的性质

worker 不应把所有不确定性都当成编码问题。开始大范围实现前，应在内部区分四类情况。

### 3.1 已由任务确定的语义

任务和项目规则已经明确的产品行为、数据边界和正确性要求，worker 直接实现，不重新讨论。

### 3.2 可以由领域事实回答的问题

例如市场规则、协议含义、第三方接口语义、数据字段含义。worker 可以自行调查，或委派一个有边界的子代理。

调查的目标是取得足以支持当前任务的可靠依据，不是建立完整领域知识库。

### 3.3 可以由小型实验回答的技术问题

例如某个库能否读取实际数据、两种局部实现哪个能满足当前约束、某项性能是否构成真实阻塞。worker 可以做可丢弃的小型实验，再决定实现。

实验必须服务当前判断；问题得到回答后应停止，不把实验脚本自然扩展成平台。

### 3.4 未被授权的产品选择

若不同选择会实质改变产品用途、数据模型、外部行为或正确性标准，而任务和人类意图没有决定，worker 不得静默选择。

此时应：

- 停止扩大实现；
- 说明存在的选择及其实际影响；
- 给出已经掌握的事实和仍缺少的信息；
- 把问题返回 orchestra。

worker 可以实现不影响该选择的公共基础，但不能为了“先做起来”把一种产品解释固化进代码和测试。

## 4. worker 内部子代理

成熟 worker 已经拥有自己的子代理系统。Orchestra 不管理子代理数量、角色或调用顺序，但 worker 需要保持以下边界。

### 4.1 适合委派的工作

子代理适合处理能够独立回答、且不会与主 worker 频繁共享局部推理的问题，例如：

- 查找代码库中与当前问题相关的实现；
- 调查一个陌生领域规则或外部第一方资料；
- 独立复现一个故障；
- 比较两个局部技术方案；
- 检查一个关键不变量或回归面；
- 对一份较大的数据或日志做有边界的采样分析。

这些工作可以显著减少主 worker 的搜索噪声，又不把局部决策中心拆散。

### 4.2 不适合委派成并行写入的工作

不要因为任务较大就按文件、类或固定角色拆分。以下情况通常不适合多个子代理独立修改：

- 同时改变同一个承重抽象；
- 需要频繁同步局部设计；
- 由不同子代理分别完成规划、编码、测试和评审；
- 多个实现最终必须由主 worker 逐行重新理解才能合并；
- 子代理自行决定项目方向或扩大产品范围。

父 worker 应维持一个清楚的局部决策中心，并对最终集成结果负责。

### 4.3 子代理返回内容

子代理默认只返回：

```text
结论
证据位置
仍未确认的内容
什么情况会推翻当前结论
```

详细命令流水、完整网页摘录、重复代码摘要和普通失败尝试不应全部回灌主 worker 上下文。必要的详细证据应写入仓库报告、测试或可定位的产物中，由主 worker 按需读取。

父 worker 不能把子代理自述直接当成事实。承重结论必须核对关键来源、代码位置或可重复结果。

## 5. 任务内执行循环

worker 可以自由采用最适合当前任务的执行方式，通常包括：

```text
理解当前任务和工作区
→ 查明关键事实与不确定性
→ 选择最小可行实现或判别实验
→ 修改并运行
→ 根据真实结果修正
→ 完成当前可观察结果
→ 做足以支持结论的验证
→ 返回精简结果
```

这不是固定阶段，不要求每次显式输出计划。worker 可以在任务内部回退方案、重构局部代码、修复测试和调用子代理。

worker 可以扩大**当前任务内部**的实现范围，但必须满足两个条件：

- 额外工作是完成同一个可观察结果不可避免的组成部分；
- 不会实质改变产品含义、数据模型或正确性标准。

普通待办、发现的相邻问题、未来扩展点和“顺手可以做”的整理，不自动进入当前任务。

## 6. 验证原则

### 6.1 目标是支持当前结论，不是最大化验证活动

worker 应运行足以支持当前任务结论的最小充分验证。验证强度由结论的承重程度、错误可见性和现有证据决定，而不是由“还能继续检查什么”决定。

优先顺序通常是：

```text
真实可观察行为
→ 与任务直接相关的端到端或集成结果
→ 承重业务不变量
→ 聚焦回归测试
→ 局部单元测试和静态检查
```

顺序不是固定要求，而是提醒 worker 优先证明项目行为，而不是只证明内部结构。

### 6.2 何时扩大验证

只有下列情况值得扩大：

- 当前结论直接依赖该事实；
- 已有证据相互矛盾；
- 错误可能静默污染结果；
- 任务、人类意图或外部协议明确要求；
- 当前失败无法由较小范围定位。

### 6.3 何时停止验证

当前业务问题已经被可靠回答，且继续检查不会改变任务结论时，应停止。

默认不做：

- 全仓库或全数据审计；
- 为普通文件建立哈希链或证据包；
- 为一次输入建立版本、迁移和恢复系统；
- 无上限的数据遍历和完整性证明；
- 因为“更严谨”而增加与当前结论无关的 gate；
- 用大量内部测试替代实际可运行结果。

外部协议、许可或人类明确要求字节身份时，必要的哈希核对仍然合理，但不能自然扩张成通用校验体系。

## 7. 完成前的内部反证检查

在最终回答前，worker 应快速检查：

```text
我是否真的产生了任务要求的可观察结果，而不只是增加代码或文档？
我是否静默选择了任务未授权的产品语义？
我是否增加了只服务未来设想、或只服务当前机制自身的工作？
哪个尚未验证的假设最可能使当前结论失效？
当前验证是否足以支持结论，还是只证明了局部实现能运行？
```

这不是新的评审阶段，不要求生成单独文档，也不要求启动固定 reviewer。若没有发现问题，直接完成；发现问题则修正，或将无法在当前范围内解决的内容写入结果。

## 8. worker 结果

### 8.1 结果应面向下一次项目判断

`result.md` 的作用不是保存完整执行历史，而是让新的 orchestra 能快速理解本任务实际改变了什么。

worker 最终回答默认保持为：

```markdown
完成：
本任务产生的真实可观察变化。

验证：
支持该结论的关键命令、结果和产物位置。

未闭合：
任务范围内仍未完成、失败或无法确认的内容。

影响项目方向：
被推翻的承重假设、新出现的产品问题或会改变下一步的事实；没有则写“无”。

产物：
相关提交、文件、报告或运行结果位置。
```

不要求程序解析这一结构，也不建立版本化输出协议。

### 8.2 详细信息留在哪里

- 代码事实留在代码和 Git；
- 测试细节留在测试和测试输出；
- 长调查留在独立报告；
- 数据统计留在对应产物说明；
- 普通调试过程留在 worker 会话和日志；
- `result.md` 只保留关键结论与索引。

不要把同一份详细材料同时复制到 README、调查报告、最终回答和 `result.md`。

### 8.3 哪些失败值得保留

只长期保留：

- 成本较高、未来很可能重复的失败路线；
- 能推翻承重假设的失败；
- 表明任务需要重新定义的失败；
- 无法通过局部修复解决的外部阻塞。

普通编译错误、一次测试失败、搜索过程和已解决的局部误判不应进入下一次 orchestra 上下文。

## 9. 完成、阻塞与提前返回

worker 可以在以下情况结束当前 turn：

### 完成

当前任务要求的可观察结果已出现，验证足以支持结论，没有未处理的任务内阻塞。

### 阻塞

外部资源、权限、环境或缺失事实使当前任务无法继续。worker 应说明已经确认的阻塞、已尝试的最小必要动作和解除阻塞所需条件，不自动创建替代任务。

### 承重假设失效

继续实现会建立在已被证伪的前提上。worker 应停止扩大范围，把证据和影响返回 orchestra。

### 产品选择未授权

事实不足以在多个产品含义之间裁决。worker 应返回问题，不把任一解释隐藏进实现。

### 当前任务需要实质重定义

新增工作已不再只是完成同一个可观察结果，而是进入新的产品方向。worker 应完成安全收尾后停止，由 orchestra 重新决定。

## 10. worker 不负责什么

worker 不负责：

- 维护项目长期路线；
- 选择当前任务完成后的下一项任务；
- 修改 `intent.md` 或 orchestra 的 `state.md`；
- 把普通发现升级为项目目标；
- 建立多 worker 调度和外层通信；
- 为证明自己完成而重新定义完成标准；
- 用更多文档、测试、校验和基础设施制造进展感；
- 把内部子代理的结论直接提升为项目事实。

## 11. 首版暂不采用的机制

首版不增加：

- worker 自报的 `requires_direction`、影响等级或完成类型字段；
- 数值置信度；
- append-only 事件账本；
- 固定 reviewer 或 auditor；
- 子代理任务图和角色队列；
- 自动决定是否触发 orchestra 的分类器；
- 对 worker 最终回答的结构校验和自动修复。

当前每个完整 worker 任务结束后，本来就会形成新的项目决策边界。先通过真实运行校准结果质量和任务边界，再判断是否存在需要自动化的稳定缺口。

## 12. 判断设计是否有效

良好的 worker 行为应逐渐表现为：

- 在当前任务内保持连续、完整的执行能力；
- 恢复或压缩后仍围绕当前任务，而不是旧计划；
- 子代理减少搜索噪声，而不是增加整合成本；
- 能区分领域调查、技术实验和产品选择；
- 不把普通不确定性扩大成全面审计；
- 结果简短，但能够支持下一次 orchestra 判断；
- 完成后主动停止，不继续选择项目下一阶段。

若长期出现以下现象，应优先修正任务说明、固定 worker 约束或上下文组装，而不是立即建设新运行时：

- worker 每次恢复后重复旧路线；
- 子代理输出大量无关过程并占满主上下文；
- worker 经常静默固定产品语义；
- 验证范围持续远大于当前结论需要；
- `result.md` 变成完整流水日志；
- worker 完成当前任务后继续实现下一阶段；
- orchestra 无法从结果中区分事实、推断和未确认内容。
