# orchestra 首版详细设计

> 本文定义一对一 orchestra 的项目状态、上下文组装、决策方法、任务边界和运行节奏。顶层定位见 [`../orchestra-design.md`](../orchestra-design.md)，worker 的任务内行为见 [`worker-design.md`](worker-design.md)。

## 0. 设计结论

首版采用三种不同的连续性：

```text
人类意图与项目状态
  跨整个项目长期存在

orchestra 决策轮
  每次从当前材料重新构建，不继承旧对话和推理叙事

worker 会话
  在一个明确任务内连续，任务实质改变后重新开始
```

整体循环：

```text
当前人类意图、项目状态、最近结果与仓库事实
                    ↓
           全新的 orchestra 决策轮
                    ↓
       选择调查、实验、实施、继续、询问或停止
                    ↓
              一个完整 worker
                    ↓
       可观察结果、证据、失败或承重发现
                    ↓
           下一次全新的 orchestra 决策轮
```

首版严格一对一。任何时刻只有一个活动 worker；worker 可以在当前任务内部使用自己的子代理，但 orchestra 不拆分或管理这些子代理。

显式团队模式是用户于 2026-10-21 新授权的例外，见下节；旧单 worker 命令维持原行为。

### 显式有限团队模式

`run-team` 由一个项目 Orchestra 在最多 4 个槽位中分配完整责任。每个 worker 的全部后代合计最多 3 个并发子代理，因此 worker 执行代理总数最多 4×(1+3)=16；Orchestra 本身单独串行判断，不占执行槽。子代理限制须由 Codex 实际配置执行，不能仅靠任务文字。worker 可以少于 4 个、子代理少于 3 个，实际数量取决于任务价值。后代的后代仍消耗同一额度，不额外施加用户未要求的深度限制。

Orchestra 每次输出当前状态与明确的 start/keep/stop 分配。保持活动任务不修改其指令；改向先请求该槽交回控制，确认真实终态后才允许替换。任务结束和周期检查均触发 fresh 团队判断，全部活动任务及其结果可见；不等待所有 worker 结束才重新决策。缺少真实终态时结束并报告现场，不将空闲槽位视为继续执行旧未确认任务的许可。

团队中的“等待”且仍有活动 worker，表示本轮不增加任务、继续等待所列 keep 的执行结果，并不结束团队或取消它们；完成事件和周期检查仍继续触发判断。只有没有活动 worker 时的“等待”，才作为本次执行退出边界。询问人类、停止、总预算和用户取消仍结束整次运行。不能把单 worker 入口的终止语义直接复用于有限团队。

Orchestra 的临时模型服务故障或无效格式不构成项目停止决定。调用未取得可应用的分配时，保留原状态和活动任务，保存错误，并按 30 秒起、最多 300 秒的间隔延后 fresh 决策；实际执行的完成与结果照常收集。总预算、用户停止及终态未知保护仍即时有效，不为等待服务恢复突破预算。只重试明确的临时调用故障和格式失败，不将配置、文件读写或程序错误伪装成模型繁忙，也不增加修复输出的代理。

worker 在项目中新研究目录下各自槽位的工作目录运行，读取共享仓库与其他槽成果，但只写自身目录，避免并发覆盖和旧报告被改写。Orchestra 决定如何组织跨领域问题、交叉验证与持续综合，不预先固定四个领域，也不把最终报告变成四份孤立结论。最终比较须以旧研究的实际证据边界为基准，不把旧文档已提出的整合原则当作新增能力。

本次团队运行最长 86400 秒，不限任务轮数，不设单 worker 一小时超时；默认每个 worker 仅继承整次运行剩余时间。周期检查不是执行超时，也不能按固定任务数或普通失败次数结束研究。达到总预算或人类停止后，先收集真实终态并保存已有综合结果，再做不启动 worker 的最终判断。模型调用不能保证在预算时刻立即返回；实际超时与未确认终态须如实报告。

当前团队运行及槽位状态单独保存为机械现场，输入输出和通知继续使用调用档案；不引入预制任务图、语义事件账本、自动重放或分布式调度。崩溃后不得无条件重启可能仍在运行的旧执行；应先核实现场。原有七个控制材料保留，团队状态不得被单 worker 入口误用为当前可执行任务。

本次 worldBox 测试经用户纠正，采用先独立重新研究、后开放旧报告比较的两阶段安排。独立阶段使用不含旧研究和旧 Git 对象的新项目目录、控制状态与模型会话，仅读取原始项目要求；不能把旧整合设计、宿主基线摘要或旧失败清单注入新任务。worker 的隔离包装不挂载旧工作区，公开网络仍用于领域研究，但不得在线获取本项目旧报告；这是文件可见性隔离与网络行为约束，不是对公开互联网内容的封闭盲测。比较前一次保存独立原稿，比较阶段新增分析，不事后改写原稿并冒充独立发现。

首版的核心不是自动跑更多轮，而是让每一轮都能回答：

```text
项目现在真实处于什么状态？
为什么还没有达到人类意图？
最近工作实际改变了什么？
当前最值得推进的完整责任是什么？
现在应该实现、调查、做判别实验、询问人类，还是停止？
```

## 1. 系统边界

### 1.1 人类

人类负责：

- 项目长期目的；
- 关键使用方式和可观察成功结果；
- 产品、安全、许可和外部承诺；
- 事实无法裁决的价值取舍；
- 明确改变或撤回既有方向。

人类不负责持续规划每个局部任务，也不需要阅读 worker 的完整执行过程。

### 1.2 orchestra

orchestra 负责任务之间及周期观察时的项目级判断：

- 重新读取当前人类意图；
- 从事实中恢复项目当前局面；
- 识别承重假设和主要收敛缺口；
- 判断当前路线是否仍值得继续；
- 选择一个完整、连贯、可验证的当前任务；
- 决定继续旧 worker 会话还是开始新会话；
- 在需要产品或价值选择时询问人类；
- 删除过时判断并重写当前项目状态。

orchestra 不负责：

- 当前任务的详细实现；
- 普通错误修复；
- 文件级任务拆分；
- worker 内部子代理管理；
- 持续跟踪每条命令或每次测试；
- 为项目建立完整路线图或预先任务图。

### 1.3 worker

worker 负责当前明确任务的完整局部闭环：

- 调查；
- 形成局部方案；
- 使用内部子代理；
- 实现、测试和修复；
- 返回可复核结果和会影响项目方向的新事实。

worker 的详细设计见 [`worker-design.md`](worker-design.md)。

### 1.4 外层程序

外层程序只承担机械责任：

- 创建全新的 orchestra 会话；
- 组装当前上下文；
- 启动或恢复 worker；
- 保存控制材料；
- 记录 Git、进程、结果和错误等机械事实；
- 允许人类显式开始、取消或停止；
- 在明确的项目决策边界再次启动 orchestra。

外层程序不根据关键词决定项目方向，不自动拆任务，也不建立语义状态机替代 orchestra。

## 2. 控制材料及其所有权

首版使用七个简单文件：

```text
intent.md
state.md
task.md
result.md
decision.txt
worker-thread.txt
last-orchestra-output.md
```

这些文件不是数据库表，也不是版本化协议。每个文件只承担一个清楚职责。

### 2.1 `intent.md`：人类当前意图

`intent.md` 是人类意图唯一来源，只由人类创建和修改。它保存当前仍有效的：

- 长期目标；
- 主要使用方式；
- 可观察成功结果；
- 硬边界和非目标；
- 已确定的产品选择；
- 仍需保留的资源或风险约束。

`intent.md` 应描述**当前有效意图**，不应长期积累为按日期追加的纠正历史。人类改变方向时，原则上整体整理旧内容：

- 删除已经被取代的要求；
- 把仍有效的修正合并进当前表述；
- 不要求下一轮 orchestra 阅读完整的人类对话历史；
- 需要追溯时使用 Git，而不是把历史过程全部保留在运行上下文中。

orchestra 和 worker 无权修改该文件，也不得在其他控制文件中生成替代的人类意图。

### 2.2 `state.md`：orchestra 当前项目判断

`state.md` 保存新的 orchestra 为下一次决策保留的**当前工作集**。它不是历史档案，而是此刻最有助于选择下一步的项目级认识。

它可以包含：

- 已确认的项目事实；
- 当前推断；
- 承重假设和失效条件；
- 主要收敛缺口；
- 已停止且容易重复的路线；
- 仍有效的能力概况：用户已经可以做什么、接口可接收范围与实际验证覆盖分别是什么；能力只有被新事实改变时才更新，不因当前转向别的主题而消失；
- 简短、可修订的当前方向及任务优先理由，与能力概况分开表达，不保存完整路线图或旧推理过程；
- 待人类决定的问题。

研究认识只保留会影响下一决定的条件、未知与证据位置；完整候选比较、实验日志和历史理由留在项目产物及调用档案。这些是语义类别，不是固定字段。首版不对章节、顺序和格式做程序校验。

`state.md` 每轮整体重写，并遵守：

- 不复制 `intent.md`；
- 不追加完整运行日志；
- 不保存旧推理链；
- 不把 worker 自述直接写成事实；
- 删除已经失效或不再影响方向的判断；
- 不为了“以后可能有用”保留所有旧细节；
- 不做版本、迁移、兼容、合并和自动修复；
- 保持人类能在数分钟内读懂当前项目局面。

这里不设置机械字数上限。判断标准是：新 orchestra 能否快速恢复正确项目局面，而不是状态是否足够详尽。

### 2.3 `task.md`：当前 worker 责任

`task.md` 是 orchestra 当前下发给 worker 的完整推进说明。它描述一个完整责任，不是路线图、任务队列或文件清单。

它只保留当前任务。新任务整体覆盖旧任务；需要追溯时使用 Git 和 worker 会话。

### 2.4 `result.md`：最近一次 worker 结果

`result.md` 只保存最近一次 worker 的精简结果。它是待核实线索，不是项目事实源。

详细实现、测试、调查和数据应留在目标仓库中。`result.md` 只需要让新的 orchestra 了解：

```text
完成了什么
最关键验证是什么
还有什么未闭合
哪些事实可能改变项目方向
相关产物在哪里
```

### 2.5 机械文件

`decision.txt` 只保存当前机械动作；`worker-thread.txt` 只保存当前任务对应的 worker 会话标识；`last-orchestra-output.md` 只用于调试和查看原始输出，不默认进入下一轮上下文。

## 3. 项目状态中的事实、推断和假设

### 3.1 已确认事实

只有会影响项目方向的事实才进入 `state.md`，例如：

- 当前真正可运行的端到端能力；
- 已验证的用户行为；
- 已确认的真实失败；
- 已形成的外部接口、数据或许可边界；
- 某项产物是否已经集成；
- 某个承重实验的结果。

承重事实应尽量指向代码版本、测试、运行结果、报告或人类决定。普通代码细节可以从仓库恢复，不重复抄写。

事实也可能随代码变化而过期。若某个判断依赖旧提交中的行为，新的 orchestra 应在需要时重新核实，而不是因为它曾经写进 `state.md` 就永久视为真理。

### 3.2 当前推断

推断是 orchestra 对事实的解释，例如“当前主要瓶颈可能是数据身份，而不是读取性能”。推断可以指导下一步，但不能与事实混写。

推断应在新证据出现后允许直接改写或删除，不需要保留所有历史版本。

### 3.3 承重假设

只有一旦错误会改变当前路线、使较大工作失效或改变正确性标准的假设才进入长期状态。

每个承重假设至少应能回答：

```text
当前假设是什么？
依据是什么？
什么结果会证明它失效？
```

不要求数值置信度。数值容易制造伪精确，而首版没有可靠的消费方式。区分“已确认事实、当前假设、未确认问题”已经足够。

### 3.4 收敛缺口

收敛缺口是 orchestra 当前对“项目为什么还没有成立”的解释，不是初始目标的机械拆分，也不是代码待办清单。

好的收敛缺口能够解释：

- 项目缺少哪种真实能力或证据；
- 为什么该缺口阻碍整体目标；
- 哪类项目变化可以显著减少它。

收敛缺口可以被新证据重写、合并或删除。完成一项任务不必对应关闭一个固定条款。

### 3.5 已停止路线

只记录成本较高、未来容易重复、且已有明确反证的路线。记录应简短：

```text
原路线
依赖的假设
反证
当前结论
```

某实现失败、工具暂不可用、证据不足、本轮未选和路线受到反证是不同结论，不能统一写成永久淘汰。保留的重要失败应说明适用范围，以及什么新条件或证据值得重新考虑。普通失败尝试、一次错误实现和已解决的调试问题不进入长期状态。

## 4. 每次决策轮的上下文

### 4.1 稳定前缀

稳定前缀包括：

- orchestra 的职责；
- 一对一边界；
- 不接管 worker 实现；
- 不继承旧推理叙事；
- 输出形式；
- 不把机械事实当成项目优先级；
- 不把“最简单”误当成“已经确认正确”。

稳定前缀可以由模型服务复用缓存。全新决策轮不等于每次请求所有内容都不同。

### 4.2 动态上下文

每轮重新读取：

```text
intent.md
state.md
task.md
result.md
decision.txt
Git 分支、提交、状态和差异等机械事实
```

这些材料说明当前人类意图、上一轮项目判断、最近任务与结果以及工作区现实。请求将原任务与 worker 完成说明放在同一相邻段落；任务和结果正文引用与本任务有关的原义、已知限制短摘及原文位置，使承重证据与完成声明直接同呈。旧任务仅有路径时，按需读取相应片段，不自动抽取、截断或拼接全部历史。这只改善证据呈现，不证明模型能正确判断完成或产品授权。

### 4.3 按需证据

orchestra 通过只读工具读取与本轮战略判断直接相关的仓库内容。它不应每轮全量理解整个代码库，也不应只相信摘要。

应优先核实：

- 会改变项目路线的事实；
- worker 自述中的承重结论；
- 当前用户流程是否真实存在；
- 项目是否只在工作目录偶然可运行；
- 新结果是否依赖未经说明的产品语义；
- 当前任务是否只是继续完善既有机制。

普通文件布局、实现细节和局部测试失败由 worker 处理，除非它们已经影响项目级判断。

### 4.4 默认不进入上下文的内容

- 上一轮 orchestra 对话；
- 完整工具流水；
- chain of thought；
- worker 完整会话；
- worker 内部子代理对话；
- 所有历史任务与结果；
- 已经被取代的人类纠正过程；
- 普通失败尝试；
- 仅用于调试的原始输出。

详细历史继续存在于 Git、仓库产物和模型会话存储中，需要时按需读取，而不是默认注入。

## 5. 单次 orchestra 决策方法

单次决策轮可以使用多轮只读工具，但最终只产生一个当前决定和一个当前任务。

### 第一步：独立恢复项目局面

先回答：

```text
人类当前真正要什么？
项目现在实际能做什么？
最近一次工作实际改变了什么？
哪些内容只是 worker 或旧 orchestra 的说法？
项目为什么仍未达到当前意图？
```

不要从“上一轮已经选择了什么”开始推理。旧决定只是待检查的当前路线，不是默认正确答案。

### 第二步：核实承重事实

只检查能够改变当前用途判断的少量事实。下发资格条件前，说明它保护哪项当前行为、来自人类约束还是已确认失败；模型自己提出的条件仍是可修订判断。长期完整覆盖不自动成为局部使用的前置条件，例如固定本地输入可复现与在线来源永久不回改不是同一要求。证据缺失只限制可声称范围，已有反证才支持否定相应假设；许可、身份和字段语义等真实使用条件不能因此略过。证据不足时，不要用更长的推理替代事实：

- 可以通过领域资料回答的，生成有边界的调查任务；
- 可以通过小型实现回答的，生成可丢弃的判别实验；
- 属于人类用途和价值选择的，询问人类；
- 不影响当前方向的细节，留给 worker。

### 第三步：重新表述当前主要缺口

必须用项目和用户行为描述缺口，而不是直接用内部构件命名。

例如：

```text
较好：用户还不能让一个交易规则基于当时可见行情产生订单。
较差：缺少 StrategyEngine 和 RuleRegistry。
```

内部构件可以是实现手段，但不能在没有证据时替代项目缺口。

### 第四步：延续或调整中程方向

证据充分支持当前方向时直接延续。阶段目标、路线和验证方法是 orchestra 可修订的判断，不因曾下发为任务就成为人类硬约束；人类要求的正确性原义则不能以术语重定义、免责声明或缩小宣传口径替换。新事实使原方法不值得继续时，可以重选阶段目标或必要的推进方式。若要推翻已有事实判断，应指出新证据或原推导的具体错误，而非以新任务授权自身。worker 结论保留用途与成立条件，完成声明仍对照原义，不能采用其事后降低的标准。无需每轮列方案，也不把所有可能工作变成待办。

阶段用期望取得的项目能力或关键认识定义，不用任务名称或内部构件定义。在当前状态中简述阶段为何服务主要缺口、开始时的关键局面、何种变化足以转入下一阶段，以及什么发现应使本阶段提前重选；不增加固定字段或完整路线图。依据现有状态和按需历史比较实际变化与投入，不臆造缺失的起点或累计预算。

任务完成不自动表示阶段完成；失败实验如果排除了关键解释，也可能推动阶段。多轮产物增加而主要缺口未缩小时，重新判断当前研究问题本身是否值得优先回答，不能只将上一结果的局限变成下一任务。必要时比较继续本线与一种能改变证据来源、问题尺度或验证方式的替代推进方式，不要求每轮列举全部候选。

区分三种选择：保留阶段与方法，交给 worker 继续完成完整责任；保留阶段目标，改变调查、实验、实现或整体验证方式；当前阶段已达到转段条件或已失去价值，重选下一阶段。选择以项目价值、关键假设和实际投入为依据，不按固定任务轮数强制换线，也不因暂时没有正面结果叫停有判别价值的研究。

### 第五步：简述为什么优先做当前任务

用整体目标、主要缺口和承重事实说明当前完整任务为何值得优先推进，而不是仅从最近产物寻找相邻待办。测试通过或代码增加只能支持能力判断，不能单独证明方向选择正确。

理由足以支持决定即可；不要求每轮反驳自己或生成额外评审文档。未经确认的产品用途和价值选择不能隐藏在实现中。

### 第六步：选择一个完整责任

首版每轮只选择一个当前任务。任务应足够大，使成熟 worker 能够在连续上下文内完整负责；也应足够聚焦，使完成后能判断项目现实发生了什么变化。

不要把一项完整任务拆成：

```text
先写设计
再写代码
再写测试
再评审
```

这些通常属于 worker 内部循环。

### 第七步：重写当前状态

决策完成后整体重写 `state.md`：

- 先按新事实更新仍有效的能力概况，分别说明接口范围、已验证覆盖及限制；
- 再更新当前方向、任务理由和调查条件，不把上一任务的三选一标签或门槛直接升级为项目事实；
- 删除被推翻或已无关内容，修正承重假设；
- 重写主要收敛缺口；
- 保留当前决定、理由边界和失效条件；
- 保留真正待人类决定的问题。

不追加一条新的历史记录，不保留完整候选比较。

### 第八步：生成推进说明并结束

生成新的 `task.md`，输出机械决定，然后结束当前 orchestra 会话。后续实现由 worker 负责。

## 6. 当前决定的类型

首版外层只有五种机械动作，但 orchestra 的语义判断可以落在以下方向。

### 6.1 继续当前任务

同一个可观察结果尚未完成，主要假设和自主范围未改变，恢复原 worker 会话。

### 6.2 开始新任务

当前任务已经完成或被重新定义，需要产生不同的项目变化，启动新的 worker 会话。

新任务可以是调查、判别实验、实施、集成或真实失败修复，不只等于写产品代码。

### 6.3 询问人类

当事实无法决定产品用途、风险容忍、许可接受、外部承诺或价值取舍时，提出少量清楚问题。

不要把普通实现选择交给人类，也不要用大量背景和十几个选项转移判断责任。

### 6.4 等待

本次运行预算用尽，或当前推进存在真实外部依赖时，可以等待。说明等待限制的是本次执行、所选路线，还是确实需要外部条件的项目行为；恢复条件只对应该范围。预算结束本身不要求补充数据或人类产品选择才能重新判断，候选未满足某用途也不自动证明全项目受阻。不要求排除所有可能路线，亦不为避免等待制造任务。

### 6.5 停止

当前人类意图已经满足，或现有事实表明继续投入没有合理项目价值。停止不要求所有内部待办归零。

## 7. worker 推进说明

推进说明应包含足以让 worker 完整负责当前任务的信息：

```markdown
## 期望项目变化
任务完成后，项目现实中应出现什么新能力、证据或被消除的不确定性。

## 为什么现在做
它为什么比其他候选更能减少当前收敛缺口。

## 相关事实
当前已确认且与任务直接相关的事实；涉及承重语义时，在相关行为旁引用须保持的人类原义和已知限制的必要短摘，标明原文位置，而非仅链接整份报告或给出待实现的新定义。

## 当前工作假设
任务允许依赖的承重假设，以及什么结果表示假设失效。

## 自主决策范围
worker 可以自行决定的局部实现、调查和测试范围。

## 必须保留
已有能力、产品边界和外部承诺。

## 所需证据
完成后足以支持项目判断的可观察结果。

## 何时提前返回
承重假设失效、出现未授权产品选择或任务需要实质重定义时。
```

这只是推荐的信息形状，不是程序校验的固定 schema。实际 `task.md` 可以使用自然语言。

知识交接必须进入完整任务，不能止于写入 `state.md`。worker 不自动接收整个项目状态或 Orchestra 专用的控制历史查询工具；团队 worker 实际接收的是自己那项完整分配。Orchestra 应带入相关事实、成立条件、未知、失败范围和目标项目内可读的产物位置，明确哪些前驱结果可以直接使用、哪些承重主张需要独立复验，避免重复全部研究。交接摘要仍可被可核实事实推翻。

推进说明不应：

- 预先写出完整文件和类设计；
- 指挥 worker 每一步操作；
- 重复 AGENTS.md 中所有长期规则；
- 要求不相关的全面测试和审计；
- 让 worker 在完成后自行选择下一阶段；
- 为一个可能被推翻的方向提前建设通用框架。

## 8. worker 会话边界

### 8.1 继续原会话

当新的推进说明仍要求完成同一个可观察结果，主要承重假设和自主范围未改变时，恢复原 worker 会话。

### 8.2 启动新会话

当目标、产品语义、完成标准或承重假设实质改变时，启动新会话。新的任务不应因为代码仍在同一个仓库就继承旧任务的全部局部叙事。

### 8.3 恢复后重新锚定

恢复 worker 时重新发送当前完整任务和精简固定约束；恢复或压缩后，worker 按需确认当前项目规则、工作区变化和验证结果，不重复注入全部文档或历史。人类约束不被模型任务覆盖，当前可核实事实可以推翻任务和旧会话的假设。

具体规则见 [`worker-design.md`](worker-design.md)。

## 9. 项目决策边界与运行粒度

### 自动运行

`run` 是人类显式启动的前台循环，默认最多 10 个 worker turn、3600 秒，项目检查间隔 300 秒（0 表示关闭周期检查）。每次 worker 返回后，包括失败和超时，都重新调用 fresh Orchestra；达到运行上限时仍吸收最后结果，但不得再启动 worker。连续三次执行失败后结束本次运行，防止无进展重试。等待、询问人类、停止以及用户中断均结束循环。

周期观察不写回当前 state/task/decision；“继续当前任务”保持执行原样，其他决定请求中断并交回控制。收到真实终态后重新决策，观察建议不直接作为新任务。中断超时或失败时结束运行，不假定旧 worker 已停止。预算在轮间和执行通知轮询时检查；模型请求本身仍受模型客户端超时控制，不能承诺在预算时刻强杀模型请求。

观察必须判断当前任务继续占用资源是否仍服务阶段，而非仅判断 worker 是否活跃或报告是否规范。当前 result 可能属于上一任务，不能据此宣布活跃任务已经完成；通知尾部只是片段，判断停滞或关键假设失效前按需查阅原任务、运行通知和产物。继续时说明正在减少的关键不确定性及值得等待的结果；交回控制时说明足以改变项目判断的新事实、等待自然完成的代价和需要重审的层次。普通调试、正常的负结果与有信息增量的研究由 worker 自治；不能为展示监督效果强行打断。观察意见不会发送给活动 worker，因此依赖修改行为的建议不能一边选择继续、一边假定建议已被执行。

`history/` 每次调用保存输入控制材料、请求、输出、Git 事实及起止用时；worker 保存通知日志和结果。这是可删除的观察档案，不是驱动项目语义的账本或状态迁移。默认只注入有限的近期调用索引、当前运行用时及通知尾部，Orchestra 可通过专用只读入口分页查询当前项目历史，不能借此读取其他项目或任意外部目录。通知中能看到的子代理事件可以检查，但不声称已接通所有后代原始会话或完整用量。

同一项目的 `init --force`、`decide`、`run-worker`、`run` 共用跨进程锁。旧 worker 活跃时不能由另一个入口改写任务；异常退出释放锁，历史中的未完成记录可供排查，但不会自动重放未确认执行。

典型项目决策边界：

- 当前完整任务结束；
- worker 明确阻塞；
- 承重假设被证伪；
- 人类修改 `intent.md`；
- 关键外部事件或判别实验产生结果；
- 当前路线连续工作但没有减少项目缺口；
- 即将进入新的产品方向；
- 项目可能已经满足当前意图。

普通测试失败、局部重构、一次提交和子代理调用不是项目决策边界。

一条人类下发给实施者的运行指令可以包含多个机械循环：

```text
fresh orchestra
→ worker
→ fresh orchestra
→ 授权范围内由 orchestra 选择的下一项 worker 任务
```

项目决策边界不等于人类批准边界。授权范围内的新任务和产品能力由 orchestra 自主选择并继续，不能仅因进入新任务而询问人类。人类明确限定的本轮目标、预算、权限和停止条件始终有效。需要停止的情况是：

- 已达到人类规定的本轮完成边界；
- 存在无法由现有意图和事实裁决的产品取舍；
- 需要尚未授权的许可、发布、外部承诺或不可逆操作；
- 真实权限、资源或运行机制阻塞。

原定数据或技术路径失败时，由 fresh orchestra 判断授权内替代推进方式；不默认反复追加调查，也不伪造缺失事实。

实施者负责运行和机械交付，不替 orchestra 选择业务路线，也不把人类提出的股票子目标自动写入 `AGENTS.md` 作为每轮授权。长期目标与真实规则继续有效；当前中程方向由 orchestra 在 `state.md` 中维护。明确的人类操作权限和运行预算按原义执行，单个自行选择任务完成不自动终止项目推进。研发观察的任务数量上限仅属于该次调用，不写成长期产品规则。

worker 沙箱不能执行而宿主已获授权的机械操作，由宿主执行并返回实际结果；不要把环境分工误判为需要人类重新授权。真正越权或需要产品价值选择时仍应返回。

## 10. worker 结果如何进入下一轮

worker 最终回答首先是声明，不是事实。新的 orchestra 应按重要性处理：

```text
用户可观察结果和可重复运行
  优先级最高

聚焦的端到端、集成和业务不变量验证
  支持当前能力判断

代码、差异和提交
  说明实现存在，但不自动证明行为正确

worker 总结与建议
  作为线索，不自动成为项目事实
```

核实深度取决于不确定性是否会改变重要决定；已有直接产物和可靠验证足以支持当前用途时，可以有条件采纳，不全量重验普通已有事实。若承重行为无法由当前只读 orchestra 独立观察，不应假装已经确认。可以选择：

- 按结果中的路径读取已有测试和运行输出；保留可定位的关键结果，不仅引用无法从仓库读取的会话，也不为此建设证据系统；
- 让下一项 worker 做有边界的验证；
- 在确实需要时询问人类体验；
- 保留为未确认假设。

需要执行或独立验证时，给 worker 原始要求、待检验主张、实际产物与评价条件，不把旧结论或预期赢家写成待复述答案。fresh 会话本身不证明验证独立。首版不设置固定 auditor，也不要求每项任务后再启动独立 reviewer。

## 11. 防止项目状态腐烂

全新 orchestra 只能避免继承旧对话，不能自动保证 `intent.md` 和 `state.md` 健康。每轮需要主动维护：

### 11.1 人类意图保持当前化

人类应合并仍有效要求，删除被取代内容。不要把 `intent.md` 变成完整聊天记录。

### 11.2 项目状态保持当前化

orchestra 写回状态时应删除：

- 已被事实推翻的假设；
- 已完成且不再影响方向的任务细节；
- 已被新决定取代的旧路线；
- 可以从 Git 直接恢复的普通代码事实；
- 不再可能改变下一步的历史风险。

### 11.3 详细产物外置

长调查、实验统计、数据说明和实现细节放在目标仓库。`state.md` 只保存结论和引用，不复制全文。

### 11.4 不为状态维护建设状态系统

如果状态开始要求：

- 固定字段；
- 版本迁移；
- 自动合并；
- 缺失字段兼容；
- append-only 决策账本；
- 状态校验器；
- 第二个模型修复输出；

应先收缩内容，而不是建设配套运行时。

## 12. 两段式上下文揭示

两段式做法仍是后续候选，不是首版默认：

```text
第一段：只看当前人类意图、事实和原始证据，先形成独立判断
第二段：再看旧决定残留、停止路线和 worker 解释，进行校正
```

只有真实运行持续出现以下问题时才值得采用：

- 新 orchestra 明显被旧决定锚定；
- worker 自述反复压过原始证据；
- 当前状态中的路线说明使模型很难否定已有投入。

采用前应先确认问题来自上下文顺序，而不是状态本身错误或任务定义不清。

## 13. 首版明确不采用的设计

### 13.1 不使用预制 DAG

软件项目的真实依赖、承重边界和路线通常在执行后才显现。预先任务图会把猜测变成计划惯性。首版只保留一个当前任务。

### 13.2 不使用长期 orchestra 会话

长期会话会积累自身决定、辩护和沉没成本。长期存在的是项目责任与当前状态，不是模型对话。

### 13.3 不使用 append-only 事件账本

Git、仓库产物和 worker 会话已经保留详细历史。首版没有多 worker 并发写入的事实需求；再建事件账本会产生压缩、索引、一致性和迁移责任。

### 13.4 不使用数值置信度

首版只区分事实、推断、假设和未确认问题。没有可靠依据的数值不会提高决策质量。

### 13.5 不让 worker 决定是否唤醒 orchestra

首版一个完整 worker 任务结束后自然形成项目决策边界，不需要 `requires_direction`、影响等级或完成类型字段。worker 可以在结果中说明项目影响，但不能用自己的布尔判断跳过新的项目判断。

### 13.6 不设置固定评审流水线

必要的独立核验应作为具体任务出现，不把规划、编码、评审、测试固化为每轮默认角色。

## 14. 判断首版设计是否工作

良好趋势：

- 新 orchestra 能从当前材料恢复人类认可的项目局面；
- 状态保持短、当前、可修改；
- 任务粒度足以让成熟 worker 连续负责；
- worker 不在任务完成后继续选择项目方向；
- 调查、判别实验和产品实现能够被正确区分；
- 新证据能推翻旧假设和已有投入；
- orchestra 不只处理最显眼的 Git、测试和文档问题；
- 人类只在真实产品或价值边界介入。

失败趋势：

- `intent.md` 变成人类对话历史；
- `state.md` 变成累积日志或固定协议；
- orchestra 只是复述 worker；
- 每轮都选择容易闭合的机械收尾；
- 任务过细，重复 worker 内部规划；
- 任务过大，把远大目标重新交还一个 worker；
- 子代理和验证活动持续增加但项目结果不变；
- 为修复一次输出或恢复问题开始建设新运行时；
- 人类仍需在每个机械步骤提供下一条命令。

出现失败趋势时，优先修正当前状态、任务说明和上下文组装；只有稳定、重复的机械缺口才进入代码实现。
