# orchestra 首版详细设计

> 本文展开一对一 episodic orchestra 的运行细节。顶层定义和稳定边界见 [`../orchestra-design.md`](../orchestra-design.md)。

## 1. 运行方式

### 1.1 orchestra 跨决策轮不继承会话

每次项目决策边界到来时：

- 创建新的 orchestra 会话；
- 不恢复上一轮 orchestra 对话；
- 不携带旧助手消息、工具记录和推理链；
- 不把上一轮计划和辩护重新塞回请求；
- 从当前项目状态和本轮新增事实重新组装上下文。

长期存在的是项目状态和 orchestra 的责任，不是一条长期模型会话。

### 1.2 单次决策轮内允许完整代理循环

全新会话不等于单次分类调用。一个决策轮内，orchestra 可以：

- 阅读项目状态；
- 检查与当前判断相关的代码和差异；
- 运行产品、测试或关键实验；
- 查看最近 worker 产物；
- 比较少量候选方向；
- 形成下一项任务、继续判断或停止判断。

orchestra 默认只读取和检查项目，不修改业务代码。否则它会逐渐成为第二个 worker。它只修改项目状态材料和推进说明。

首版不要求 orchestra 调用额外子代理。先把单个战略代理的上下文和判断边界调通，避免引入新的混杂问题。

### 1.3 worker 会话绑定当前任务，而不是整个项目

worker 会话的连续性应服务于一个明确任务：

```text
同一任务仍在调查、实现、测试或修复
→ 恢复原 worker 会话

orchestra 只是补充证据、澄清边界或要求继续同一任务
→ 恢复原 worker 会话

orchestra 选择了目标、承重假设或完成标准实质不同的新任务
→ 默认启动新的 worker 会话
```

这不是需要首版通过对照实验决定的变量，而是角色边界本身：成熟 worker 负责把一个明确任务做完整，项目长期连续性不应继续寄生在 worker 会话中。

首版任何时刻仍然只有一个活动 worker。新的 worker 会话启动后，旧会话只作为可查询材料保留，不继续承担项目判断。

任务边界无法判断时，优先问：

```text
新的推进说明是否仍要求 worker 完成同一个可观察结果？
主要承重假设和自主决策范围是否仍然相同？
旧会话中的局部代码理解是否仍直接有用？
```

若答案大体为是，可以继续原会话；若项目方向已被重新解释，应开启新会话，避免旧目标继续污染执行。

### 1.4 全新 orchestra 不等于放弃前缀缓存

不能复用的是旧模型生成的对话和策略叙事，不是所有稳定输入。

稳定的职责说明、人类长期意图和硬边界仍可作为固定请求前缀。每轮变化的项目事实、任务结果和证据放在动态部分。

## 2. 持久项目状态

持久项目状态只服务于下一次 orchestra 判断。它不是完整历史，不是冻结合同，也不是新的运行时数据库。

本节列出的是 orchestra 需要考虑的信息类别，不是首版固定字段、固定章节或可校验结构。

首版最多使用一份可整体重写的自由格式 Markdown 文档，并遵守：

- 整体覆盖更新，不追加运行日志；
- 不做字段校验；
- 不做版本协议；
- 不做迁移；
- 不做新旧格式兼容；
- 不做自动合并或修复；
- 不要求 worker 读取或维护该文档；
- Git 只负责普通历史追溯；
- 任何内容都可以直接改写或删除。

如果这份状态材料开始产生自己的结构兼容、迁移、恢复或校验责任，应立即收缩，而不是继续建设配套机制。

### 2.1 人类意图

保留：

- 长期目的；
- 当前重大方向；
- 可观察成功结果；
- 真实约束；
- 已确认的非目标；
- 后续明确修改和撤回。

worker 或 orchestra 自己建立的机制不能反向扩张人类意图。

### 2.2 已确认的项目事实

只保留会影响项目方向的事实：

- 当前真正可运行的端到端能力；
- 已验证的用户流程；
- 当前真实失败和阻塞；
- 已形成的外部协议或数据承诺；
- 已集成结果与仍然孤立的产物；
- 对应的代码版本、测试、日志或运行结果引用。

代码和 Git 可直接恢复的普通细节不重复抄写。

### 2.3 承重假设

只保留一旦错误会改变后续路线的项目级假设：

```text
假设
当前依据
什么事实会证明它失效
```

承重假设不是事实，也不是上一轮推理历史。

### 2.4 当前收敛缺口

保留 orchestra 当前对“项目为什么还没有成立”的精简解释，例如：

- 核心能力尚未形成端到端闭环；
- 两个已有能力尚未集成；
- 关键协议语义仍不明确；
- 缺少判断真实失败所需的反馈；
- 当前路线局部持续成功，但没有减少项目级风险。

它不是代码待办列表，可以随新证据直接改写或删除。

### 2.5 精简结果和已停止路线

重要任务只保留：

- 原本想产生什么项目变化；
- 实际产生了什么可验证变化；
- 哪个承重假设成立、失败或仍未知；
- 当前路线应继续、调整还是停止。

只有成本较高且未来容易重复的失败路线，才保留原假设、反证和停止结论。普通局部失败不进入长期状态。

### 2.6 待人类决定事项

只保留真正属于产品方向、外部承诺、不可逆风险或价值取舍的问题。

### 2.7 当前决定残留

上一轮决定最多保留：

```text
当前方向
依赖的承重假设
预期信号
明确失效条件
尚未解决的风险
```

这不是决策账本，也不是要求下一轮继续维护旧路线的理由。

## 3. 事实、判断和决定必须分开

全新 orchestra 只有在输入没有把旧判断伪装成事实时才真正有意义。项目状态在语义上应区分：

```text
人类意图
已观察事实
当前推断
承重假设
当前决定
开放的不确定性
```

不要求首版建立对应字段，但组织材料时必须保留这些边界。

worker 的总结也不能直接变成项目事实。它只是线索；涉及项目方向的结论应由 orchestra 结合代码、测试、运行结果或人类输入核实。

## 4. 最小充分上下文

每次 orchestra 决策轮的输入由四部分组成：

```text
稳定前缀
  orchestra 职责、人类长期意图、硬边界、输出要求

当前项目状态
  已确认事实、承重假设、收敛缺口、当前决定残留

本轮变化
  最近任务结果、人类变化、外部变化

按需证据
  与本轮判断直接相关的代码、差异、测试、日志和运行结果
```

不直接拼接上一轮 orchestra 对话，也不全量复制 worker 对话。

首版需要重点调试的不是上下文越少越好，而是哪些内容对于项目级判断是必要的，哪些内容只会把 orchestra 拉回旧路线。

### 4.1 两段式揭示不是首版固定流程

候选做法是：

```text
第一段：先看当前事实和原始证据，不看旧策略与 worker 建议
第二段：再看精简决定残留、停止路线和 worker 解释，校正初步判断
```

它有合理动机，但先作为上下文设计的后续选项，不写成首版强制流程。只有实际运行表明它稳定减少锚定，才考虑采用。

## 5. 项目决策边界

orchestra 不常驻，也不检查每个 worker 动作。典型触发：

- 当前任务完成，并产生可能改变下一步的结果；
- worker 确认阻塞或承重假设失效；
- 人类发来重大方向变化；
- 关键实验或外部事件产生结果；
- 连续执行没有产生实质项目变化；
- worker 建议继续加固同一内部机制；
- 即将投入大规模或不可逆路线；
- 项目可能已经达到长期目标。

普通测试失败、局部实现选择、worker 内部子代理调度和普通提交不触发 orchestra。

首版不自动判断所有边界。先由人工主会话或简单脚本显式触发，观察哪些触发过早、哪些触发过晚，再决定是否需要自动化。

## 6. 单次 orchestra 决策轮

### 第一步：重新确认人类意图

回答：

- 人类最终需要什么项目结果？
- 当前重大方向和外部边界是什么？
- 哪些目标来自人类，哪些只是代理自建结构？

### 第二步：检查项目现实

独立检查：

- 当前真正能运行什么；
- 哪些端到端结果已经验证；
- 上一任务实际改变了什么；
- 当前主要收敛缺口是什么；
- 原路线依赖的承重假设是否仍成立。

### 第三步：生成少量候选动作

候选可以是：

- 继续当前任务；
- 调整当前任务边界；
- 结束当前路线并选择新任务；
- 做一个有限判别实验；
- 建立当前确实缺失的反馈能力；
- 等待真实外部依赖；
- 请求人类；
- 停止项目。

不生成完整长期路线图。

### 第四步：只选择一个当前任务

首版始终只维护一个当前任务。即使发现多个可能方向，也只选择当前最值得推进的一项，或先做能够区分方向的有限实验。

如果决定继续同一任务，恢复原 worker 会话；如果选择实质不同的新任务，默认启动新的 worker 会话。

### 第五步：更新项目状态并下发任务

只写回：

- 新增或失效的关键事实；
- 新增、修正或失效的承重假设；
- 新增、关闭或重写的收敛缺口；
- 当前决定及其失效条件；
- 待人类决定事项；
- 下一次 orchestra 唤醒条件。

然后生成 worker 推进说明并结束本次 orchestra 会话。

## 7. worker 推进说明

推进说明应短而完整：

```markdown
## 期望项目变化
本任务希望让项目现实发生什么变化

## 为什么现在做
为什么这是当前最有价值的一步

## 相关事实
与本任务相关的已确认事实和证据引用

## 当前工作假设
允许 worker 使用的承重假设及其失效信号

## 自主决策范围
worker 可以自主决定的实现范围

## 必须保留
已有能力和真实约束

## 所需证据
完成后需要返回的可复核结果

## 何时提前上报
哪些项目级变化需要在任务完成前通知 orchestra
```

不规定文件、类、实现步骤、子代理数量、测试写法或局部评审流程。

首版需要重点观察推进说明的粒度：过细会重复 worker 的规划能力，过粗则无法把项目级判断落实成可执行任务。

## 8. 什么算有效项目变化

下一项任务必须有项目级因果依据，但不要求每一轮都立刻产生用户可见界面或功能。

合法变化包括：

- 新增用户可观察能力；
- 修复真实端到端失败；
- 集成已经孤立存在的能力；
- 消除一个承重不确定性；
- 建立后续判断必需且当前确实缺失的反馈能力；
- 降低已确认的不可逆风险；
- 删除或停止已经被事实证明无价值的路线。

不能单独成为新任务理由：

- 代码已经存在这个结构；
- 已有测试覆盖它；
- 上一轮留下待办；
- 继续完善会更严谨；
- 已投入很多时间或计算量；
- 新机制自身又产生迁移、兼容、恢复或审计责任。

反事实检查：

> **即使不考虑这个机制已经存在，它是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不把继续完善该机制自动升级为项目目标。
