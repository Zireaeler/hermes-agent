# orchestra 首版目标：股票模拟系统

> 本文定义首版使用的真实长期目标。目标不是构造一个覆盖全部 orchestra 设计点的演示，而是提供一个足够宏大、可以串行推进、会自然暴露路线选择与注意力涣散问题的独立业务项目。

## 0. 选择结论

首版使用一个历史行情驱动的股票模拟交易系统作为主要目标。

建议的人类意图是：

> **做一个本地可运行、结果可复现的股票模拟交易系统。用户提供历史行情、初始资金和交易规则，系统按时间推进，接受买卖指令，模拟成交，维护现金、持仓、成本和账户净值，并能查看和解释完整过程。重点是让交易流程和账户结果可信、透明、可反复验证，不是接入真实券商，不是提供投资建议，也不是提前建设一个通用量化平台。**

首版只运行这一个宏大目标。不会同时维护第二、第三候选，也不会把多 worker 能力混进来。

该项目应放在独立业务仓库中，不在 `hermes-agent` 内直接实现。这样可以避免 orchestra 再次围绕自身状态、提示词、恢复和兼容问题形成自指增长。

## 1. 为什么这个目标适合首版

### 1.1 长期方向稳定，具体路线未定

长期方向容易理解：用户应能用历史行情完成一次可信的模拟交易过程，并理解资金和持仓为什么发生变化。

但实现路线并不天然确定：

- 行情时间怎样推进；
- 下单时可以看到哪些信息；
- 订单在何时、以什么价格成交；
- 多只股票的时间轴怎样对齐；
- 费用、滑点和未成交怎样处理；
- 持仓成本和已实现收益怎样计算；
- 用户通过什么方式表达交易规则；
- 什么结果足以说明模拟可信；
- 哪些真实市场细节应当进入首版，哪些应明确排除。

这些问题需要随着端到端结果逐步暴露，不适合在开始时冻结成完整架构和路线图。

### 1.2 会自然跨越多个完整 worker 任务

该目标通常不会由一个普通编码任务结束。它会自然经历：

- 建立最小可运行交易过程；
- 验证行情时间与信息边界；
- 建立订单、成交和账户变化之间的一致关系；
- 暴露并修正持仓、费用或未成交语义；
- 让用户能够定义和运行不同交易规则；
- 提供可解释、可复现的结果；
- 用更真实的数据和场景检验原假设；
- 删除或停止不再服务真实用户流程的内部机制。

这些不是预先固定阶段。orchestra 应在每个真实结果之后重新判断下一项任务。

### 1.3 存在真实的注意力陷阱

股票模拟系统非常容易从用户流程滑向内部平台建设：

- 在一次交易尚未完整跑通前建设通用事件总线；
- 在一个简单规则尚未验证前设计策略插件系统；
- 在日线回放尚不可信前实现逐笔撮合和订单簿；
- 在结果尚不可解释前增加大量指标和图表；
- 提前建设交易所、券商、数据源和账户的多层抽象；
- 为未来实盘接入增加权限、审计、恢复和兼容机制；
- 把数据库迁移、任务队列和分布式运行变成新的项目中心；
- 因已经写了大量测试和抽象而继续维护错误路线。

这些局部工作都可能合理，却可能让原始目标退出注意力中心，适合校准 orchestra 的项目级判断。

### 1.4 有清楚的外部结果

项目是否在成形，可以从真实用户流程观察，而不是靠代码行数、测试数量或内部架构判断：

```text
准备一份历史行情
→ 设置初始资金和交易规则
→ 启动模拟
→ 时间按明确规则推进
→ 产生下单、成交或未成交
→ 现金、持仓和账户净值一致变化
→ 用户能查看每笔变化及其依据
→ 使用相同输入可以复现相同结果
```

这使 orchestra 能不断回到产品现实，而不是只维护内部结构。

### 1.5 可以由一个 worker 串行推进

该目标足够大，但不依赖多个外层 worker 同时工作。每一轮 orchestra 只选择一个当前任务，由一个完整 worker 自行规划、使用内部子代理、实现、测试和修复。

因此它不会把多 worker 的并行、工作区、消息和集成问题混入首版。

## 2. 首版固定边界

这些边界来自人类意图，避免项目无限扩张。它们不是内部实现方案。

### 2.1 必须坚持

- 系统只进行模拟，不向真实券商提交订单；
- 不提供投资建议、收益承诺或自动选股结论；
- 首版以本地历史行情为主，不依赖付费服务才能运行；
- 相同输入、规则和配置应产生可复现结果；
- 模拟使用的价格、费用、滑点和成交假设必须可以被用户看到；
- 下单不能使用当时尚不可见的未来信息；
- 账户结果必须能够由交易、费用、现金和持仓变化解释；
- 项目首先服务单个用户完成完整模拟流程。

### 2.2 首版明确不做

- 真实资金和券商接入；
- 实时行情与持续在线运行；
- 高频交易、逐笔订单簿和完整交易所微观结构；
- 多用户系统、账户权限、订阅和收费；
- 通用策略市场、插件平台或工作流引擎；
- 覆盖所有市场、税务、分红、拆股和停牌规则；
- 机器学习预测平台；
- 为未来扩展提前建立复杂版本、迁移和兼容体系；
- 用大量指标、图表和报表代替交易过程正确性。

如果真实运行证明其中某项已经成为当前目标不可避免的阻塞，应由新的 orchestra 决策轮重新判断，而不是由 worker 自动扩大范围。

## 3. 项目开始前准备什么

### 3.1 一个独立仓库

可以是空仓库，也可以有极少量启动代码。不要先写完整架构、模块清单和任务列表。

仓库应允许 worker 本地运行测试和示例，不依赖难以获得的私有环境。

### 3.2 一份本地历史行情

建议准备一份可以直接提交到测试环境或以固定路径读取的数据：

- 包含多只股票；
- 覆盖足够长的连续交易时期；
- 至少包含日期、开盘、最高、最低、收盘和成交量；
- 数据来源、时区和是否复权应有简单说明；
- 首版运行不需要联网重新下载；
- 可以包含少量真实缺失或不同股票上市时间不一致的情况，但不要为了覆盖设计点人工制造大量特殊样本。

数据只是固定输入，不要求在首版先建设数据源平台。

### 3.3 初始人类材料

开始时只提供：

- 上述人类意图；
- 本地行情的位置与已知含义；
- 初始资金和基础市场范围；
- 首版固定边界与非目标；
- 当前仓库事实；
- 人类已经确认的少量外部成形迹象。

不要提供完整实现路线图，也不要预先规定必须先建设哪一层抽象。

## 4. 项目正在成形的外部迹象

以下内容用于判断项目是否更接近成立，不是一次性冻结的验收合同。

### 4.1 用户流程开始连贯

用户能够：

- 选择一段历史行情；
- 设置初始资金；
- 表达一个简单但真实的交易规则；
- 运行模拟；
- 查看订单、成交、现金、持仓和账户净值；
- 找到结果异常时对应的交易和市场依据。

### 4.2 模拟语义可以解释

至少能够说明：

- 当前时间点能看到什么信息；
- 订单在什么条件下成交或不成交；
- 使用了什么价格；
- 费用和滑点如何影响账户；
- 持仓和收益如何从历史交易得到；
- 为什么某次运行得出当前结果。

### 4.3 结果可以复现

相同数据、规则、初始资金和配置应产生相同交易序列与账户结果。若存在随机因素，应显式固定并记录。

### 4.4 新场景不要求重写整个流程

换一组股票、一个不同但同类的交易规则或一套费用参数时，用户仍使用同一条基本模拟流程，不需要重新修改核心业务代码。

这不意味着必须先建设通用插件框架。只有真实第二个场景出现后，才能判断哪些边界值得稳定下来。

### 4.5 核心账目保持一致

任何时点至少应满足可解释的一致关系：

```text
账户净值 = 现金 + 当前持仓市值
```

交易前后现金、持仓数量、持仓成本、费用和收益变化应能相互核对。具体成本算法可以选择，但必须明确且保持一致。

## 5. 初始承重不确定性

以下问题适合由 orchestra 持续关注，但不能在目标开始前直接写死答案。

### 5.1 时间与信息边界

- 模拟时间以日、分钟还是其他粒度推进；
- 交易规则在一个时间点可以读取哪些价格；
- 下单与成交之间是否跨时间点；
- 如何避免使用未来数据；
- 多只股票缺失行情时如何处理。

如果这些语义错误，后续所有收益结果都会失去意义。

### 5.2 订单与成交模型

- 首条可用路径需要什么订单能力；
- 市价、限价、部分成交和未成交应做到什么程度；
- 使用开盘、收盘或区间价格时如何说明假设；
- 滑点和费用是固定、比例还是其他形式；
- 订单何时失效。

首版只需要足以支持真实用户流程的最小模型，不追求完整交易所仿真。

### 5.3 账户与持仓语义

- 持仓成本如何计算；
- 已实现和未实现收益如何区分；
- 卖出超过持仓时怎样处理；
- 现金不足时是否拒绝订单；
- 费用在何时扣除；
- 多次买卖后怎样保证账目可核对。

### 5.4 用户怎样表达交易规则

可能是简单脚本、回调、配置或交互式操作。目标只要求用户能够表达和运行规则，不预先要求建设一种通用语言或插件体系。

### 5.5 结果怎样证明可信

- 只看最终收益是否足够；
- 是否需要完整交易记录；
- 哪些不变量必须自动检查；
- 什么场景可以暴露前视偏差；
- 什么结果应由独立计算核对；
- 如何让用户理解模拟假设的局限。

### 5.6 产品入口应做到什么程度

命令行、简单页面或可调用接口都可能成立。首版不以界面形态作为目标中心，先保证完整流程真实可用，再根据人类使用体验决定是否需要新的入口。

## 6. 第一轮 orchestra 应做什么

第一轮不应直接照本文生成完整路线图，也不应预先宣布要建立“行情层、撮合层、账户层、策略层和报表层”。

它应当：

1. 核实仓库与本地行情的真实状态；
2. 重新确认人类意图和首版边界；
3. 找出当前最承重且最缺证据的问题；
4. 选择一个能够产生端到端结果或判别性证据的明确任务；
5. 为 worker 保留完整实现自由；
6. 说明什么结果会改变下一轮项目判断。

在空仓库中，一个合理的首任务通常会倾向于建立最薄的纵向交易过程，而不是先建设横向平台。但具体任务仍应由第一轮 orchestra 根据数据和环境决定。

可能合理的任务形态包括：

- 用极小数据跑通一笔订单到账户结果的完整路径；
- 验证行情推进和下单信息边界，排除前视偏差；
- 建立能够核对现金、持仓和交易的最小账目模型；
- 先做一个有限实验，比较两种会影响全局的成交语义。

这些只是任务形态示例，不是固定首轮计划。

## 7. 自然项目决策边界

股票模拟系统中，以下变化适合重新启动全新的 orchestra：

- 当前明确任务完成，并产生新的端到端能力；
- 交易或账目结果暴露出承重语义错误；
- 数据现实推翻了时间轴、复权或缺失处理假设；
- 用户需要的第二个真实场景无法沿用当前流程；
- worker 建议继续建设通用框架，却尚无真实使用方；
- 当前任务开始无限扩大到实时、实盘或完整交易所模拟；
- 关键结果无法解释或无法复现；
- 人类改变了目标中的真实使用方式；
- 项目可能已经达到当前长期目的。

普通测试失败、局部类设计、一次重构和 worker 内部子代理调度不触发 orchestra。

## 8. 最容易出现的错误路线

### 8.1 把回测引擎当成最终产品

只实现一组内部计算接口，没有一条用户能够准备数据、运行交易并理解结果的完整路径。

### 8.2 把最终收益当成正确性

即使收益曲线看起来合理，也可能存在未来数据、重复成交、现金透支、费用遗漏或持仓错误。

### 8.3 过早追求市场真实性

在最小语义尚不稳定时实现逐笔撮合、订单簿、停牌、分红、拆股、税费和全部交易所规则。

### 8.4 过早建设扩展框架

提前抽象多个交易所、券商、行情源、策略插件和账户类型，却没有第二个真实场景证明边界。

### 8.5 把指标和界面当成推进

增加大量技术指标、图表、主题和报表，但无法解释基础订单、持仓和账户结果。

### 8.6 为模拟任务建设运行平台

引入数据库集群、分布式任务、队列、审计、恢复、迁移和复杂缓存，最终项目主要维护自己的基础设施。

### 8.7 因已有投入继续错误路线

已经写出的抽象、测试和文档不能单独成为继续维护的理由。仍需执行反事实检查：

> **即使当前结构尚不存在，它是否仍然由股票模拟的真实用户流程、已确认错误或承重不确定性直接要求？**

## 9. 人类在首版中的校准基准

首版调试时，人类不需要替 orchestra 规划全部任务，但应能够检查：

- orchestra 是否回到了完整模拟交易流程；
- 是否把内部框架误当成产品结果；
- 是否忽略时间与未来信息边界；
- 是否忽略现金、持仓和交易之间的一致性；
- 是否提出了过大或过小的 worker 任务；
- 是否在没有真实需要时扩大到实盘、实时和平台化；
- 是否出现事实无法裁决、确实需要人类选择的产品问题。

每次人类修正都应记录原因：缺少事实、错误推断、任务边界不合适、路线判断错误或真实价值选择。不要把人类修正直接堆回长期项目状态。

## 10. 首轮项目状态起点

正式运行前，可以用以下内容作为自由格式 `state.md` 的起点，但必须根据真实仓库和数据改写：

```markdown
# 人类意图
做一个本地可运行、结果可复现的股票模拟交易系统。用户可以用历史行情、初始资金和交易规则完成模拟，并理解订单、成交、现金、持仓和账户净值的变化。不是实盘系统，不提供投资建议，不提前建设通用量化平台。

# 已确认事实
- 目标仓库位置：待填写
- 当前代码状态：待核实
- 本地历史行情位置：待填写
- 数据包含的股票、时间范围、字段和复权方式：待核实
- 当前可以运行的用户流程：待核实

# 当前边界
- 不接真实券商和真实资金
- 不依赖付费实时行情
- 不做多用户平台
- 不做高频和完整订单簿模拟
- 不以指标、图表和测试数量代替交易过程可信性

# 承重不确定性
- 当前最小时间与成交语义尚未确认
- 账户和持仓应采用什么一致算法尚未确认
- 第一条端到端模拟路径尚未形成

# 当前收敛缺口
项目还没有一条用户能够准备数据、运行交易、查看并解释账户结果的完整流程。
```

这只是启动材料，不是固定模板。后续 orchestra 可以直接重写或删除任何部分。

## 11. 不选择其他股票项目表述的原因

### 11.1 不使用“实现一个回测引擎”

它过于内部化，worker 容易围绕接口、性能和指标建设，却不形成真实用户流程。

### 11.2 不使用“实现一个交易所撮合系统”

它把目标收窄到市场微观结构，主要难点变成高精度撮合，不再检验跨多个产品任务的长期方向。

### 11.3 不使用“实现一个实时模拟盘平台”

它过早引入实时数据、持续服务、用户账户、权限和外部可靠性，基础设施成本会压过 orchestra 的一对一战略问题。

### 11.4 不使用“建设通用量化研究平台”

它过于抽象，几乎任何数据、策略、指标、分布式运行和插件工作都能被解释成目标，反而无法判断是否收敛。

当前选择的“历史行情驱动的本地股票模拟交易系统”位于中间：足够宏大、路线未定、结果可观察，也可以由一个 worker 串行推进。

## 12. 何时考虑第二个宏大目标

只有股票模拟系统已经连续运行多个自然决策轮，并且一对一 orchestra 的上下文、任务边界和项目状态基本稳定后，才考虑另一个领域。

第二个目标届时根据真实需要重新挑选，不在当前文档预先维护候选清单。这样可以避免候选目标本身变成新的规划和文档维护责任。
