# orchestra 首版宏大目标选择

> 本文说明首版应选择什么样的真实长期目标，并给出第一批可直接使用的候选。目标不是构造一个覆盖所有设计点的演示，而是让 orchestra 在真实项目的自然决策边界中反复工作。

## 0. 当前结论

首版需要一个足够宏大的真实目标，但“宏大”不等于含糊，也不等于一次塞入几十项要求。

合适的目标应当同时具备：

```text
长期方向稳定
具体路线尚未确定
需要连续完成多个自然任务
执行过程中会暴露新的承重假设
存在局部合理但可能偏离整体的工作
最终结果可以从真实产品或系统行为观察
```

首版不要同时运行多个宏大目标。建议：

1. 先选一个主要真实目标，连续运行多个项目决策轮；
2. 用少量 Hermes 历史快照做提示词回归；
3. 一对一设计稳定后，再用第二个不同领域目标检查是否只是对首个项目过拟合；
4. 多 worker 与目标选择无关，仍然排除在首版之外。

## 1. 什么样的目标适合 orchestra

### 1.1 必须有真实外部结果

目标必须指向人类、用户或外部系统能观察到的变化，例如：

- 一条完整用户流程可用；
- 多个已有能力真正集成；
- 一个线上失败模式被消除；
- 一个外部协议可以可靠支持；
- 一个长期依赖的人工作业被系统替代；
- 一个原本只能局部运行的系统达到日常可用。

“重构架构”“完善运行时”“提高严谨性”“补齐所有测试”不能单独作为宏大目标。

### 1.2 路线不能已经被写成详细路线图

如果人类已经给出完整模块拆分、执行顺序和验收条目，worker 只需按计划实现，orchestra 的战略判断空间很小。

合适的目标只固定：

- 人类真正想得到什么；
- 当前已知现实；
- 不可破坏的外部边界；
- 可以观察的成形迹象；
- 明确不做什么。

具体先做哪一项、哪条路线值得继续，应留给后续决策轮根据新事实判断。

### 1.3 应自然跨越多个完整任务

一个普通问题单、局部缺陷、单次迁移或明确功能，不足以暴露长期视野问题。

合适目标通常会自然经历：

- 对现状的重新理解；
- 一个或多个有限实现；
- 真实运行或集成；
- 原假设被支持或推翻；
- 路线调整；
- 旧能力保留；
- 反馈能力补齐；
- 最终收敛或停止。

这些不是预先冻结的阶段，只是说明该目标不能在一个普通 worker 任务中自然结束。

### 1.4 必须存在真实的注意力陷阱

首版目标应当让普通长期 worker 容易被局部结构吸引，例如：

- 当前代码已有一套看似应该继续完善的抽象；
- 每次修改都会产生新的兼容、恢复和测试责任；
- 多个局部问题都合理，但只有少数真正推进外部结果；
- 承重假设只有在集成后才会暴露；
- 存在“继续加固现有机制”与“回到端到端目标”的冲突。

如果目标只是把已知列表逐项完成，就无法校准 orchestra 的项目级判断。

### 1.5 人类必须理解该领域

首版是工程调试。人类需要能够判断：

- orchestra 是否漏掉关键事实；
- 当前任务是否真的推进项目；
- 某个假设是否已被现实推翻；
- worker 是否扩大了无关范围；
- 哪些方向属于产品取舍。

因此不应为了“客观”随便挑选一个人类不熟悉的开源项目。

### 1.6 必须能以单 worker 串行推进

目标可以很大，但首版每个时刻只允许一个当前任务和一个活动 worker。

如果一个目标只有依赖多 worker 并发才有意义，或者其主要难点就是多人协调，就不适合作为首版目标。

### 1.7 不应首先选择 orchestra 自身

“实现完整 orchestra”不适合作为首个宏大目标。它会让 orchestra 自己产生的状态、提示词、恢复、日志和兼容问题再次成为下一轮最显眼的工作，重演旧运行时内核的自指增长。

首个目标应优先来自独立业务或产品系统。orchestra 代码只在真实运行暴露出直接缺口时修改。

## 2. 不适合的目标

首版排除：

- 单个 SWE-bench 或普通问题单；
- 玩具命令行工具；
- 预先列出全部模块与阶段的完整规格；
- 纯代码清理或纯重构；
- 只要求增加测试覆盖率；
- 只要求建设平台、框架、运行时或通用协议；
- 主要价值来自多 worker 并行的任务；
- 需要大量未知付费服务、私有凭证或不可控外部依赖的任务；
- 人类无法判断方向是否正确的陌生项目；
- 为了覆盖 orchestra 设计点而人工拼装的综合演示。

## 3. 宏大目标的输入形式

一个宏大目标开始时，只准备四类材料。

### 3.1 人类意图

用一到数段自然语言说明最终希望项目成为什么，不写内部架构方案。

### 3.2 当前已确认现实

只列当前确实存在的能力、已知失败、外部接口和真实约束。每项最好能指向代码、运行结果或人类确认。

### 3.3 不可破坏边界与非目标

例如：

- 已发布接口必须兼容；
- 不允许修改某类数据语义；
- 首轮不接入全部供应商；
- 不建设通用工作流平台；
- 不以测试数量代替产品结果。

### 3.4 项目正在成形的外部迹象

这些不是冻结验收合同，只用于判断路线是否更接近成立，例如：

- 一条真实端到端流程开始工作；
- 原有能力没有回归；
- 关键不确定性被现实证据消除；
- 新增一个同类对象不再要求改上层业务；
- 线上或测试环境中的真实失败减少。

## 4. 首选目标：多供应商视频任务能力

### 4.1 建议的人类意图

> **把现有视频任务能力演进为可持续扩展的多供应商服务。用户仍通过统一接口创建和查询任务，系统能在已配置渠道中选择和切换实际供应商，并保持任务身份、状态查询、失败处理和计量语义一致。后续接入新的供应商时，不应反复修改上层业务流程。**

这是当前最适合作为首版主要目标的候选。

### 4.2 为什么它足够宏大

它不是一个“增加 ecloud 适配器”的局部功能，而是同时包含多个会在执行中相互影响的项目问题：

- 现有渠道调度能否继续作为统一选择入口；
- 渠道选择与供应商实现应在哪里分离；
- 创建任务后如何记住真正执行的供应商；
- 后续查询、取消和轮询如何回到正确实现；
- 首个渠道失败后切换是否改变任务和计量语义；
- 不同供应商协议差异应由哪一层吸收；
- 现有 Volc 路径如何保持兼容；
- 什么反馈足以证明多供应商链路真的成立。

这些问题不能靠一开始写出完整架构图可靠解决，适合由 orchestra 在每个真实结果之后重新判断下一项任务。

### 4.3 当前可作为启动材料的事实

以下内容来自当前讨论，正式运行前需要在目标仓库中核实：

- 现有系统已经有 new-api 渠道表、用户渠道配置、权重排序和重试调度逻辑；
- 当前存在一条透传 Volc 标准参数的任务创建与查询路径；
- ecloud 有自己的协议，未来还可能接入其他自有协议供应商；
- 当前设想是先统一进入渠道筛选，再根据选中的渠道进入具体供应商实现；
- 当前最需要先确定整体结构，而不是一次完成所有供应商细节；
- 成熟 worker 已经能够在一个明确任务内自行调查、实现、测试和调用子代理。

这些是待核实的项目事实，不应直接扩展成冻结设计。

### 4.4 初始承重不确定性

第一轮 orchestra 可以重点检查，但不能预先把结论写死：

- 现有渠道调度语义是否真的适用于异步视频任务；
- “按渠道选择实现”是否足以表达后续任务归属；
- fallback 是否允许在创建任务失败后直接切换，而不会破坏计量与查询；
- 当前数据结构是否已经保存实际供应商归属；
- 现有上层接口是否能容纳各供应商的共同结果；
- 是否需要先建立一个最小假供应商或故障注入手段来获得证据。

### 4.5 项目正在成形的外部迹象

以下迹象可以帮助判断方向，但不要求一次任务全部满足：

- 现有 Volc 用户流程继续可用；
- 至少第二种供应商能通过同一外部入口完成真实或受控任务；
- 渠道失败切换后，任务查询仍能找到实际执行方；
- 失败和成功记录的计量口径没有重复或漂移；
- 调用方不需要知道内部供应商协议；
- 再增加一种受控供应商时，上层创建和查询流程不需要重新改写；
- 出现失败时，可以从现有日志或测试看出选择、切换和归属过程。

### 4.6 该目标最容易出现的视野陷阱

orchestra 需要特别警惕：

- 在第二个供应商尚未跑通前建设“通用供应商框架”；
- 为每种未来差异提前增加版本、能力声明和兼容层；
- 把任务状态、恢复、审计和账本扩展成新的工作流运行时；
- 因已有某个抽象就持续为其补测试和迁移；
- 把“所有供应商参数完全统一”当成前置条件；
- 在真实 fallback 尚未验证前设计复杂权重和恢复策略；
- 用大量模拟测试替代一条可观察的端到端链路；
- 因首个结构已经投入较多代码而拒绝回退。

### 4.7 首轮不要预选具体实现任务

目标启动时不要直接规定“先写某个接口”或“先建 provider 层”。

第一轮 orchestra 应读取真实仓库，确认当前创建、调度、查询和计量链路，再选择一个能够最大程度减少当前不确定性的明确任务。

合理输出可能是有限调查、最小纵向实现或故障实验，但必须由当前证据决定。

## 5. 第二候选：可信的请求计量与运营统计

### 5.1 建议的人类意图

> **让 MaaS 请求计量、日志和统计成为业务可以长期依赖的运营事实。在重试、状态更新、失败切换、缓存计量和多供应商条件下保持口径一致，支持近实时查询，并且业务使用方不需要理解底层日志去重细节。**

### 5.2 为什么适合后续迁移检查

这个目标同样会跨越多个自然任务：

- 明确什么记录代表一次真实请求；
- 处理重试和最终状态；
- 处理不同模型与供应商计量字段；
- 建立近实时统计；
- 验证失败、限流、缓存和状态更新的口径；
- 控制查询成本和刷新延迟；
- 让运营查询能够解释异常。

它容易让 worker 长期陷入物化视图、分区、刷新、性能分析和结构兼容，而忘记“统计是否真实可用”这一外部目的，因此适合作为第二领域检查。

### 5.3 可观察的成形迹象

- 同一请求在重试和状态更新后不会重复计量；
- 失败与限流记录遵守已确认的计量语义；
- 缓存相关字段在统计中保持一致；
- 业务查询能在可接受延迟内得到稳定结果；
- 原始日志变化后，统计结果仍能解释和追溯；
- 增加新的供应商字段时，不需要重写所有上层查询。

### 5.4 主要视野陷阱

- 把数据库结构本身当成产品；
- 无限增加物化视图和预聚合层；
- 为理论上的所有乱序和恢复情况提前建设协议；
- 以查询计划或行数优化代替口径正确；
- 因已有测试数据而维护不再需要的兼容路径。

## 6. 第三候选：Hermes 的 Windows 原生日常可用性

### 6.1 建议的人类意图

> **让 Hermes 在 Windows 原生环境中具备可日常使用的编码代理体验，不依赖 WSL。安装、终端和文件工具、会话恢复、后台进程、代理网络与常见故障处理应形成一条连贯可靠的用户流程。**

### 6.2 为什么适合作为不同领域目标

该目标有明确用户体验，但路线分散在多个平台边界：

- 安装与升级；
- PowerShell、CMD 和终端行为；
- 路径、编码和权限；
- 进程与后台任务；
- 图片、文件和会话；
- 网络代理；
- 崩溃诊断和恢复。

普通长期 worker 很容易逐个修兼容问题，却没有形成“可以日常使用”的完整流程。因此它能检查 orchestra 是否只对后端架构项目有效。

### 6.3 可观察的成形迹象

- 新机器可以按明确步骤安装并完成第一次编码任务；
- 常用终端、文件、图片和网络能力不需要 WSL；
- 中断后能够恢复当前任务；
- 后台任务和进程不会因 Windows 差异频繁失效；
- 常见故障有实际可执行的诊断路径；
- 用户不需要理解大量内部平台兼容机制。

### 6.4 主要视野陷阱

- 在首条用户流程跑通前设计完整跨平台抽象；
- 为所有 Windows 版本建立巨大兼容矩阵；
- 把测试环境、安装器或诊断框架自身变成长期目标；
- 为极少发生的边界不断增加防御逻辑；
- 每修一个工具就继续补一整套平台协议。

## 7. 不建议作为首个目标的候选

### 7.1 “实现完整 orchestra”

自指风险最高，会立即把状态、提示词、日志、恢复和调度问题变成项目目标。只允许根据真实业务运行暴露的问题逐步修改 orchestra。

### 7.2 “让 Hermes 无人值守完成任意长期项目”

范围同时包含 orchestra、worker、权限、恢复、消息、部署和多 worker，无法区分首版一对一设计的问题来源。

### 7.3 “重新实现旧运行时内核但更简单”

这会从旧结构出发，而不是从人类外部目标出发，最容易重复机制自我增长。

## 8. Hermes 历史材料如何使用

旧运行时内核不是首版宏大目标，而是上下文和提示词的回归材料。

建议从历史中挑选六到十个真实决策点，覆盖：

- 代理自建机制开始产生下一轮需求；
- 项目目标被运行时一致性问题替代；
- 局部阶段全部完成但没有新增端到端能力；
- 承重假设已失效却继续维护旧路线；
- 应停止投入但模型继续设计后续阶段；
- 独立评审或验证从一次手段升级成永久系统。

每个历史决策点只准备：

```text
当时的人类意图
当时可见的项目事实
最近一次实际结果
已知的外部约束
熟悉项目的人类认为必须注意的问题
明显不可接受的继续方向
```

不要给 orchestra 提供事后的完整正确路线，也不要把后来所有历史塞回上下文。

历史材料用于检查：

- 新提示词是否又建议继续旧机制；
- 删除某类项目状态后是否漏掉关键事实；
- worker 总结是否造成锚定；
- 两段式揭示是否有价值；
- orchestra 是否因全新会话随机反转。

它不用于证明 orchestra 在统计上优于 worker。

## 9. 目标选择检查表

正式启动前，人类只需回答：

```text
这个目标是否来自真实项目，而不是为了测试 orchestra？
最终结果是否能被用户或外部系统观察？
路线是否仍有真实不确定性？
它是否自然需要多个完整任务？
当前代码是否存在可能吸走注意力的局部结构？
人类是否足够熟悉该领域来纠偏？
是否可以始终由一个 worker 串行推进？
是否能在不建设多 worker 的情况下获得真实结果？
是否避免把 orchestra 自身作为主要产品？
是否有明确的外部边界和非目标？
```

大部分答案为“是”时才适合首版。

## 10. 推荐使用顺序

```text
历史快照
  只用于调试上下文和提示词

多供应商视频任务能力
  作为首个真实长期目标

可信请求计量与运营统计
  作为相邻业务领域的第二目标

Hermes Windows 原生日常可用性
  作为不同领域的迁移检查
```

不要并行运行这些目标。先让首个目标经历足够多的自然决策边界，确认一对一接口可以工作，再选择第二个目标检查设计是否过拟合。
