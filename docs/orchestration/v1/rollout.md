# orchestra 首版落地与调试

> 本文记录首版如何接入真实项目、逐轮调试和判断设计是否可用。运行机制见 [`design.md`](design.md)。

## 1. 首版是工程调试

首版不需要人为设计一个同时包含所有失败模式的项目演示，也不需要把“有 orchestra”和“无 orchestra”做成形式化胜负对照。

原因很直接：单 worker 长期自我维持远大目标会发生视野涣散，已经是本项目的出发事实。当前真正未知的是 orchestra 具体怎样工作才不会产生新的问题。

首版直接在真实项目的自然决策边界运行，每次只处理一个实际问题，并围绕以下内容反复调试：

### 1.1 上下文是否充分

- orchestra 能否从精简材料恢复当前项目局面？
- 哪些项目事实必须直接提供？
- 哪些内容只需要给出引用，按需读取？
- 是否必须保留承重假设和已停止路线？
- worker 总结会提供有效线索，还是造成新的锚定？

### 1.2 检查深度是否合适

- orchestra 只看项目状态是否会过度依赖摘要？
- 每轮全量阅读仓库是否会退化成第二个 worker？
- 哪些承重事实值得亲自运行或检查？
- 怎样限制一次决策轮的调查范围？

### 1.3 决策边界是否合适

- 每个任务结束都唤醒是否过于频繁？
- 等到多个任务后再唤醒是否已经太晚？
- 哪些 worker 信号真正代表项目级变化？
- 哪些只是任务内部噪声？

### 1.4 推进说明是否能有效纠偏

- worker 能否理解 orchestra 给出的项目级方向？
- 同一任务中的 worker 会话能否接受边界澄清？
- 新任务是否应该使用新 worker 会话？
- 推进说明是否过细、过粗或包含过多旧叙事？
- worker 返回的材料是否足以支持下一次全新判断？

### 1.5 项目状态是否能长期保持轻量

- 状态是否持续贴近真实项目？
- 是否开始堆积过时结论？
- 是否出现固定字段、兼容和迁移冲动？
- 全新的 orchestra 是否频繁重做已证伪路线？
- 不继承旧推理后，是否出现随机摇摆？

## 2. 首版落地方式

### 2.1 直接接入真实项目

首版不先构造专门 demo。选择一个正在真实推进、且人类已经理解其长期方向的项目，在自然决策边界运行 orchestra。

初期可以由人类保留最终决定权：

```text
真实任务产生结果
→ 全新的 orchestra 独立检查并给出下一项任务
→ 人类只检查是否遗漏关键事实或明显偏离方向
→ 接受、轻微修正或否决
→ worker 执行实际任务
```

这不是为了比较人类和 orchestra 谁得分更高，而是快速暴露：上下文缺了什么、orchestra 被什么误导、任务边界是否错误。

随着错误类型稳定减少，人类逐渐只在重大方向、不可逆风险和价值选择时介入。

### 2.2 历史快照只作为回归材料

Hermes 旧运行时内核中的典型失焦点可以保留为少量回归材料，例如：

- 应停止继续完善自建运行时机制；
- 当前路线已经远离原始产品目标；
- 某个承重假设已被现实推翻；
- 下一步应回到端到端能力，而不是补内部一致性。

这些快照用于在修改提示词或项目状态内容后检查是否重新出现旧错误，不用于证明 orchestra 必要，也不要求覆盖所有设计点。

### 2.3 每次只调整一个主要设计变量

一次调试中不要同时更换：

- orchestra 模型；
- worker 模型；
- 项目状态内容；
- 上下文揭示方式；
- 推进说明结构；
- 决策边界规则；
- worker 会话边界。

否则无法判断错误来自哪里。

### 2.4 调试记录与项目状态分开

项目状态只保存当前有效认识，应整体重写。

调试过程可以另行记录：

- orchestra 输入；
- orchestra 输出；
- 人类修正；
- worker 最终结果；
- 本轮暴露的错误类型；
- 模型成本和耗时。

这些记录只是研发材料，不进入下一次 orchestra 的默认上下文，也不升级成运行时事实源。

## 3. 首版最小实现

首版只需要：

```text
一份可整体重写的自由格式项目状态材料
一个启动全新 orchestra 的脚本或人工主会话
一个当前活动的 Codex 或 Claude Code worker
少量代码、测试、日志和任务结果引用
人工显式触发的项目决策边界
```

单次 orchestra 只做：

1. 检查必要事实；
2. 判断当前项目缺口和路线；
3. 选择继续同一任务或启动一个新任务；
4. 写一份短推进说明；
5. 整体更新项目状态材料；
6. 结束会话。

首版不需要：

- 状态数据库；
- 固定字段解析器；
- 决策结构定义；
- 状态校验器；
- 自动上下文组装器；
- 自动边界检测；
- 两段式提示词；
- 反证代理；
- 多 worker；
- 独立评审流水线；
- 正式对照基准。

## 4. 首版判断标准

首版不是通过一次最终演示判定成功或失败，而是看实际运行中是否逐渐出现以下结果：

- 全新的 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要把完整历史和完整 worker 对话重新塞入上下文；
- 能识别已失效假设和代理自建工作；
- 能提出粒度合适、具有项目意义的下一项任务；
- worker 能依据推进说明完成明确任务或改变旧方向；
- 新任务不再继承无关的旧 worker 叙事；
- 不因全新会话而频繁随机反转；
- 项目状态保持短、可改写、没有形成新协议；
- 人类在项目决策边界需要做的纠偏逐渐减少；
- 项目持续产生有效项目变化，而不是继续维护代理自建机制。

若持续出现以下情况，说明当前设计需要修正：

- 人类每轮仍需重新讲解整个项目；
- orchestra 只是复述 worker 的总结；
- 缺少完整历史就无法作出稳定判断；
- 为避免摇摆开始保存越来越多旧推理；
- 项目状态长成字段、校验、迁移和兼容系统；
- orchestra 过度阅读和修改代码，成为第二个 worker；
- 新任务仍被旧 worker 会话中的目标和结构绑架；
- 人类纠偏没有减少。

这些结果首先用于定位上下文、边界或接口问题，不急于推导 orchestra 整体无效。

## 5. 后续独立研究

以下问题不属于首版，只有一对一结构稳定后才单独研究。

### 5.1 两段式上下文

比较一次性输入与先看事实、后看精简历史，确认它是否稳定减少锚定，而不是只增加调用成本。

### 5.2 自动决策边界

研究如何从 worker 结果、外部事件和项目状态中自动判断何时唤醒 orchestra。

### 5.3 worker 会话策略细化

首版采用“同一任务继续，新任务默认新会话”的简单边界。后续可以研究哪些自然延续任务值得复用旧会话，以及何时应主动丢弃已经退化的会话。

### 5.4 多 worker

多 worker 至少包含：

- 如何判断两个任务是否适合并行；
- 如何管理独立工作区；
- 如何处理共享边界变化；
- 如何决定合并、暂停和取消；
- 谁承担最终集成责任；
- 并行收益是否大于协调成本。

多 worker 是独立且复杂的研究线，不能从一对一结构直接推导，也不能作为首版演示功能。

## 6. 首版明确非目标

首版不建设：

- 用对照实验再次证明单 worker 长期会漂移；
- 用一个综合项目演示证明完整体系优越；
- 多 worker 调度和管理；
- 外层任务并行；
- worker 登记系统；
- 多工作区合并机制；
- worker 间通信层；
- 固定角色团队；
- orchestra 长期子代理团队；
- 完整路线图冻结；
- 目标合同、进展账本和执行图；
- 图修订校验器；
- 检查点、快照和压缩系统；
- 复杂产物关系追踪；
- 自动负向评审或清理；
- 持久推理历史。

首版的任务只是把一对一 orchestra 的上下文、决策边界、worker 任务边界和推进说明调通。只有实际运行暴露出明确缺口时，才增加对应的最小能力。
