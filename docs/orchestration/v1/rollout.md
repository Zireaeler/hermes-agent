# orchestra 首版落地与调试

> 本文保留首版从“只有文档”进入“可运行闭环”，再进入股票模拟系统的落地顺序。行为边界见 [`design.md`](design.md)，实际代码与验收见 [`implementation.md`](implementation.md)，真实目标见 [`targets.md`](targets.md)。

## 0. 当前状态

Orchestra v1 已于 2026-09-01 完成前五个阶段：

```text
Codex worker 通信验证：完成
→ 控制材料与机械命令：完成
→ 全新 orchestra 决策轮：完成
→ 一对一闭环：完成
→ 极小仓库真实三轮机械验收：完成
→ 股票模拟系统真实运行：尚未开始
```

实际验收包括三个 fresh Orchestra session、真实 Codex thread 的新建与恢复、第三轮新 thread 边界以及无需人工复制材料的状态和结果传递。详细证据见 [`implementation.md`](implementation.md) 第 10 节。

以下各阶段仍保留为落地与复核顺序；当前执行位置已经进入股票模拟系统初始化之前。

## 1. 第一阶段：验证一个真实 worker

第一步只解决 Codex app-server 接入，不实现 orchestra。

必须实际确认：

- 可以启动 app-server；
- 可以完成初始化；
- 可以新建 thread；
- 可以开始一次执行；
- 可以等待执行结束并取得最终消息；
- 可以保存 thread 标识；
- app-server 进程退出后可以恢复同一 thread；
- 可以中断当前执行。

使用临时仓库完成一次新建和一次恢复即可。

这一阶段不得加入：

- 通用 worker 接口；
- Claude Code；
- worker 池；
- 任务数据库；
- 自动重试；
- 旧运行时节点和 receipt 协议。

如果旧 Runtime Kernel 中已有可抽取的 Codex 通信代码，只抽取与 app-server 通信直接相关的部分。

## 2. 第二阶段：实现机械外壳

实现：

```text
init
status
控制目录
原子文件写入
Git 机械事实收集
orchestra 输出解析
```

这一阶段用固定假输出代替模型。

需要证明：

- 同一项目总能找到同一控制目录；
- 初始化不会覆盖已有状态；
- 状态更新失败不会留下半写文件；
- 五种决定可以被识别；
- 格式错误不会覆盖旧状态；
- `status` 只显示机械事实，不自行解释项目。

## 3. 第三阶段：实现全新 orchestra 决策轮

接入 Hermes `AIAgent`：

```text
读取 state.md、task.md、result.md
→ 收集 Git 机械事实
→ 创建全新 orchestra 会话
→ 提供只读代码检查能力
→ 取得当前决定、新状态和 worker 任务
→ 原子保存
→ 结束会话
```

每轮必须确认：

- 使用新的 `session_id`；
- 不传入上一轮对话；
- 不加载普通记忆、人格和上下文文件；
- 不加载 `last-orchestra-output.md`；
- 单轮内允许完整工具循环；
- orchestra 不修改业务代码；
- 每轮最多产生一个当前任务。

这一阶段先只运行 `decide`，不自动启动 worker。人类检查数轮输出，确认任务粒度和项目状态没有明显错误后，再连接执行层。

## 4. 第四阶段：连接一对一闭环

接入 `run-worker`：

```text
开始新任务
→ 新建 Codex thread

继续当前任务
→ 恢复当前 Codex thread

等待 / 询问人类 / 停止
→ 不启动 worker
```

worker 完成后把最终结果保存到 `result.md`，但不自动开始下一轮。

再实现交互式 `step`：

```text
decide
→ 显示决定和 worker 任务
→ 人类确认
→ run-worker
```

首版始终由人类显式启动每一步，不运行无人值守循环。

## 5. 第五阶段：机械闭环验收

在极小临时仓库中连续运行至少三个决策轮。

该仓库只用于验证程序连接，不用于评价 orchestra 的战略能力。任务可以很简单，但必须覆盖：

1. 第一个新任务启动新 worker thread；
2. 同一个任务未完成时恢复原 thread；
3. 实质不同的新任务启动新 thread；
4. worker 结果被下一轮 orchestra 读取；
5. 至少一次 `等待`、`询问人类` 或 `停止` 不启动 worker；
6. 全程不需要人工复制粘贴 `state.md`、`task.md` 或 `result.md`。

只有这一阶段通过，才能称为“已经有首版 orchestra”。

## 6. 第六阶段：进入股票模拟系统

机械闭环通过后，按 [`targets.md`](targets.md) 建立独立股票模拟系统仓库。

开始前只准备：

- 本地历史行情；
- 人类意图；
- 首版真实边界；
- 当前仓库事实；
- 少量可观察的项目成形迹象。

不要预先规定完整模块图和路线图。

股票项目的第一轮流程：

```text
init 写入初始人类意图
→ decide 启动全新 orchestra
→ orchestra 检查数据与仓库现实
→ 生成一个当前任务
→ 人类只检查关键遗漏和明显越界
→ run-worker 启动真实 Codex
→ 保存结果
→ 下一次 decide 重新判断
```

股票系统用于调试：

- orchestra 需要哪些项目事实；
- 哪些事实只应按需读取；
- 项目决策边界是否过早或过晚；
- worker 任务是否过大或过小；
- 新任务是否需要新 worker thread；
- 项目状态是否开始膨胀；
- 项目是否从完整模拟流程漂移到通用量化平台和内部框架。

## 7. 股票项目中的自然决策边界

典型触发：

- 当前 worker 任务完成；
- 当前任务明确阻塞；
- 时间、成交或账户语义的承重假设被推翻；
- 一条完整用户流程首次跑通；
- 新数据暴露未来信息或账目不一致；
- worker 开始把任务扩大到插件平台、事件总线或实盘能力；
- 连续工作没有产生有效项目变化；
- 即将作出大范围或不可逆决定；
- 人类改变重大方向；
- 项目可能已经达到当前长期目的。

普通测试失败、函数选择、文件组织和 worker 内部子代理调度不触发 orchestra。

首版由人类显式判断边界。只有重复出现稳定规律后，才研究自动提醒。

## 8. 每轮调试记录

项目状态只保存当前有效认识，并整体覆盖。

研发调试可以另外保留：

- orchestra 原始输入；
- orchestra 原始输出；
- 人类修正；
- worker 最终结果；
- 本轮错误类型；
- 模型、成本和耗时。

这些记录默认不进入下一轮上下文，也不形成版本、迁移和恢复责任。

错误类型至少区分：

- 缺少关键事实；
- 把 worker 自述当成事实；
- 被旧决定锚定；
- 没有新事实却随机换方向；
- 过度深入局部实现；
- worker 任务过大；
- worker 任务过小；
- 把代理自建机制当成项目目标；
- 没有发现承重假设失效；
- 不必要地询问人类；
- 正确发现人类忽略的问题。

一次只调整一个主要变量。

## 9. 进入股票项目后的可用趋势

应逐渐出现：

- 全新 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要注入完整旧对话；
- orchestra 会按需核实关键事实，而不是只改写摘要；
- orchestra 不成为第二个编码 worker；
- 每轮只生成一个粒度合适的任务；
- worker 能在明确任务中完整自治；
- 实质不同的新任务不继承旧 worker 叙事；
- 股票系统持续形成可运行交易流程、可解释账目或判别性证据；
- 项目状态保持短且可直接重写；
- 人类纠偏逐渐集中到真正的方向与价值选择。

若长期出现以下情况，应停止扩建并修正现有接口：

- 人类每轮都要重讲整个项目；
- orchestra 只是复述 worker；
- 缺少完整历史就无法判断；
- 为防摇摆开始保存越来越多旧推理；
- 项目状态长出固定字段、版本、迁移和兼容；
- orchestra 开始直接实现业务代码；
- worker 任务持续过大或过小；
- 股票项目持续转向内部框架、实盘或通用平台；
- 人类纠偏没有减少。
