# orchestra 首版落地与调试

> 本文说明首版按什么顺序进入真实项目。行为边界见 [`design.md`](design.md)，代码实施边界见 [`implementation.md`](implementation.md)，目标选择见 [`targets.md`](targets.md)。

## 0. 落地原则

首版不是形式化胜负实验，也不是一次综合项目演示。

Hermes 已经真实出现过：同一个 worker 在长期上下文中不断自行选择下一步，局部任务持续完成，但注意力逐渐转向自己创建的结构，原始项目目标退出中心。首版不再花成本重复证明这一点。

首版直接调试六个实际接口：

```text
人类意图与项目事实
        ↓
全新的 orchestra 会话
        ↓
项目级判断
        ↓
一个明确 worker 任务
        ↓
一个完整 worker
        ↓
可供下一轮重新判断的真实结果
```

需要逐轮确认：

- orchestra 应掌握哪些上下文；
- 项目决策边界应在何时出现；
- orchestra 应亲自检查多深；
- worker 任务边界是否清楚；
- 任务说明是否既能纠偏又不微操；
- 项目状态是否能长期保持轻量。

## 1. 首个目标

首版主要目标使用 [`targets.md`](targets.md) 中的“多供应商视频任务能力”。

选择它不是因为它能人工覆盖所有 orchestra 设计点，而是因为它本身是一个真实、长期、路线未定且存在注意力陷阱的业务目标。

开始前，人类只准备：

- 当前长期意图；
- 已确认的外部接口和约束；
- 当前仓库与运行环境；
- 已知的 Volc、渠道调度、任务查询和计量现实；
- 明确非目标；
- 少量可观察的项目成形迹象。

不要预先写完整路线图，也不要把讨论中的初步架构直接写成事实。

第二和第三候选只在首个目标的一对一运行方式基本稳定后使用，不并行推进。

## 2. 落地分为五步

### 第一步：准备首轮项目状态

创建一份自由格式 `state.md`，只写当前有效材料：

```text
人类意图
已确认项目事实
承重假设与失效信号
当前收敛缺口
重要外部边界与非目标
少量已停止路线
```

这里不是要求固定章节。首轮宁可少写，也不要把完整历史、路线辩护和旧 worker 对话塞入状态。

准备后由熟悉项目的人类快速检查：

- 是否把推断写成了事实；
- 是否遗漏真正的外部目标；
- 是否把旧运行时机制当成当前需求；
- 是否已经暗中写入一条完整路线图。

### 第二步：人工跑通两到三个决策轮

暂时不写启动器，由人工主会话完成材料传递：

```text
准备 state.md 与最近结果
→ 启动全新的 Hermes 会话扮演 orchestra
→ orchestra 按需检查仓库
→ 生成新的 state.md 与 task.md
→ 人类只检查关键遗漏和明显越界
→ 启动一个完整 worker
→ 保存 worker 最终结果
→ 再启动全新的 orchestra
```

这一步重点看材料边界，不评价体系优越性。

每轮记录的问题至少归入一种：

- 缺少关键事实；
- 把 worker 自述当成事实；
- 被旧决定锚定；
- 随机反转仍有效路线；
- 过度深入局部实现；
- 任务粒度过大；
- 任务粒度过小；
- 把代理自建机制当成项目目标；
- 没有识别承重假设失效；
- 不必要地询问人类；
- 正确发现人类忽略的问题。

一次只调整一个主要变量：状态内容、提示词、检查深度、任务说明或决策边界，不同时全部改动。

### 第三步：实现薄的 `decide` 启动器

人工流程稳定后，按 [`implementation.md`](implementation.md) 实现：

- 读取 `state.md`、`task.md`、`result.md`；
- 收集少量 Git 机械事实；
- 创建新的 `AIAgent` 会话；
- 禁用普通记忆与旧上下文文件；
- 允许本轮完整工具循环；
- 保存当前决定、完整新状态和 worker 推进说明；
- 结束 orchestra 会话。

这一阶段仍由人类显式触发，每轮仍可查看原始输出。

不要同时实现 worker 后端抽象、自动触发、数据库或状态校验。

### 第四步：接入一个真实 worker

只选择当前最稳定的一个 Codex 或 Claude Code 入口。

规则保持简单：

```text
同一明确任务继续
→ 恢复当前 worker 会话

任务目标、承重假设或自主范围实质变化
→ 启动新的 worker 会话
```

worker 在当前任务内自行规划、使用内部子代理、实现、测试和修复。外层只保存最终结果。

这一步重点确认：

- orchestra 下发的任务是否足够完整；
- worker 是否仍有充分执行自由；
- worker 是否会自行把任务扩大成下一阶段；
- 项目级新事实是否能明确上报；
- 新任务是否摆脱了旧 worker 会话的局部叙事。

### 第五步：在真实项目中连续运行

一对一闭环跑通后，继续使用真实项目的自然决策边界：

- 当前任务完成；
- 承重假设失效；
- worker 因项目级问题阻塞；
- 人类改变重大方向；
- 关键实验或外部事件完成；
- 当前任务开始无限扩大；
- 连续工作没有产生有效项目变化；
- 即将作出大范围或不可逆决定；
- 项目可能已经达到长期目的。

人类初期保留否决权，但只检查：

- 是否遗漏关键事实；
- 是否明显偏离外部目标；
- 是否越过不可逆边界；
- 是否出现只有人类能做的价值选择。

不要由人类重新替 orchestra 完整规划每一步。每次修正应说明是上下文缺口、提示词问题、检查深度问题还是判断错误。

## 3. 历史材料的使用方式

Hermes 旧运行时内核中的真实失焦点只作为回归材料。

选择六到十个历史决策点，覆盖：

- 自建机制开始产生下一轮需求；
- 项目目的被运行时一致性问题替代；
- 阶段完成但没有新端到端能力；
- 承重假设失效后仍继续旧路线；
- 应停止投入却继续增加阶段；
- 一次验证手段升级为永久系统。

每次修改 orchestra 提示词或项目状态内容后，可以重新运行少量相关快照，确认旧错误没有重新出现。

历史回放不比较“长期 worker”和“新 orchestra”谁更强，也不要求 orchestra 猜中唯一正确任务。它只检查当前上下文能否让新的 orchestra 看见人类已经知道的项目级问题。

## 4. 调试记录与运行状态分开

项目状态只保存当前有效认识，并整体覆盖。

研发调试可以另外保留：

- orchestra 原始输入；
- orchestra 原始输出；
- 人类修正；
- worker 最终结果；
- 本轮错误类型；
- 模型、成本和耗时。

这些记录默认不进入下一轮上下文，也不产生兼容、迁移和恢复责任。

优先复用 Hermes 已有会话日志与使用量记录。没有明确分析需求时，不再建立新的日志结构。

## 5. 每轮校准方法

### 5.1 上下文不足

表现：orchestra 漏掉人类认为显然重要的项目事实。

处理顺序：

1. 先确认该事实是否可以通过仓库或运行结果按需发现；
2. 若发现成本过高，再决定是否写入 `state.md`；
3. 只加入影响项目方向的精简事实；
4. 不把完整历史作为补救。

### 5.2 上下文过多

表现：orchestra 主要复述旧路线、worker 总结或旧设计文档。

处理：

- 删除无效历史；
- 把 worker 自述与事实分开；
- 只提供证据引用；
- 缩短当前决定残留；
- 必要时再单独测试两段式输入。

### 5.3 检查过浅

表现：orchestra 不核实代码与运行结果，只改写摘要。

处理：在固定职责中加强“对承重事实按需核实”，而不是把整个仓库预先塞进请求。

### 5.4 检查过深

表现：orchestra 花大量时间理解局部实现、开始给出代码方案或直接修改业务代码。

处理：

- 收窄本轮需要决定的问题；
- 强化只读边界；
- 要求只核实会改变项目方向的事实；
- 把普通实现选择留给 worker。

### 5.5 任务说明过细

表现：推进说明规定文件、类、函数、子代理和测试步骤。

处理：只保留期望项目变化、事实、假设、边界和证据要求。

### 5.6 任务说明过粗

表现：worker 收到的仍是原始宏大目标，无法形成一个连贯任务。

处理：让 orchestra 明确本轮希望项目现实发生的一个变化、为什么现在做、什么证据足以返回。

### 5.7 全新决策轮随机摇摆

表现：没有新事实却频繁换方向。

处理：

- 保留简短当前决定、承重假设、预期信号和失效条件；
- 要求方向改变必须指出新增证据或此前遗漏的矛盾；
- 不恢复旧推理辩护；
- 若仍不稳定，再单独研究两段式输入。

## 6. 首版可用的趋势

首版不是靠一次演示通过，而是实际运行中逐渐出现：

- 新的 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要注入完整旧对话；
- orchestra 能核实关键事实而不成为第二个 worker；
- 已失效假设和代理自建工作能够被识别；
- 每轮只生成一个粒度合适的任务；
- worker 能完整执行且保持自主；
- 新任务不再继承无关旧会话；
- 项目持续产生真实能力、集成结果或关键证据；
- 项目状态保持短且可直接重写；
- 人类纠偏逐渐集中到真正的方向和价值选择。

若长期出现以下情况，应暂停扩建并重新检查设计：

- 人类每轮都要重讲整个项目；
- orchestra 只是复述 worker；
- 缺少完整历史就无法判断；
- 为防摇摆开始保存越来越多旧推理；
- 项目状态长出固定字段、版本、迁移和兼容；
- orchestra 开始承担实现；
- worker 任务持续过大或过小；
- 人类纠偏没有减少；
- 项目仍然只在维护代理自建机制。

## 7. 何时进入第二目标

只有满足以下条件后，才考虑使用 [`targets.md`](targets.md) 中的第二目标：

- 一对一闭环已经在首个目标中连续运行；
- 项目状态和推进说明不再频繁大改；
- orchestra 的常见错误类型已经稳定；
- 新任务和旧任务的 worker 会话边界基本可判断；
- 没有为了首个项目增加大量专用规则；
- 人类认为当前设计可能已经对首个项目过拟合。

第二目标用于检查上下文原则能否迁移，不用于同时扩大系统规模。

## 8. 后续独立研究

以下内容不属于首版落地：

### 8.1 两段式输入

比较一次性输入与先看事实、后看精简历史，确认是否稳定减少锚定。

### 8.2 自动项目决策边界

只有手工触发形成稳定规律后，才研究最小自动提醒。

### 8.3 worker 会话策略细化

首版使用“同一任务继续，新任务默认新会话”。后续再研究哪些自然延续值得复用。

### 8.4 多 worker

多 worker 需要单独解决并行判断、工作区、共享边界、取消、合并和集成责任。它不是一对一首版的自然扩展，也不应作为当前演示功能。

## 9. 明确不做

- 重新证明单 worker 会长期漂移；
- 综合项目演示；
- 正式排行榜或通用基准；
- 多 worker；
- 守护进程；
- 自动轮询；
- 任务数据库；
- 执行图；
- 状态校验与版本迁移；
- 通用 worker 适配层；
- 自动评审流水线；
- 固定阶段类型；
- 持久 orchestra 推理历史。

首版只把一对一 orchestra 的上下文、项目决策边界、worker 任务边界和推进说明在真实项目中实际跑通。
