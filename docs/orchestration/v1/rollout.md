# orchestra 首版落地与调试

> 本文说明首版按什么顺序进入真实项目。行为边界见 [`design.md`](design.md)，代码实施边界见 [`implementation.md`](implementation.md)，目标选择见 [`targets.md`](targets.md)。

## 0. 落地原则

首版不是形式化胜负实验，也不是一次综合项目演示。

Hermes 已经真实出现过：同一个 worker 在长期上下文中不断自行选择下一步，局部任务持续完成，但注意力逐渐转向自己创建的结构，原始项目目标退出中心。首版不再花成本重复证明这一点。

首版直接调试六个实际接口：

```text
人类意图与项目事实
        ↓
全新的 orchestra 会话
        ↓
项目级判断
        ↓
一个明确 worker 任务
        ↓
一个完整 worker
        ↓
可供下一轮重新判断的真实结果
```

需要逐轮确认：

- orchestra 应掌握哪些上下文；
- 项目决策边界应在何时出现；
- orchestra 应亲自检查多深；
- worker 任务边界是否清楚；
- 任务说明是否既能纠偏又不微操；
- 项目状态是否能长期保持轻量。

## 1. 首个目标

首版主要目标使用 [`targets.md`](targets.md) 中的“股票模拟系统”。

人类意图是：

> 做一个本地可运行、结果可复现的股票模拟交易系统。用户提供历史行情、初始资金和交易规则，系统按时间推进，接受买卖指令，模拟成交，维护现金、持仓、成本和账户净值，并能查看和解释完整过程。它不是实盘交易系统，不提供投资建议，也不提前建设通用量化平台。

选择它不是因为它能人工覆盖所有 orchestra 设计点，而是因为它本身是一个真实、长期、路线未定且存在注意力陷阱的业务目标。

开始前，人类只准备：

- 一个独立的目标仓库；
- 一份本地历史行情及其来源、字段、时区和复权说明；
- 当前长期意图；
- 不接实盘、不做实时高频、不做多用户平台等真实边界；
- 当前仓库与运行环境事实；
- 少量可观察的项目成形迹象。

不要预先写完整路线图，不要预先规定行情层、撮合层、账户层、策略层和报表层，也不要把某个内部架构设想直接写成事实。

首版只运行这一个宏大目标。另一个领域目标在一对一运行方式基本稳定后再重新选择，不在当前阶段维护候选清单。

## 2. 落地分为五步

### 第一步：准备首轮项目状态

创建一份自由格式 `state.md`，只写当前有效材料：

```text
人类意图
已确认项目事实
承重假设与失效信号
当前收敛缺口
重要外部边界与非目标
少量已停止路线
```

这里不是要求固定章节。首轮宁可少写，也不要把完整历史、路线辩护和旧 worker 对话塞入状态。

股票模拟系统的首轮状态至少需要核实：

- 本地行情实际包含哪些股票、日期和字段；
- 当前仓库是否已有可运行代码；
- 当前是否存在任何端到端模拟流程；
- 人类对模拟时间、订单和账户结果有哪些明确要求；
- 哪些市场细节已经被明确排除；
- 当前最承重、但最缺证据的模拟语义是什么。

准备后由熟悉项目的人类快速检查：

- 是否把推断写成了事实；
- 是否遗漏真正的外部目标；
- 是否已经暗中写入一条完整路线图；
- 是否把“回测引擎”“通用量化平台”或某种架构当成了人类目标；
- 是否在最小交易过程尚未形成前加入大量未来市场规则。

### 第二步：人工跑通两到三个决策轮

暂时不写启动器，由人工主会话完成材料传递：

```text
准备 state.md 与最近结果
→ 启动全新的 Hermes 会话扮演 orchestra
→ orchestra 按需检查仓库和行情
→ 生成新的 state.md 与 task.md
→ 人类只检查关键遗漏和明显越界
→ 启动一个完整 worker
→ 保存 worker 最终结果
→ 再启动全新的 orchestra
```

这一步重点看材料边界，不评价体系优越性。

每轮记录的问题至少归入一种：

- 缺少关键事实；
- 把 worker 自述当成事实；
- 被旧决定锚定；
- 随机反转仍有效路线；
- 过度深入局部实现；
- 任务粒度过大；
- 任务粒度过小；
- 把代理自建机制当成项目目标；
- 没有识别承重假设失效；
- 忽略未来信息、账目一致性或结果复现；
- 不必要地询问人类；
- 正确发现人类忽略的问题。

一次只调整一个主要变量：状态内容、提示词、检查深度、任务说明或决策边界，不同时全部改动。

### 第三步：实现薄的 `decide` 启动器

人工流程稳定后，按 [`implementation.md`](implementation.md) 实现：

- 读取 `state.md`、`task.md`、`result.md`；
- 收集少量 Git 机械事实；
- 创建新的 `AIAgent` 会话；
- 禁用普通记忆与旧上下文文件；
- 允许本轮完整工具循环；
- 保存当前决定、完整新状态和 worker 推进说明；
- 结束 orchestra 会话。

这一阶段仍由人类显式触发，每轮仍可查看原始输出。

不要同时实现 worker 后端抽象、自动触发、数据库或状态校验。

### 第四步：接入一个真实 worker

只选择当前最稳定的一个 Codex 或 Claude Code 入口。

规则保持简单：

```text
同一明确任务继续
→ 恢复当前 worker 会话

任务目标、承重假设或自主范围实质变化
→ 启动新的 worker 会话
```

worker 在当前任务内自行规划、使用内部子代理、实现、测试和修复。外层只保存最终结果。

这一步重点确认：

- orchestra 下发的任务是否足够完整；
- worker 是否仍有充分执行自由；
- worker 是否会自行把任务扩大成下一阶段；
- 项目级新事实是否能明确上报；
- 新任务是否摆脱了旧 worker 会话的局部叙事；
- worker 是否把股票模拟扩大成实盘、实时、交易所或通用平台建设。

### 第五步：在真实项目中连续运行

一对一闭环跑通后，继续使用真实项目的自然决策边界：

- 当前任务完成；
- 时间、成交或账户语义的承重假设失效；
- worker 因项目级问题阻塞；
- 人类改变真实使用方式；
- 关键行情实验或核对结果完成；
- 当前任务开始无限扩大；
- 连续工作没有产生有效项目变化；
- 即将作出大范围或不可逆决定；
- 项目可能已经达到长期目的。

人类初期保留否决权，但只检查：

- 是否遗漏关键事实；
- 是否明显偏离完整模拟交易流程；
- 是否越过实盘、实时或平台化边界；
- 是否忽略未来信息与账目一致性；
- 是否出现只有人类能做的产品价值选择。

不要由人类重新替 orchestra 完整规划每一步。每次修正应说明是上下文缺口、提示词问题、检查深度问题还是判断错误。

## 3. 历史材料的使用方式

Hermes 旧运行时内核中的真实失焦点只作为回归材料。

选择六到十个历史决策点，覆盖：

- 自建机制开始产生下一轮需求；
- 项目目的被运行时一致性问题替代；
- 阶段完成但没有新端到端能力；
- 承重假设失效后仍继续旧路线；
- 应停止投入却继续增加阶段；
- 一次验证手段升级为永久系统。

每次修改 orchestra 提示词或项目状态内容后，可以重新运行少量相关快照，确认旧错误没有重新出现。

历史回放不比较“长期 worker”和“新 orchestra”谁更强，也不要求 orchestra 猜中唯一正确任务。它只检查当前上下文能否让新的 orchestra 看见人类已经知道的项目级问题。

股票模拟系统自身运行后，也可以逐渐保留极少量真实决策快照，例如：

- 在一笔交易尚未跑通前是否开始建设通用框架；
- 发现未来信息问题后是否仍只修补收益指标；
- 账目不一致时是否转向增加图表；
- 第二个真实场景出现后是否正确判断需要稳定的边界；
- 某个模拟机制已无真实使用方时是否继续维护。

这些仍然只是提示词回归材料，不进入项目状态。

## 4. 调试记录与运行状态分开

项目状态只保存当前有效认识，并整体覆盖。

研发调试可以另外保留：

- orchestra 原始输入；
- orchestra 原始输出；
- 人类修正；
- worker 最终结果；
- 本轮错误类型；
- 模型、成本和耗时。

这些记录默认不进入下一轮上下文，也不产生兼容、迁移和恢复责任。

优先复用 Hermes 已有会话日志与使用量记录。没有明确分析需求时，不再建立新的日志结构。

## 5. 每轮校准方法

### 5.1 上下文不足

表现：orchestra 漏掉人类认为显然重要的项目事实。

处理顺序：

1. 先确认该事实是否可以通过仓库、行情或运行结果按需发现；
2. 若发现成本过高，再决定是否写入 `state.md`；
3. 只加入影响项目方向的精简事实；
4. 不把完整历史作为补救。

### 5.2 上下文过多

表现：orchestra 主要复述旧路线、worker 总结或旧设计文档。

处理：

- 删除无效历史；
- 把 worker 自述与事实分开；
- 只提供证据引用；
- 缩短当前决定残留；
- 必要时再单独测试两段式输入。

### 5.3 检查过浅

表现：orchestra 不核实代码、行情与运行结果，只改写摘要。

处理：在固定职责中加强“对承重事实按需核实”，而不是把整个仓库和全部行情预先塞进请求。

### 5.4 检查过深

表现：orchestra 花大量时间理解局部实现、开始给出代码方案或直接修改业务代码。

处理：

- 收窄本轮需要决定的问题；
- 强化只读边界；
- 要求只核实会改变项目方向的事实；
- 把普通实现选择留给 worker。

### 5.5 任务说明过细

表现：推进说明规定文件、类、函数、子代理和测试步骤。

处理：只保留期望项目变化、事实、假设、边界和证据要求。

### 5.6 任务说明过粗

表现：worker 收到的仍是原始宏大目标，无法形成一个连贯任务。

处理：让 orchestra 明确本轮希望项目现实发生的一个变化、为什么现在做、什么证据足以返回。

### 5.7 全新决策轮随机摇摆

表现：没有新事实却频繁换方向。

处理：

- 保留简短当前决定、承重假设、预期信号和失效条件；
- 要求方向改变必须指出新增证据或此前遗漏的矛盾；
- 不恢复旧推理辩护；
- 若仍不稳定，再单独研究两段式输入。

### 5.8 被金融复杂性拖走

表现：项目开始追求所有市场规则、所有订单类型、所有公司行为或完整交易所真实性。

处理：

- 回到当前用户流程和已确认场景；
- 要求说明新复杂性阻塞了哪个真实结果；
- 没有真实场景时停止扩展；
- 把模拟假设显式写清，而不是用无限规则掩盖边界。

### 5.9 结果看似合理但无法核对

表现：收益曲线和指标已经存在，但无法从交易、现金、费用和持仓重新得到账户结果。

处理：优先选择恢复可解释性和账目一致性的任务，不继续增加策略、指标和界面。

## 6. 首版可用的趋势

首版不是靠一次演示通过，而是实际运行中逐渐出现：

- 新的 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要注入完整旧对话；
- orchestra 能核实关键事实而不成为第二个 worker；
- 已失效假设和代理自建工作能够被识别；
- 每轮只生成一个粒度合适的任务；
- worker 能完整执行且保持自主；
- 新任务不再继承无关旧会话；
- 股票模拟项目持续产生真实用户流程、集成结果或关键证据；
- 时间、成交和账户假设逐渐清楚且可核对；
- 项目状态保持短且可直接重写；
- 人类纠偏逐渐集中到真正的方向和价值选择。

若长期出现以下情况，应暂停扩建并重新检查设计：

- 人类每轮都要重讲整个项目；
- orchestra 只是复述 worker；
- 缺少完整历史就无法判断；
- 为防摇摆开始保存越来越多旧推理；
- 项目状态长出固定字段、版本、迁移和兼容；
- orchestra 开始承担实现；
- worker 任务持续过大或过小；
- 人类纠偏没有减少；
- 项目主要在建设量化框架、交易平台或自身基础设施；
- 基础交易和账户过程仍不可解释，却不断增加策略、指标和界面。

## 7. 何时考虑另一个领域目标

只有满足以下条件后，才考虑离开股票模拟系统，重新选择另一个宏大目标：

- 一对一闭环已经连续运行多个自然决策轮；
- 项目状态和推进说明不再频繁大改；
- orchestra 的常见错误类型已经稳定；
- 新任务和旧任务的 worker 会话边界基本可判断；
- 没有为了股票项目增加大量专用规则；
- 股票模拟系统已经形成一条可信、可复现、可解释的完整用户流程，或出现真实理由决定停止；
- 人类认为当前设计可能已经对金融领域过拟合。

第二个目标届时根据真实需要重新选择，不在当前文档提前维护候选清单。它只用于检查上下文原则能否迁移，不用于同时扩大系统规模。

## 8. 后续独立研究

以下内容不属于首版落地：

### 8.1 两段式输入

比较一次性输入与先看事实、后看精简历史，确认是否稳定减少锚定。

### 8.2 自动项目决策边界

只有手工触发形成稳定规律后，才研究最小自动提醒。

### 8.3 worker 会话策略细化

首版使用“同一任务继续，新任务默认新会话”。后续再研究哪些自然延续值得复用。

### 8.4 多 worker

多 worker 需要单独解决并行判断、工作区、共享边界、取消、合并和集成责任。它不是一对一首版的自然扩展，也不应作为当前演示功能。

## 9. 明确不做

- 重新证明单 worker 会长期漂移；
- 综合项目演示；
- 正式排行榜或通用基准；
- 多 worker；
- 守护进程；
- 自动轮询；
- 任务数据库；
- 执行图；
- 状态校验与版本迁移；
- 通用 worker 适配层；
- 自动评审流水线；
- 固定阶段类型；
- 持久 orchestra 推理历史；
- 真实券商接入；
- 实时模拟盘平台；
- 通用量化研究平台；
- 完整交易所微观结构仿真。

首版只把一对一 orchestra 的上下文、项目决策边界、worker 任务边界和推进说明，在股票模拟系统这个真实长期目标中实际跑通。
