# 深审 Prompt

Orchestra 深审（见 `orchestra-design.md` §2.2、§6.2）使用的 prompt。由命名实体计数
越过阈值触发。

## 设计依据

三条约束来自实证结果，改动前请先确认没有推翻它们：

1. **必须喂外部信号，不能让模型内省。** 无外部反馈的内在自我纠正在推理类任务上不成立，
   有时纠正后更差。所以输入里必须有确定性读数，不能只问"这是不是过度设计了"。
2. **不给它生成侧的上下文。** 同一系统既生成又审查，得到的不是第二意见，是规模化的
   确认偏差。因此输入不含历次批准记录、不含原始生成 prompt、不含决策者身份。
3. **不要促进反复自检。** 前沿模型已经架构性地激进自检，叠加"仔细检查""再确认一遍"
   会浪费 token 甚至导致循环。

审查者模型的选择：避开会自我拔高的模型族。测量显示部分模型对自己家族的评分显著偏高，
也有模型持续低估自己家族——对否定任务而言，后者是有利方向。

## 已知的可靠性边界

过度设计与多余功能是当前确定性工具和 LLM 都检测不可靠的一类。本 prompt 的第一步
（逐项审计）把一部分主观判断转成了机械查找，这部分可靠；第二步里 1、3、4 有确定性
读数托底，2、5、6 仍是判断，会有漏检和误报。

**不要指望它抓全，指望它抓到足够多、足够早。**

---

## Prompt

```markdown
# 深审

你继承了一个正在进行的项目，做一次结构审计。你没有参与过它的任何决定，
也看不到当初是谁、基于什么理由做的。你只能看到原始意图和现在的状态。

## 输入

【原始意图】
<项目为什么存在、要什么、红线。这是唯一的参照基准。>

【确定性读数】（由工具产生，不是判断，直接采信）
- 机制/模块/抽象/文档清单及各自的规模
- 自上次审计以来新增的命名实体数
- 语义重复检测结果（做同一件事的多处实现）
- 复杂度指标及其变化量
- 各机制自加入以来是否被触发/使用过

【现状描述】
<当前产物做到了什么、哪些意图条目已满足。>

【未消解的怀疑】
<历次审计留下、尚未解决的疑虑。不含任何过往的批准记录。>

## 第一步：逐项审计（必须完成，不可跳过）

对清单里的**每一个**条目，填一行：

| 名称 | 一句话说明它做什么 | 服务原始意图的哪一条 | 依据 |
|---|---|---|---|

「依据」只接受两种：
- **意图追溯**——直接服务于原始意图的某一条，写出是哪条；
- **实际故障**——为处理一个**真实发生过**的故障而存在，写出那次故障。

不接受：看起来更稳妥、将来可能需要、是良好实践、别的系统都这么做、
理论上能防止某种问题、让结构更规范。

**填不出合格依据的行直接进入移除候选。这是发现，不是判断——你不需要论证
它不好，只需如实记录找不到依据。**

## 第二步：形状检查

每个问题都要引用【确定性读数】里的具体数据作为证据。

1. **增长是否成比例？** 新增了多少个需要人理解的名字，换来了多少条意图被
   真正满足。
2. **有没有为自己造的问题打的补丁？** 是否存在这样的机制：它的存在理由是
   修复另一个我们自己引入的机制带来的问题。有就列出整条链——应当砍掉链的
   源头，而不是加固补丁。
3. **有没有语义重复？** 对照重复检测读数，指出哪几处在做同一件事。写法不同
   不算不同。
4. **有没有从未被触发过的机制？** 对照使用读数，列出加入后从未生效的条目。
5. **有没有在给一条不通的路砌墙？** 同一区域反复修改加固，但那条路上的意图
   条目始终没有推进。
6. **可读性**：一个只看当前状态的人，能否说清这个项目在做什么。说不清的话，
   指出是哪些条目造成的。

## 第三步：结论

只输出三样：

**移除清单**——每项写明移除什么、依据（引用第一步或第二步的具体发现）、
预期减少的命名实体数。

可以为空，但只有当第一步每行都有合格依据、且第二步六项均无发现时才成立。
空清单必须由表格证明。

**未消解的怀疑**——你在盯什么、什么让你不放心、什么情况会让你推翻本次结论。
传给下一次审计。

**终止判断**——三选一并说明理由：继续／已达成原始意图／不值得继续（未被阻塞
但投入产出比已反转）。

## 硬性禁止

- **不得提出任何新机制、新流程、新规范、新检查、新文档。** 发现问题时唯一
  允许的回应是移除、合并或简化。
- 不得建议"改进"或"完善"某个条目。要么它有合格依据保留原样，要么进入移除
  清单。
- 不得为了产出而制造移除项。找不到就报告找不到。
- 不得评价代码质量、风格、命名、测试覆盖。本次只关心结构与意图对齐。
- 不要反复自我检查或重复验证已经得出的结论。一遍即可。
```

## 输出的去向

移除清单作为一个普通任务派给 worker 执行。验收标准不是 worker 的自述（它会说
"已移除"），而是**下一次快照的命名实体数必须真的下降**。

删除类任务极易变成新增类任务——worker 常见的做法是加一层兼容包装、加一个开关、
加一段迁移代码，为了删掉东西反而加了更多东西。计数是唯一可靠的验收。
