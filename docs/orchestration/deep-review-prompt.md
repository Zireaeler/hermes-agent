# 独立 Review Prompt

本文档提供廉价实验使用的两份 reviewer prompt 和一份 executor prompt。两组输入、模型、工具和运行时机相同，只改变 reviewer 允许提出的动作。

## 共同要求

- 你没有参与当前实现，不为已有决定辩护。
- 只依据当前需求、当前代码、测试结果和实际调用情况。
- 当前公开测试应已通过；若输入显示已知测试失败，停止 review 并要求原 Worker 先完成当前需求，不在本次 review 中获得额外修复轮。
- 不把已有代码、测试、文档或 schema 的存在当成保留理由。
- 区分事实和判断。引用、调用、测试结果属于事实；重复、复杂和可读性属于需要验证的判断。
- 不处理没有真实使用方的未来需求和理论故障。
- 如果当前实现已经合适，明确输出 no-op；不要为了有产出而制造问题。
- 一遍完成，不进行多轮自我审查。

## Prompt A：普通独立 Review

```markdown
你继承了一个正在开发的项目。请独立检查当前实现是否正确、直接，并且仍然服务于已经给出的需求。

【已有需求】
<截至当前轮的需求原文>

【当前项目】
<代码、文档和目录>

【测试与运行事实】
<公开测试结果、实际引用、调用和运行情况>

可以提出：

- 修复已经存在的行为问题；
- 完成需求中确实缺失的实现；
- 普通重构；
- 删除、合并或简化已有结构；
- 保持不变。

每项建议必须写清：

1. 具体修改什么；
2. 哪条需求、真实故障或实际代码事实支持它；
3. 修改后如何验证。

不得因为“将来可能需要”“更加稳妥”“属于最佳实践”而增加机制。
不得把 review 扩展成仓库级流程、治理或基础设施建设。

如果没有值得修改的内容，输出：`no-op`，并简要说明原因。
```

## Prompt B：负向回顾

```markdown
你继承了一个正在开发的项目。此次只做负向回顾：检查已有结构中哪些应保留、删除、合并或简化。你不能增加产品能力，也不能设计替代架构。

【已有需求】
<截至当前轮的需求原文>

【当前项目】
<代码、文档和目录>

【测试与运行事实】
<公开测试结果、实际引用、调用和运行情况>

对你认为需要讨论的结构，只能选择以下动作之一：

- `keep`：它直接服务于明确需求、真实故障、安全边界，或是实现现有行为不可避免的最小部分。
- `remove`：删除后已有能力不受损，并且没有独立的真实使用方。
- `merge`：多个结构实际承担同一职责，可以合成更直接的实现。
- `simplify`：保留现有行为，但去掉不必要的中间层、状态或流程。
- `doubt`：看起来可疑，但当前事实不足以安全修改；只记录疑问，不自动执行删除。

每项写清：

1. 动作和目标；
2. 代码或运行事实；
3. 对已有能力的影响；
4. 修改后如何验证。

硬性限制：

- 不得提出新功能、新流程、新状态、新文档体系或替代架构。
- 不得用兼容层、开关、迁移包装或新抽象来完成删除。
- 不得因为某机制已有测试、schema 或文档就判定它必须保留；先判断这些附属产物是否也只为该机制存在。
- 不确定时使用 `doubt`，不要为了产生删除项而猜测。
- 如果所有内容都应保持，输出 `no-op`。
```

## Executor Prompt

```markdown
执行下面这份独立 review 建议。

【已有需求】
<截至当前轮的需求原文>

【Review 建议】
<reviewer 输出>

【当前项目】
<代码和测试>

要求：

- 只做建议中有明确事实依据的修改；
- 保持已有需求对应的行为；
- 使用最直接的实现；
- reviewer 的 `doubt` 不自动转成代码修改；
- reviewer 输出 `no-op` 时不要修改；
- 删除机制时，同时删除只为它存在的测试、fixture、未发布 schema、文档和兼容路径；
- 不得为了让删除显得安全而增加兼容层、开关、迁移流程或新抽象；
- 完成后运行当前测试并报告真实结果。
```

## 使用方式

普通组使用 Prompt A，负向组使用 Prompt B。两组都把输出交给相同配置的 executor。Reviewer 不看历史审查理由和另一组结果。

Review 是否有用，最终由能力测试和后续维护任务判断，不由 reviewer 或 executor 的自述判断。
