# Orchestra 方向说明

## 0. 当前状态

本文档记录一个尚未验证的方向，不是已经定稿的 Runtime 规范。

想法是：成熟的 Codex、Claude Code 等 coding agent 已经能作为完整 Worker 完成明确的软件任务；在长期连续开发中，额外的独立判断者也许能帮助项目重新检查目标、路线和已有结构，而不是让自动循环只会继续增加内容。

当前没有证据证明这层 Orchestra 有净收益。近期只验证其中一个很小的假设：负向回顾是否比普通独立 review 更有助于减少后续维护负担。实验见 `cheap-experiment.md`。

## 1. 真正的问题

一个连续 coding loop 很容易运行：给 Worker 一个需求，完成后再给下一个需求。

问题不是它不能推进，而是连续推进可能出现以下倾向：

- Agent 为提高信心增加 hash、snapshot、gate、ledger、retry 等辅助机制；
- 辅助机制产生自己的 schema、测试、迁移、恢复和文档；
- 后续 Agent 把这些自己创建的产物当成独立需求；
- 清理时继续保留、替换或扩展原本没有真实使用方的能力。

这是一种自我强化的结构增长。Hermes Runtime Kernel 的历史也说明：更多 phase、节点、协调事件和验证机制不代表项目价值更高，协调成本可能远高于实际收益。

但这并不自动证明“增加一个 Orchestra”能够解决问题。新的 Orchestra 同样可能增加更多 review、记录和治理。因此先做直接实验，而不是先实现系统。

## 2. 角色

### Human

Human 提供：

- 项目意图；
- 当前需求；
- 不可越过的真实边界；
- 少数确实需要人的方向选择。

目标是让 Human 不必持续监管实现过程。

### Worker

Worker 是完整的 coding agent，而不是被拆成 planner、coder、reviewer、tester 的局部组件。

Worker 自己决定如何阅读、实现、测试和调用内部子代理。外层不重复建设 Worker 已有的任务拆分和 subagent 管理。

### Orchestra

如果未来值得建设，Orchestra 的作用不是替 Worker 实现，而是在较长周期上重新判断：

- 当前产物是否仍服务于原始意图；
- 当前路线是否仍值得继续；
- 已有结构是否应保留、删除、合并或简化；
- 是否应该停止、回退、换方向或询问 Human。

这些都是可能的职责，不是已经验证的能力。

### 独立核实者

独立核实者检查当前代码、测试和运行事实，不依赖 Worker 自述。它可以是一次性的 agent，不需要成为永久节点或子系统。

## 3. 这次先验证什么

只验证负向回顾：

```text
普通独立 review
vs
只允许 keep / remove / merge / simplify / doubt 的独立 review
```

重点不是它有没有成功删除一段代码，而是：

1. 已有能力是否保持；
2. 后续维护任务是否更容易正确完成；
3. review 带来的成本是否小于收益。

一次删除不能证明完整 Orchestra 成立；一次没有删除也不能证明长期判断不可能有价值。这个实验只决定负向回顾是否值得继续研究。

## 4. 判断与代码边界

语义判断由 agent 完成，例如：

- 路线是否值得继续；
- 某个抽象是否真的有用；
- 是否应该删除、替换或停止。

代码可以保护真实的操作边界，例如：

- 凭证和权限；
- 破坏性或不可逆操作；
- 已发布数据和外部协议；
- 明确的预算上限；
- 基本的数据完整性。

代码不应通过不断增加 validator、状态和流程来代替语义判断。反过来，agent 也不能绕过真实安全边界。

## 5. 信息限制

外部判断者有一个真实难题：

- 阅读全部实现和历史，容易被细节淹没并继承作者的理由；
- 只读总结，又可能看不到结构增长和真实耦合。

目前不建设 snapshot、ledger 或长期判断记录系统来解决它。廉价实验直接让 reviewer 阅读当前项目、需求、测试和运行事实。

为了减少锚定：

- reviewer 不看作者辩护；
- reviewer 不看另一组结果；
- reviewer 先独立判断当前状态；
- 旧疑虑只在独立判断后按需对照。

如果连小项目上的直接阅读都没有收益，建设更复杂的信息系统没有意义。

## 6. 并行和子代理

并行不是免费的。无论是竞争式尝试还是协作式拆分，都消耗 token、wall time、上下文和整合注意力。

默认让一个完整 Worker 连贯完成任务。可以使用任意数量的内部子代理，但每个子代理应承担独立且有用的工作。不能把更多 agent、更多节点或更多 review 当成成功指标。

普通工作默认使用 `terra-high` 及以下；Luna 用于简单查找和机械核验；Sol 只处理多个 Terra 无法用测试或事实裁决的关键冲突。

## 7. 如何看结构负担

不使用单一实体数、文件数、类数或 LOC 判断结构好坏。真正关心的是：

- 新维护者需要理解多少概念；
- 一次局部变化会牵动多少地方；
- 删除一个能力是否需要处理大量无关结构；
- 修改后需要多大的验证范围；
- 相同后续需求能否更快、更少失败地完成。

因此廉价实验使用实际后续维护任务作为主要观察，而不是建设新的复杂度测量系统。

## 8. 停止条件

当前只进行文档修正和廉价实验。

在实验显示稳定收益前，不建设：

- 新数据库或状态机；
- decision session、checkpoint 或 compaction；
- review ledger、artifact lineage 或证据协议；
- 节点通信和持久化协调；
- 围绕 Orchestra 的 validator 和恢复系统。

如果实验没有收益，停止这个方向。若有收益，再根据实际结果决定最小下一步，而不是提前设计完整 Runtime。
