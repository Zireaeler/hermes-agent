# orchestra 设计：项目战略层

## 0. 核心定义

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮从当前人类意图、项目状态、最近结果和按需证据重新构建上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承旧对话、推理过程和策略辩护。**

首版结构：

```text
人类
  │  提供长期意图、重大方向和价值选择
  ▼
全新的 orchestra 决策轮
  │  恢复项目局面、判断主要缺口、选择当前任务
  ▼
一个完整 worker
  │  在当前任务内持续调查、实现、测试和修复
  │  可以自行使用内部子代理
  ▼
可观察结果、证据、失败或承重发现
  │
  └────────→ 下一次全新的 orchestra 决策轮
```

长期存在的是：

- 人类当前意图；
- 项目当前状态；
- orchestra 对项目方向负责的角色；
- 目标仓库中的真实产物和证据。

不长期存在的是：

- orchestra 的完整对话；
- orchestra 的推理链；
- 旧计划和设计辩护；
- worker 的完整执行过程在项目级上下文中的复制。

架构原则：

```text
项目连续性属于持久项目状态。
orchestra 推理只属于单次决策轮。
worker 执行连续性只属于当前明确任务。
详细历史属于仓库、Git 和 worker 会话。
项目状态是当前工作集，不是运行时协议或历史账本。
```

## 1. 设计要解决的问题

成熟的 Codex、Claude Code 等 worker 已经能够在一个明确任务内完成：

- 阅读代码；
- 形成局部方案；
- 调用内部子代理；
- 并行调查局部问题；
- 编码、测试、调试和修复；
- 整合局部结果。

因此 orchestra 的价值不来自重新建立规划者、编码者、测试者和评审者。它解决的是现有 worker 在跨多个任务、长期持有项目方向时容易出现的视野问题：

```text
人类给出远大目标
→ worker 完成一个局部任务
→ 下一步从自己刚建立的结构中产生
→ 新机制成为最显眼的问题
→ 继续补一致性、恢复、兼容和审计
→ 每项局部工作都可解释
→ 原始产品目标逐渐退出注意力中心
```

Hermes 旧 Runtime Kernel 已经真实出现这种现象。它不是关于所有模型和项目的普遍定理，但足以成为本系统明确要解决的工程前提。

orchestra 每次重新回答：

```text
项目现在真实能做什么？
距离人类当前意图还缺什么？
最近工作实际减少了哪个缺口？
当前路线依赖的承重假设是否仍成立？
下一项工作应当实现、调查、做判别实验，还是询问人类？
现在最值得推进的是否只是最显眼、最容易闭合的机械问题？
```

## 2. 两个不同时间尺度的循环

系统不是一个上层代理逐步遥控下层代理，而是两个不同时间尺度的自治循环。

### 2.1 worker 的快速执行循环

```text
理解当前任务
→ 查明局部事实
→ 形成方案
→ 调用子代理
→ 修改和运行
→ 根据结果修正
→ 完成和验证
```

该循环需要连续上下文。orchestra 不应在每次文件修改、测试失败或子代理返回后介入。

### 2.2 orchestra 的慢速项目循环

```text
读取当前人类意图与项目状态
→ 吸收最近结果
→ 核实少量承重事实
→ 重写项目为何尚未成立
→ 选择一个完整责任
→ 交给 worker
```

该循环不需要长期模型会话。旧对话反而会带入此前决定、辩护和沉没成本，使模型更难否定自己的路线。

### 2.3 人类的更慢循环

人类只在以下情况介入：

- 产品用途或价值取舍；
- 许可和风险接受；
- 外部承诺；
- 不可逆操作；
- 项目方向实质改变；
- 已形成较大用户能力，需要体验和选择后续方向。

人类不应成为每次 `decide`、worker 完成或普通提交的审批节点。

## 3. fresh 决策轮不是无状态

每次 orchestra 使用全新会话，是为了不继承模型自己生成的历史叙事，而不是让系统遗忘项目。

```text
模型会话：全新
项目责任：连续
项目状态：持久
仓库事实：持久
```

新的决策轮通过重新读取：

- `intent.md` 中的人类当前意图；
- `state.md` 中的当前项目判断；
- 最近的 `task.md` 和 `result.md`；
- Git 和仓库机械事实；
- 与本轮判断相关的按需证据；

恢复项目局面。

fresh 的关键是**重新构造最小充分上下文**，不是把全部历史换一种摘要形式重新塞入。

稳定的角色说明和输出要求可以作为固定前缀并利用缓存；不能继承的是旧 assistant 消息、完整推理、策略辩护和已被取代的上下文。

## 4. 项目状态不是普通记忆

普通记忆回答“以前发生过什么”。项目状态必须支持当前决策：

```text
人类现在仍然要什么？
项目已经真实具备什么？
哪些解释只是推断？
当前路线依赖什么承重假设？
什么事实会推翻它？
项目为什么仍未成立？
哪些过去失败值得防止重复？
```

首版不建立事件账本、图数据库、状态版本和迁移。详细历史已经存在于 Git、仓库产物和 worker 会话中。

### 4.1 人类意图与项目判断分离

`intent.md` 只由人类维护，保存当前仍有效的目标、成功结果、硬边界和产品选择。

`state.md` 由 orchestra 重写，保存当前事实、推断、承重假设、收敛缺口、停止路线和决定残留。

orchestra 不能改写人类意图，也不能把自己的判断反向扩张为人类目标。

### 4.2 当前状态不是历史日志

`intent.md` 和 `state.md` 都应保持当前化：

- 被新决定取代的内容应删除；
- 不再影响方向的细节应删除；
- 可以从 Git 恢复的普通代码事实不重复保存；
- 长报告只保存结论和引用；
- 不按日期无限追加纠正和阶段记录。

需要追溯时使用 Git，而不是要求每次 fresh orchestra 重新阅读全部历史。

### 4.3 事实、推断和假设必须区分

- **事实**：由代码、测试、运行、报告或人类决定支持；
- **推断**：orchestra 对事实的当前解释；
- **承重假设**：当前路线依赖、且一旦错误会改变后续方向的前提；
- **开放问题**：目前不能确认；
- **决定**：当前选择，不是永久真理。

首版不要求固定字段和数值置信度，但不能把这些性质不同的内容混写成同一种“项目事实”。

## 5. orchestra 的核心决策职责

### 5.1 识别当前主要收敛缺口

收敛缺口应以项目和用户行为表达，而不是直接以内部构件命名。

```text
较好：用户还不能根据提交时点前可见行情让规则产生订单。
较差：缺少 StrategyEngine、RuleRegistry 和 EventBus。
```

内部构件可以是实现结果，但不应在事实不足时替代项目问题本身。

### 5.2 选择推进方式

下一项工作不一定是业务实现。orchestra 需要区分：

```text
产品用途或价值选择不明确
→ 询问人类

领域事实可以缩小不确定性
→ 有边界的调查任务

技术可行性需要真实结果判断
→ 可丢弃的判别实验

项目语义与边界已经足够清楚
→ 完整实施任务

已有能力彼此孤立
→ 集成任务

出现真实端到端失败
→ 聚焦修复任务

外部依赖尚未满足
→ 等待

当前意图已经满足或继续投入无价值
→ 停止
```

不得用“最简单”替代“已经确认正确”。简单实现可以是技术选择，但不能静默决定产品含义、数据模型和正确性标准。

### 5.3 选择一个完整责任

首版每轮只选择一个当前任务。任务应是成熟 worker 可以完整占有的连贯责任，而不是一条命令、一个文件或固定阶段。

orchestra 不应把一个任务拆成：

```text
规划
编码
测试
评审
```

这些通常属于 worker 内部循环。

### 5.4 在提交决定前反证自己的选择

orchestra 应快速检查：

```text
首选方向依赖的最大假设是什么？
最近结果是否削弱了它？
是否只是选择了最容易观察和闭合的 Git、测试或文档问题？
它是否真正减少主要收敛缺口？
是否隐藏了未授权产品选择？
是否存在成本更小、信息增益更高的调查或实验？
即使当前机制还不存在，是否仍会因为人类意图和真实事实选择它？
```

这不是新的 reviewer，不产生评审节点，也不要求保存完整反驳过程。它只是减少旧路线、机械事实和沉没成本对决策的影响。

## 6. orchestra 应掌握的上下文

任何可能改变以下判断的信息属于 orchestra 上下文：

```text
下一项任务是什么？
当前路线是否继续？
需要实现、调查、实验还是询问人类？
worker 会话应继续还是重新开始？
项目是否已经满足当前意图？
```

只影响当前任务具体如何完成的信息留在 worker 内部。

orchestra 默认需要：

- 当前人类意图；
- 已确认的端到端能力和真实失败；
- 承重假设与失效条件；
- 当前主要收敛缺口；
- 最近 worker 结果；
- 当前仓库和 Git 的机械事实；
- 重要停止路线；
- 待人类决定的问题。

orchestra 默认不需要：

- 完整代码库摘要；
- worker 完整 transcript；
- 子代理对话；
- 每次命令和失败；
- 所有历史候选路线；
- 普通文件级实现计划。

## 7. worker 的设计边界

worker 接收一个明确任务，在任务内保持连续并可使用内部子代理。

它必须：

- 以当前 task、项目规则和工作区事实为权威；
- 在恢复或上下文压缩后重新锚定当前任务；
- 区分领域事实、技术不确定性和未授权产品选择；
- 只把能够独立回答的问题委派给子代理；
- 对子代理结果做关键核实和整合；
- 运行足以支持当前结论的验证；
- 当前问题得到可靠回答后停止验证；
- 完成后返回精简结果，不自行选择下一阶段。

worker 详细设计见 [`v1/worker-design.md`](v1/worker-design.md)。

## 8. 为什么首版不使用 DAG

DAG 假设任务结构和依赖可以在执行前相对可靠地知道。长期软件项目中，真正承重的依赖和工作边界往往在调查、实现和运行后才显现。

预制 DAG 容易产生：

- 把猜测变成计划惯性；
- 因图上存在节点而继续执行；
- 为维护节点、依赖、状态和修订增加运行时责任；
- 让 orchestra 主要维护图，而不是重新理解项目。

首版只维护一个当前任务。新的结构在执行后自然暴露，再由下一轮 orchestra 判断。

未来多 worker 也不应等同于把一张大图并行执行。外层并行只应对应多个能够独立维持局部决策循环、且协调耦合较低的项目推进面。该问题不属于首版。

## 9. 项目决策边界与运行节奏

典型边界：

- 一个完整 worker 任务结束；
- worker 明确阻塞；
- 承重假设被证伪；
- 关键调查或判别实验产生结果；
- 人类修改当前意图；
- 当前路线连续执行但没有减少项目缺口；
- 即将进入新的产品方向；
- 项目可能已经达到当前目标。

普通测试失败、局部重构、子代理调用和普通提交不是项目决策边界。

一条人类给实施者的运行指令可以覆盖多个机械循环：

```text
fresh orchestra
→ worker
→ fresh orchestra
→ 同一方向的必要收尾 worker
```

不应每完成一个命令就回到人类。只有到达产品选择、许可风险、不可逆动作、新产品方向、运行机制故障或较大用户能力验收时才停止。

实施者负责运行现有闭环，orchestra 负责项目方向，worker 负责任务实现。

## 10. 结果与证据

worker 最终回答是声明，不自动成为项目事实。新的 orchestra 应优先依据：

```text
真实可观察行为和可重复运行
→ 端到端与集成结果
→ 承重业务不变量
→ 聚焦测试和静态检查
→ 代码与提交
→ worker 总结和建议
```

该顺序不是固定评分公式，而是提醒：代码存在和测试很多不等于产品已经成立。

详细调查、数据统计和实现说明应写入仓库产物；`result.md` 只保留完成、关键验证、未闭合、方向影响和产物位置。

首版不设置固定 auditor。需要独立核验时，它应作为一个具体、有限的当前任务出现，而不是每轮默认流程。

## 11. 防止新系统重演旧 Runtime Kernel

以下现象出现时应立即收缩：

- `state.md` 需要版本、迁移或兼容；
- 每次输出错误都增加一个修复器或校验器；
- 每项任务都需要固定评审和测试节点；
- 因恢复问题开始建设复杂会话状态机；
- 因未来多 worker 预先建立注册表、消息层和执行图；
- 任务数量、测试数量、文档数量和调度活动被当成进展；
- 当前机制自身产生的问题不断升级为项目目标。

反事实检查：

> **即使当前机制尚不存在，这项工作是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不应因为已有投入继续扩大。

## 12. 首版范围

首版只实现和校准：

- 一个 fresh orchestra；
- 一个当前完整任务；
- 一个真实 worker；
- 人类意图与项目状态分离；
- worker 会话按任务连续；
- 结果进入下一轮项目判断；
- 人类显式触发或运行较大的闭环区间。

首版不实现：

- 多 worker；
- 外层任务并行；
- worker 直接通信；
- 执行图；
- 状态数据库；
- append-only 事件账本；
- 数值置信度；
- 自动项目决策边界；
- 固定评审流水线；
- 长期 orchestra 会话；
- 自动输出修复；
- 通用 worker 插件系统。

## 13. 判断设计是否有效

设计表现良好时，应逐渐看到：

- fresh orchestra 能从较短材料恢复人类认可的项目局面；
- 新证据可以推翻旧方向和已有投入；
- orchestra 正确区分调查、实验、实施和人类选择；
- 任务足够完整，不重复 worker 的内部规划；
- worker 在任务内保持强执行力，完成后停止；
- 子代理减少局部噪声，而不是增加整合成本；
- 项目状态保持当前、简短、可直接改写；
- orchestra 不只选择最显眼的机械收尾；
- 人类介入逐渐集中到真实产品和价值边界。

设计失效时，通常会出现：

- 人类每轮重讲整个项目；
- `intent.md` 变成完整纠正历史；
- `state.md` 变成状态协议或累积日志；
- orchestra 只是复述 worker；
- 每轮都处理 Git、文档、测试和恢复等易闭合问题；
- worker 任务过细或重新变成远大目标；
- 验证活动持续扩大而产品能力不变；
- 为修复一次真实故障继续建设更多运行时机制。

出现问题时，优先修改当前项目状态、任务说明和上下文组装。只有重复、稳定、无法通过这些材料解决的机械缺口，才应进入 Orchestra 代码。
