# orchestra 设计：间歇式项目战略层

## 0. 当前结论

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮都从当前人类意图、项目事实、精简结果和按需证据重新组装上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承旧对话、推理过程和策略辩护。**

首版严格采用一对一结构：

```text
人类
  │
  ▼
全新的 orchestra 决策轮
  │  选择、修正或停止当前推进方向
  ▼
一个完整 worker
  │  在当前明确任务内持续工作，自行使用内部子代理
  ▼
任务结果或项目级新事实
  │
  └────────→ 下一次全新的 orchestra 决策轮
```

本设计把以下现象作为已经观察到的工程前提，不再设计实验重复证明：

> **在长期项目中，让同一个 worker 在自己的连续上下文里不断维持远大目标并自行选择下一步，容易使目标逐渐涣散，注意力转向自己刚建立的结构，最终形成局部持续完成、整体不再收敛。**

这不是关于所有模型和所有项目的普遍定理，而是 Hermes 已经真实出现、且本系统明确要解决的问题。

因此首版不研究：

- 单 worker 是否会长期漂移；
- orchestra 在抽象意义上是否必要；
- 一次综合项目演示能否证明完整体系优越；
- 多 worker 是否比单 worker 更强。

首版直接解决以下工程问题：

```text
orchestra 应掌握哪些上下文？
怎样从精简项目状态恢复当前项目局面？
什么变化构成项目决策边界？
orchestra 应亲自检查到什么深度？
怎样把项目级判断变成 worker 能完整执行的任务？
worker 会话应在哪个任务边界结束或继续？
怎样维持长期连续性，又不重新长出一套运行时协议？
```

多 worker 的发现、分配、并行、协调和集成是另一组复杂问题，不属于首版。

架构原则：

```text
项目连续性属于持久项目状态。
orchestra 的推理只属于单次决策轮。
worker 的执行连续性只属于当前明确任务。
项目状态是可直接重写的材料，不是运行时协议。
```

本文档是一版待落地和反复调试的设计，不是新的运行时规范。第一版优先使用 Hermes 已有能力、普通项目文件和独立代理会话，在真实项目的自然决策边界逐轮运行。

## 1. 问题边界

完整的 Claude Code 或 Codex worker 已经能够在一个明确任务内完成：

- 阅读代码；
- 形成方案；
- 调用内部子代理；
- 拆分并行调查；
- 编码、测试和修复；
- 整合局部结果。

因此 orchestra 不应重复建立规划者、编码者、测试者和评审者，也不应把一个明确任务再次拆成多个外层 worker。

真正未被现有 worker 解决的是跨多个任务的长期项目方向：

```text
人类给出远大目标
→ worker 完成当前任务
→ worker 从自己刚建立的结构中选择下一步
→ 新机制成为新的注意力中心
→ 继续补一致性、恢复、兼容和审计
→ 原始产品目标逐渐退出注意力中心
```

每个局部任务可能都完成正确，但整个项目没有形成新的端到端能力，没有消除关键不确定性，也没有更接近可交付状态。

orchestra 的职责不是提高 worker 的局部编码能力，而是在项目决策边界重新回答：

```text
项目现在真实处于什么状态？
项目为什么仍未成立？
当前路线是否仍然值得继续？
下一项任务应让项目发生什么变化？
什么时候应该继续、改向、回退、等待或停止？
```

## 2. 首版只讨论一对一关系

首版固定只有：

```text
一个 orchestra
一个当前活动 worker
一个当前明确任务
```

一对一不表示 orchestra 持续盯住 worker。orchestra 只在项目决策边界出现，worker 在当前任务内保持完整自治。

worker 可以使用自身已有的子代理系统。它如何并行调查、拆分实现和整合结果，不属于 orchestra 的管理范围。

首版不讨论：

- 同时运行多个外层 worker；
- 识别低耦合并行任务；
- worker 之间的消息和共享状态；
- 多工作区写入和合并；
- 动态扩容、暂停和回收 worker；
- 多 worker 的集成责任；
- orchestra 自己维护长期子代理团队。

这些能力即使未来需要，也必须作为独立研究线逐项调试，不能被当成首版天然应有的功能。

## 3. 角色边界

### 3.1 人类

人类提供：

- 长期意图；
- 关键成功体验和可观察结果；
- 产品、安全和外部协议边界；
- 后续重大方向变化；
- 事实无法裁决的价值选择。

人类不负责持续决定每个局部下一步，也不需要阅读 worker 的完整执行过程。

首版调试期间，人类临时承担判断基准：指出 orchestra 漏掉的关键事实、错误路线和不合适的任务边界。该职责用于校准设计，不应成为最终系统的长期依赖。

### 3.2 orchestra

orchestra 只负责任务之间的项目级判断：

- 重新确认当前人类意图；
- 独立检查与战略判断相关的项目事实；
- 判断上一项任务是否真正推动项目；
- 判断当前路线和承重假设是否仍然成立；
- 选择下一项有项目意义的明确任务；
- 决定继续、调整、回退、等待、询问人类或停止；
- 更新精简项目状态并生成 worker 推进说明。

orchestra 不负责任务内部实现，不接管普通错误修复，不管理 worker 内部子代理。

当一个实施任务需要在多个会实质改变产品含义、数据模型或正确性标准的解释之间作出选择，而当前人类意图和项目事实不足以决定时，orchestra 不得把其中一种解释隐藏在 worker 实施任务中。属于产品用途和价值选择的问题应询问人类；可以由领域证据减少的不确定性应先形成有边界的调查任务；可以由小型实现判断的问题应先形成可抛弃的判别实验；不得用“最简单”代替“已经确认正确”。

### 3.3 worker

worker 接收一个相对完整、有限、可验证的推进说明，并完整负责：

- 理解代码和任务；
- 形成局部方案；
- 自行拆分工作；
- 调用内部子代理；
- 编码、测试和修复；
- 返回可验证结果和可能影响项目方向的新事实。

worker 不需要向 orchestra 上报普通局部计划、命令历史、每次测试失败和内部子代理对话。

### 3.4 外层程序

首版外层程序只负责：

- 启动全新的 orchestra 会话；
- 启动或恢复当前 worker 会话；
- 投递人类消息、任务结果和证据引用；
- 管理基本进程、权限、预算和取消；
- 保存一份精简项目状态材料；
- 由人类或简单规则显式触发项目决策边界。

外层程序不判断下一步，不拆任务，不建立执行图和校验流程。

## 4. 核心运行原则

```text
项目连续性属于持久项目状态。
orchestra 的推理只属于单次决策轮。
worker 的执行连续性只属于当前明确任务。
项目状态是可直接重写的材料，不是运行时协议。
```

每次项目决策边界启动新的 orchestra 会话，不继承旧对话、工具记录和推理叙事。单次决策轮内允许完整代理循环。worker 在同一个明确任务内保持连续；实质不同的新任务默认使用新 worker 会话。

持久材料把人类意图与 Orchestra 判断分开：`intent.md` 是只由人类维护的唯一意图来源；`state.md` 只保存已确认事实、承重假设、收敛缺口、重要结果和待人类决定事项。两者都不是完整历史、冻结合同或固定 schema。

详细首版运行设计见 [`v1/design.md`](v1/design.md)。

## 5. 首版范围

首版严格是一对一关系：

```text
一个 orchestra
一个当前活动 worker
一个当前明确任务
```

首版只把以下部分调通：

- fresh orchestra 的上下文；
- 一份轻量项目状态；
- 项目决策边界；
- worker 任务边界；
- orchestra 到 worker 的推进说明；
- 真实项目中的逐轮校准。

首版落地与调试方式见 [`v1/rollout.md`](v1/rollout.md)。

## 6. 明确非目标

首版不建设：

- 多 worker 调度和外层并行；
- worker registry 或通信层；
- 固定角色团队；
- 路线图冻结、目标合同或执行图；
- 状态数据库、字段校验、版本和迁移；
- decision ledger、checkpoint、snapshot 或 compaction；
- 自动负向 review 或 cleanup；
- 持久 Orchestra 推理历史。

多 worker、两段式上下文、自动决策边界和 worker 会话策略细化都属于后续独立研究。
