# orchestra 设计：间歇式项目战略层

## 0. 当前结论

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮都从当前人类意图、项目事实、精简结果和按需证据重新组装上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承旧对话、推理过程和策略辩护。**

首版严格采用一对一结构：

```text
人类
  │
  ▼
全新的 orchestra 决策轮
  │  选择、修正或停止当前推进方向
  ▼
一个完整 worker
  │  在当前明确任务内持续工作，自行使用内部子代理
  ▼
任务结果或项目级新事实
  │
  └────────→ 下一次全新的 orchestra 决策轮
```

本设计把以下现象作为已经观察到的工程前提，不再设计实验重复证明：

> **在长期项目中，让同一个 worker 在自己的连续上下文里不断维持远大目标并自行选择下一步，容易使目标逐渐涣散，注意力转向自己刚建立的结构，最终形成局部持续完成、整体不再收敛。**

这不是关于所有模型和所有项目的普遍定理，而是 Hermes 已经真实出现、且本系统明确要解决的问题。

因此首版不研究：

- 单 worker 是否会长期漂移；
- orchestra 在抽象意义上是否必要；
- 一次综合项目演示能否证明完整体系优越；
- 多 worker 是否比单 worker 更强。

首版直接解决以下工程问题：

```text
orchestra 应掌握哪些上下文？
怎样从精简项目状态恢复当前项目局面？
什么变化构成项目决策边界？
orchestra 应亲自检查到什么深度？
怎样把项目级判断变成 worker 能完整执行的任务？
worker 会话应在哪个任务边界结束或继续？
怎样维持长期连续性，又不重新长出一套运行时协议？
```

多 worker 的发现、分配、并行、协调和集成是另一组复杂问题，不属于首版。

架构原则：

```text
项目连续性属于持久项目状态。
orchestra 的推理只属于单次决策轮。
worker 的执行连续性只属于当前明确任务。
项目状态是可直接重写的材料，不是运行时协议。
```

本文档是一版待落地和反复调试的设计，不是新的运行时规范。第一版优先使用 Hermes 已有能力、普通项目文件和独立代理会话，在真实项目的自然决策边界逐轮运行。

## 1. 问题边界

完整的 Claude Code 或 Codex worker 已经能够在一个明确任务内完成：

- 阅读代码；
- 形成方案；
- 调用内部子代理；
- 拆分并行调查；
- 编码、测试和修复；
- 整合局部结果。

因此 orchestra 不应重复建立规划者、编码者、测试者和评审者，也不应把一个明确任务再次拆成多个外层 worker。

真正未被现有 worker 解决的是跨多个任务的长期项目方向：

```text
人类给出远大目标
→ worker 完成当前任务
→ worker 从自己刚建立的结构中选择下一步
→ 新机制成为新的注意力中心
→ 继续补一致性、恢复、兼容和审计
→ 原始产品目标逐渐退出注意力中心
```

每个局部任务可能都完成正确，但整个项目没有形成新的端到端能力，没有消除关键不确定性，也没有更接近可交付状态。

orchestra 的职责不是提高 worker 的局部编码能力，而是在项目决策边界重新回答：

```text
项目现在真实处于什么状态？
项目为什么仍未成立？
当前路线是否仍然值得继续？
下一项任务应让项目发生什么变化？
什么时候应该继续、改向、回退、等待或停止？
```

## 2. 首版只讨论一对一关系

首版固定只有：

```text
一个 orchestra
一个当前活动 worker
一个当前明确任务
```

一对一不表示 orchestra 持续盯住 worker。orchestra 只在项目决策边界出现，worker 在当前任务内保持完整自治。

worker 可以使用自身已有的子代理系统。它如何并行调查、拆分实现和整合结果，不属于 orchestra 的管理范围。

首版不讨论：

- 同时运行多个外层 worker；
- 识别低耦合并行任务；
- worker 之间的消息和共享状态；
- 多工作区写入和合并；
- 动态扩容、暂停和回收 worker；
- 多 worker 的集成责任；
- orchestra 自己维护长期子代理团队。

这些能力即使未来需要，也必须作为独立研究线逐项调试，不能被当成首版天然应有的功能。

## 3. 角色边界

### 3.1 人类

人类提供：

- 长期意图；
- 关键成功体验和可观察结果；
- 产品、安全和外部协议边界；
- 后续重大方向变化；
- 事实无法裁决的价值选择。

人类不负责持续决定每个局部下一步，也不需要阅读 worker 的完整执行过程。

首版调试期间，人类临时承担判断基准：指出 orchestra 漏掉的关键事实、错误路线和不合适的任务边界。该职责用于校准设计，不应成为最终系统的长期依赖。

### 3.2 orchestra

orchestra 只负责任务之间的项目级判断：

- 重新确认当前人类意图；
- 独立检查与战略判断相关的项目事实；
- 判断上一项任务是否真正推动项目；
- 判断当前路线和承重假设是否仍然成立；
- 选择下一项有项目意义的明确任务；
- 决定继续、调整、回退、等待、询问人类或停止；
- 更新精简项目状态并生成 worker 推进说明。

orchestra 不负责任务内部实现，不接管普通错误修复，不管理 worker 内部子代理。

### 3.3 worker

worker 接收一个相对完整、有限、可验证的推进说明，并完整负责：

- 理解代码和任务；
- 形成局部方案；
- 自行拆分工作；
- 调用内部子代理；
- 编码、测试和修复；
- 返回可验证结果和可能影响项目方向的新事实。

worker 不需要向 orchestra 上报普通局部计划、命令历史、每次测试失败和内部子代理对话。

### 3.4 外层程序

首版外层程序只负责：

- 启动全新的 orchestra 会话；
- 启动或恢复当前 worker 会话；
- 投递人类消息、任务结果和证据引用；
- 管理基本进程、权限、预算和取消；
- 保存一份精简项目状态材料；
- 由人类或简单规则显式触发项目决策边界。

外层程序不判断下一步，不拆任务，不建立执行图和校验流程。

## 4. 运行方式

### 4.1 orchestra 跨决策轮不继承会话

每次项目决策边界到来时：

- 创建新的 orchestra 会话；
- 不恢复上一轮 orchestra 对话；
- 不携带旧助手消息、工具记录和推理链；
- 不把上一轮计划和辩护重新塞回请求；
- 从当前项目状态和本轮新增事实重新组装上下文。

长期存在的是项目状态和 orchestra 的责任，不是一条长期模型会话。

### 4.2 单次决策轮内允许完整代理循环

全新会话不等于单次分类调用。一个决策轮内，orchestra 可以：

- 阅读项目状态；
- 检查与当前判断相关的代码和差异；
- 运行产品、测试或关键实验；
- 查看最近 worker 产物；
- 比较少量候选方向；
- 形成下一项任务、继续判断或停止判断。

orchestra 默认只读取和检查项目，不修改业务代码。否则它会逐渐成为第二个 worker。它只修改项目状态材料和推进说明。

首版不要求 orchestra 调用额外子代理。先把单个战略代理的上下文和判断边界调通，避免引入新的混杂问题。

### 4.3 worker 会话绑定当前任务，而不是整个项目

worker 会话的连续性应服务于一个明确任务：

```text
同一任务仍在调查、实现、测试或修复
→ 恢复原 worker 会话

orchestra 只是补充证据、澄清边界或要求继续同一任务
→ 恢复原 worker 会话

orchestra 选择了目标、承重假设或完成标准实质不同的新任务
→ 默认启动新的 worker 会话
```

这不是需要首版通过对照实验决定的变量，而是角色边界本身：成熟 worker 负责把一个明确任务做完整，项目长期连续性不应继续寄生在 worker 会话中。

首版任何时刻仍然只有一个活动 worker。新的 worker 会话启动后，旧会话只作为可查询材料保留，不继续承担项目判断。

任务边界无法判断时，优先问：

```text
新的推进说明是否仍要求 worker 完成同一个可观察结果？
主要承重假设和自主决策范围是否仍然相同？
旧会话中的局部代码理解是否仍直接有用？
```

若答案大体为是，可以继续原会话；若项目方向已被重新解释，应开启新会话，避免旧目标继续污染执行。

### 4.4 全新 orchestra 不等于放弃前缀缓存

不能复用的是旧模型生成的对话和策略叙事，不是所有稳定输入。

稳定的职责说明、人类长期意图和硬边界仍可作为固定请求前缀。每轮变化的项目事实、任务结果和证据放在动态部分。

## 5. 持久项目状态

持久项目状态只服务于下一次 orchestra 判断。它不是完整历史，不是冻结合同，也不是新的运行时数据库。

本节列出的是 orchestra 需要考虑的信息类别，不是首版固定字段、固定章节或可校验结构。

首版最多使用一份可整体重写的自由格式 Markdown 文档，并遵守：

- 整体覆盖更新，不追加运行日志；
- 不做字段校验；
- 不做版本协议；
- 不做迁移；
- 不做新旧格式兼容；
- 不做自动合并或修复；
- 不要求 worker 读取或维护该文档；
- Git 只负责普通历史追溯；
- 任何内容都可以直接改写或删除。

如果这份状态材料开始产生自己的结构兼容、迁移、恢复或校验责任，应立即收缩，而不是继续建设配套机制。

### 5.1 人类意图

保留：

- 长期目的；
- 当前重大方向；
- 可观察成功结果；
- 真实约束；
- 已确认的非目标；
- 后续明确修改和撤回。

worker 或 orchestra 自己建立的机制不能反向扩张人类意图。

### 5.2 已确认的项目事实

只保留会影响项目方向的事实：

- 当前真正可运行的端到端能力；
- 已验证的用户流程；
- 当前真实失败和阻塞；
- 已形成的外部协议或数据承诺；
- 已集成结果与仍然孤立的产物；
- 对应的代码版本、测试、日志或运行结果引用。

代码和 Git 可直接恢复的普通细节不重复抄写。

### 5.3 承重假设

只保留一旦错误会改变后续路线的项目级假设：

```text
假设
当前依据
什么事实会证明它失效
```

承重假设不是事实，也不是上一轮推理历史。

### 5.4 当前收敛缺口

保留 orchestra 当前对“项目为什么还没有成立”的精简解释，例如：

- 核心能力尚未形成端到端闭环；
- 两个已有能力尚未集成；
- 关键协议语义仍不明确；
- 缺少判断真实失败所需的反馈；
- 当前路线局部持续成功，但没有减少项目级风险。

它不是代码待办列表，可以随新证据直接改写或删除。

### 5.5 精简结果和已停止路线

重要任务只保留：

- 原本想产生什么项目变化；
- 实际产生了什么可验证变化；
- 哪个承重假设成立、失败或仍未知；
- 当前路线应继续、调整还是停止。

只有成本较高且未来容易重复的失败路线，才保留原假设、反证和停止结论。普通局部失败不进入长期状态。

### 5.6 待人类决定事项

只保留真正属于产品方向、外部承诺、不可逆风险或价值取舍的问题。

### 5.7 当前决定残留

上一轮决定最多保留：

```text
当前方向
依赖的承重假设
预期信号
明确失效条件
尚未解决的风险
```

这不是决策账本，也不是要求下一轮继续维护旧路线的理由。

## 6. 事实、判断和决定必须分开

全新 orchestra 只有在输入没有把旧判断伪装成事实时才真正有意义。项目状态在语义上应区分：

```text
人类意图
已观察事实
当前推断
承重假设
当前决定
开放的不确定性
```

不要求首版建立对应字段，但组织材料时必须保留这些边界。

worker 的总结也不能直接变成项目事实。它只是线索；涉及项目方向的结论应由 orchestra 结合代码、测试、运行结果或人类输入核实。

## 7. 最小充分上下文

每次 orchestra 决策轮的输入由四部分组成：

```text
稳定前缀
  orchestra 职责、人类长期意图、硬边界、输出要求

当前项目状态
  已确认事实、承重假设、收敛缺口、当前决定残留

本轮变化
  最近任务结果、人类变化、外部变化

按需证据
  与本轮判断直接相关的代码、差异、测试、日志和运行结果
```

不直接拼接上一轮 orchestra 对话，也不全量复制 worker 对话。

首版需要重点调试的不是上下文越少越好，而是哪些内容对于项目级判断是必要的，哪些内容只会把 orchestra 拉回旧路线。

### 7.1 两段式揭示不是首版固定流程

候选做法是：

```text
第一段：先看当前事实和原始证据，不看旧策略与 worker 建议
第二段：再看精简决定残留、停止路线和 worker 解释，校正初步判断
```

它有合理动机，但先作为上下文设计的后续选项，不写成首版强制流程。只有实际运行表明它稳定减少锚定，才考虑采用。

## 8. 项目决策边界

orchestra 不常驻，也不检查每个 worker 动作。典型触发：

- 当前任务完成，并产生可能改变下一步的结果；
- worker 确认阻塞或承重假设失效；
- 人类发来重大方向变化；
- 关键实验或外部事件产生结果；
- 连续执行没有产生实质项目变化；
- worker 建议继续加固同一内部机制；
- 即将投入大规模或不可逆路线；
- 项目可能已经达到长期目标。

普通测试失败、局部实现选择、worker 内部子代理调度和普通提交不触发 orchestra。

首版不自动判断所有边界。先由人工主会话或简单脚本显式触发，观察哪些触发过早、哪些触发过晚，再决定是否需要自动化。

## 9. 单次 orchestra 决策轮

### 第一步：重新确认人类意图

回答：

- 人类最终需要什么项目结果？
- 当前重大方向和外部边界是什么？
- 哪些目标来自人类，哪些只是代理自建结构？

### 第二步：检查项目现实

独立检查：

- 当前真正能运行什么；
- 哪些端到端结果已经验证；
- 上一任务实际改变了什么；
- 当前主要收敛缺口是什么；
- 原路线依赖的承重假设是否仍成立。

### 第三步：生成少量候选动作

候选可以是：

- 继续当前任务；
- 调整当前任务边界；
- 结束当前路线并选择新任务；
- 做一个有限判别实验；
- 建立当前确实缺失的反馈能力；
- 等待真实外部依赖；
- 请求人类；
- 停止项目。

不生成完整长期路线图。

### 第四步：只选择一个当前任务

首版始终只维护一个当前任务。即使发现多个可能方向，也只选择当前最值得推进的一项，或先做能够区分方向的有限实验。

如果决定继续同一任务，恢复原 worker 会话；如果选择实质不同的新任务，默认启动新的 worker 会话。

### 第五步：更新项目状态并下发任务

只写回：

- 新增或失效的关键事实；
- 新增、修正或失效的承重假设；
- 新增、关闭或重写的收敛缺口；
- 当前决定及其失效条件；
- 待人类决定事项；
- 下一次 orchestra 唤醒条件。

然后生成 worker 推进说明并结束本次 orchestra 会话。

## 10. worker 推进说明

推进说明应短而完整：

```markdown
## 期望项目变化
本任务希望让项目现实发生什么变化

## 为什么现在做
为什么这是当前最有价值的一步

## 相关事实
与本任务相关的已确认事实和证据引用

## 当前工作假设
允许 worker 使用的承重假设及其失效信号

## 自主决策范围
worker 可以自主决定的实现范围

## 必须保留
已有能力和真实约束

## 所需证据
完成后需要返回的可复核结果

## 何时提前上报
哪些项目级变化需要在任务完成前通知 orchestra
```

不规定文件、类、实现步骤、子代理数量、测试写法或局部评审流程。

首版需要重点观察推进说明的粒度：过细会重复 worker 的规划能力，过粗则无法把项目级判断落实成可执行任务。

## 11. 什么算有效项目变化

下一项任务必须有项目级因果依据，但不要求每一轮都立刻产生用户可见界面或功能。

合法变化包括：

- 新增用户可观察能力；
- 修复真实端到端失败；
- 集成已经孤立存在的能力；
- 消除一个承重不确定性；
- 建立后续判断必需且当前确实缺失的反馈能力；
- 降低已确认的不可逆风险；
- 删除或停止已经被事实证明无价值的路线。

不能单独成为新任务理由：

- 代码已经存在这个结构；
- 已有测试覆盖它；
- 上一轮留下待办；
- 继续完善会更严谨；
- 已投入很多时间或计算量；
- 新机制自身又产生迁移、兼容、恢复或审计责任。

反事实检查：

> **即使不考虑这个机制已经存在，它是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不把继续完善该机制自动升级为项目目标。

## 12. 首版不是验证实验，而是工程调试

首版不需要人为设计一个同时包含所有失败模式的项目演示，也不需要把“有 orchestra”和“无 orchestra”做成形式化胜负对照。

原因很直接：单 worker 长期自我维持远大目标会发生视野涣散，已经是本项目的出发事实。当前真正未知的是 orchestra 具体怎样工作才不会产生新的问题。

首版直接在真实项目的自然决策边界运行，每次只处理一个实际问题，并围绕以下内容反复调试：

### 12.1 上下文是否充分

- orchestra 能否从精简材料恢复当前项目局面？
- 哪些项目事实必须直接提供？
- 哪些内容只需要给出引用，按需读取？
- 是否必须保留承重假设和已停止路线？
- worker 总结会提供有效线索，还是造成新的锚定？

### 12.2 检查深度是否合适

- orchestra 只看项目状态是否会过度依赖摘要？
- 每轮全量阅读仓库是否会退化成第二个 worker？
- 哪些承重事实值得亲自运行或检查？
- 怎样限制一次决策轮的调查范围？

### 12.3 决策边界是否合适

- 每个任务结束都唤醒是否过于频繁？
- 等到多个任务后再唤醒是否已经太晚？
- 哪些 worker 信号真正代表项目级变化？
- 哪些只是任务内部噪声？

### 12.4 推进说明是否能有效纠偏

- worker 能否理解 orchestra 给出的项目级方向？
- 同一任务中的 worker 会话能否接受边界澄清？
- 新任务是否应该使用新 worker 会话？
- 推进说明是否过细、过粗或包含过多旧叙事？
- worker 返回的材料是否足以支持下一次全新判断？

### 12.5 项目状态是否能长期保持轻量

- 状态是否持续贴近真实项目？
- 是否开始堆积过时结论？
- 是否出现固定字段、兼容和迁移冲动？
- 全新的 orchestra 是否频繁重做已证伪路线？
- 不继承旧推理后，是否出现随机摇摆？

## 13. 首版落地方式

### 13.1 直接接入真实项目

首版不先构造专门 demo。选择一个正在真实推进、且人类已经理解其长期方向的项目，在自然决策边界运行 orchestra。

初期可以由人类保留最终决定权：

```text
真实任务产生结果
→ 全新的 orchestra 独立检查并给出下一项任务
→ 人类只检查是否遗漏关键事实或明显偏离方向
→ 接受、轻微修正或否决
→ worker 执行实际任务
```

这不是为了比较人类和 orchestra 谁得分更高，而是快速暴露：上下文缺了什么、orchestra 被什么误导、任务边界是否错误。

随着错误类型稳定减少，人类逐渐只在重大方向、不可逆风险和价值选择时介入。

### 13.2 历史快照只作为回归材料

Hermes 旧运行时内核中的典型失焦点可以保留为少量回归材料，例如：

- 应停止继续完善自建运行时机制；
- 当前路线已经远离原始产品目标；
- 某个承重假设已被现实推翻；
- 下一步应回到端到端能力，而不是补内部一致性。

这些快照用于在修改提示词或项目状态内容后检查是否重新出现旧错误，不用于证明 orchestra 必要，也不要求覆盖所有设计点。

### 13.3 每次只调整一个主要设计变量

一次调试中不要同时更换：

- orchestra 模型；
- worker 模型；
- 项目状态内容；
- 上下文揭示方式；
- 推进说明结构；
- 决策边界规则；
- worker 会话边界。

否则无法判断错误来自哪里。

### 13.4 调试记录与项目状态分开

项目状态只保存当前有效认识，应整体重写。

调试过程可以另行记录：

- orchestra 输入；
- orchestra 输出；
- 人类修正；
- worker 最终结果；
- 本轮暴露的错误类型；
- 模型成本和耗时。

这些记录只是研发材料，不进入下一次 orchestra 的默认上下文，也不升级成运行时事实源。

## 14. 首版最小实现

首版只需要：

```text
一份可整体重写的自由格式项目状态材料
一个启动全新 orchestra 的脚本或人工主会话
一个当前活动的 Codex 或 Claude Code worker
少量代码、测试、日志和任务结果引用
人工显式触发的项目决策边界
```

单次 orchestra 只做：

1. 检查必要事实；
2. 判断当前项目缺口和路线；
3. 选择继续同一任务或启动一个新任务；
4. 写一份短推进说明；
5. 整体更新项目状态材料；
6. 结束会话。

首版不需要：

- 状态数据库；
- 固定字段解析器；
- 决策结构定义；
- 状态校验器；
- 自动上下文组装器；
- 自动边界检测；
- 两段式提示词；
- 反证代理；
- 多 worker；
- 独立评审流水线；
- 正式对照基准。

## 15. 首版判断标准

首版不是通过一次最终演示判定成功或失败，而是看实际运行中是否逐渐出现以下结果：

- 全新的 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要把完整历史和完整 worker 对话重新塞入上下文；
- 能识别已失效假设和代理自建工作；
- 能提出粒度合适、具有项目意义的下一项任务；
- worker 能依据推进说明完成明确任务或改变旧方向；
- 新任务不再继承无关的旧 worker 叙事；
- 不因全新会话而频繁随机反转；
- 项目状态保持短、可改写、没有形成新协议；
- 人类在项目决策边界需要做的纠偏逐渐减少；
- 项目持续产生有效项目变化，而不是继续维护代理自建机制。

若持续出现以下情况，说明当前设计需要修正：

- 人类每轮仍需重新讲解整个项目；
- orchestra 只是复述 worker 的总结；
- 缺少完整历史就无法作出稳定判断；
- 为避免摇摆开始保存越来越多旧推理；
- 项目状态长成字段、校验、迁移和兼容系统；
- orchestra 过度阅读和修改代码，成为第二个 worker；
- 新任务仍被旧 worker 会话中的目标和结构绑架；
- 人类纠偏没有减少。

这些结果首先用于定位上下文、边界或接口问题，不急于推导 orchestra 整体无效。

## 16. 后续独立研究

以下问题不属于首版，只有一对一结构稳定后才单独研究。

### 16.1 两段式上下文

比较一次性输入与先看事实、后看精简历史，确认它是否稳定减少锚定，而不是只增加调用成本。

### 16.2 自动决策边界

研究如何从 worker 结果、外部事件和项目状态中自动判断何时唤醒 orchestra。

### 16.3 worker 会话策略细化

首版采用“同一任务继续，新任务默认新会话”的简单边界。后续可以研究哪些自然延续任务值得复用旧会话，以及何时应主动丢弃已经退化的会话。

### 16.4 多 worker

多 worker 至少包含：

- 如何判断两个任务是否适合并行；
- 如何管理独立工作区；
- 如何处理共享边界变化；
- 如何决定合并、暂停和取消；
- 谁承担最终集成责任；
- 并行收益是否大于协调成本。

多 worker 是独立且复杂的研究线，不能从一对一结构直接推导，也不能作为首版演示功能。

## 17. 首版明确非目标

首版不建设：

- 用对照实验再次证明单 worker 长期会漂移；
- 用一个综合项目演示证明完整体系优越；
- 多 worker 调度和管理；
- 外层任务并行；
- worker 登记系统；
- 多工作区合并机制；
- worker 间通信层；
- 固定角色团队；
- orchestra 长期子代理团队；
- 完整路线图冻结；
- 目标合同、进展账本和执行图；
- 图修订校验器；
- 检查点、快照和压缩系统；
- 复杂产物关系追踪；
- 自动负向评审或清理；
- 持久推理历史。

首版的任务只是把一对一 orchestra 的上下文、决策边界、worker 任务边界和推进说明调通。只有实际运行暴露出明确缺口时，才增加对应的最小能力。
