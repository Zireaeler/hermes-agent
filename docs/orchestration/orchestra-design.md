# Orchestra 层方向说明

## 0. 当前结论

三次实验已经结束。当前没有证据支持建设 Orchestra Runtime、自动负向 review 系统或新的多节点协调基础设施。

实验得到的最终结论是：

- 负向 review 可以发现真实问题，也可以做有用的局部 cleanup；
- 普通独立 review 同样能发现真实问题；
- 前两次实验中负向组成品维护更快，但结果与第一次 review 前的实现和项目内测试分叉高度重合；
- 第三次从完全相同的 R1–R3 基线分组后，负向 review 没有表现出稳定净维护收益，主轨迹反而更慢、更贵；
- 代码更少本身没有稳定转化为更低维护成本。

因此，“专门增加一个负向判断者来抑制结构增长”不是已经成立的 Orchestra 核心能力。该方向停止。

仍然需要讨论的问题是：在完整 Worker 之外，是否存在少量真正属于长周期外层的职责。这个问题尚未验证，不能直接扩建成 Runtime。

## 1. 原始问题仍然存在

连续 coding agent 很容易一条需求接一条需求地推进，但可能形成自我强化增长：

```text
Agent 为提高信心增加辅助机制
→ 机制产生 schema、测试、迁移、恢复、文档和验证责任
→ 后续 Agent 把这些自身产物当成独立需求
→ cleanup 继续保留或替换没有真实使用方的机制
```

Hermes Runtime Kernel 的历史说明：更多 phase、节点、artifact、事件和验证流程不代表更高质量，协调成本可能远高于业务实现。

解决这个问题最有效的当前手段不是 Orchestra，而是直接工作规则：

- 用户当前可观察结果优先；
- Agent 自建产物不能反过来成为新需求；
- 没有真实消费者、故障或边界时不增加机制；
- 一次性验证不升级成永久 gate；
- 内部未发布结构默认可直接修改或删除；
- 达到验收条件立即停止。

这些规则已经写入全局 `/root/.codex/AGENTS.md`，Claude Code 通过 `/root/.claude/CLAUDE.md` 读取。它们不需要被包装成新的运行时系统。

## 2. 三次实验结果

### 2.1 第一对：本地 scheduler

两组从空目录独立完成 R1–R7，在 R3、R5、R7 review。

结果：

- 两组能力测试均通过；
- 负向组两个维护任务合计 wall time 少约 38%，成本少约 56%；
- 但两组从 R1 起选择了不同存储架构；
- 普通组从早期开始生成并维护大量项目内测试，负向组没有。

结果有明显混杂，不能归因于 review。

协议与结果见 `cheap-experiment.md`。

### 2.2 第二对：JSON 决策规则解释器

换成完全确定、无持久状态、无时间和无并发的问题。

结果：

- 两组公开和隐藏能力测试均通过；
- 负向组两个维护任务合计 wall time 少约 37%，成本少约 35%；
- 两组最终实现文件本身几乎同规模；
- 普通组在第一次 review 前就生成了 907 行项目内测试，负向组仍没有项目内测试；
- 普通维护 agent 的额外工作主要是同步修改和删除这些测试。

相同混杂再次出现。负向 review 本身没有造成测试差异。

协议与结果见 `rule-interpreter-experiment.md`。

### 2.3 第三次：受控库存 CLI

共同 Worker 完成 R1–R3，然后在 Review 1 前复制完全相同的代码、测试和存储格式。两组复制点 SHA256 相同，均无项目内测试。

结果：

- 两组 R1–R7 和最终有效隐藏行为均通过；
- 负向组 treatment 主轨迹 wall time 高约 7%，成本高约 17%；
- 最终负向组代码少约 9%；
- 新增盘点批次维护任务两组因相同 CLI 误解而失败；
- 删除预留维护任务两组均成功，成本基本相同。

消除 treatment 前混杂后，没有复现负向 review 的显著维护优势。

协议与结果见 `controlled-stockroom-experiment.md`。

## 3. 已经排除的 Orchestra 职责

当前不应让 Orchestra 承担以下职责。

### 3.1 不做 Worker 的外部 planner/coder/tester

Codex、Claude Code 等完整 Worker 已经能够：

- 阅读项目；
- 制定局部实现方案；
- 修改代码；
- 运行测试；
- 调用内部子代理；
- 根据错误继续修复。

外层再拆 planner、coder、tester、reviewer 会重复 Worker 能力，并增加 handoff 和上下文损耗。

### 3.2 不做每轮强制 review

三次实验没有证明额外负向 review 有稳定净收益。Review 可以按真实风险或用户要求一次性调用，但不应成为每轮永久节点。

### 3.3 不做结构复杂度治理系统

不建设：

- concept surface；
- dependency surface；
- 类数、实体数或 LOC gate；
- schema/contract 审批；
- cleanup 状态机；
- 结构健康 ledger。

实际维护任务比这些代理指标更可靠，但即使维护评估也不应变成所有项目的永久流程。

### 3.4 不重复管理 Worker 内部子代理

外层不规定 Worker 必须启动多少 agent、如何拆角色或怎样投票。子代理数量不是成功指标。

### 3.5 不建设长期证据和恢复协议

不建设 review ledger、snapshot、artifact lineage、decision session、checkpoint、seal、hash 链、恢复协调或节点通信协议。

Git、现有代码、用户需求、测试和 provider 已经承担大量事实记录与恢复能力。没有确认缺口时不得建设第二套。

## 4. Worker 与外层的边界

### Human

Human 提供：

- 项目意图；
- 当前可观察结果；
- 真实不可越过边界；
- 少数无法由事实裁决的方向选择。

Human 不应持续监管实现细节。

### Worker

Worker 是完整 coding agent。一个连贯任务应由一个 Worker 从理解到验证完成，而不是被外层拆碎。

Worker 自己决定：

- 如何搜索和理解代码；
- 是否需要规划；
- 是否使用内部子代理；
- 如何实现和测试；
- 在当前需求范围内如何修复失败。

### 外层代码

代码只保护可明确表达的真实边界：

- 凭证和权限；
- 不可逆或破坏性操作；
- 已发布数据和外部协议；
- 明确预算上限；
- 基本数据完整性；
- 用户明确要求的调度和超时。

代码不通过不断增加 validator、状态和流程来代替语义判断。

## 5. 可能仍属于 Orchestra 的残余职责

以下职责在逻辑上可能位于单个 Worker 之外，但尚未通过实验验证。

### 5.1 在多个用户目标之间选择“下一件事”

当系统面对的不是一个明确任务，而是多个待办、外部事件或互相竞争的项目目标时，需要决定：

- 当前最值得推进哪一项；
- 哪一项已经失去价值；
- 哪一项依赖尚未满足；
- 是否应该停止继续投入。

这是 portfolio/goal selection，不是单个 coding task 的实现规划。

如果用户已经明确指定当前任务，这项职责不存在，Orchestra 应该退出，让 Worker 直接执行。

### 5.2 在独立 Worker turn 之间保持用户意图

长周期项目可能跨多个独立会话。外层需要确保下一次交给 Worker 的仍是用户当前目标，而不是此前 Agent 自己生成的路线。

最小形式可以只是当前用户目标和验收条件，不需要 decision ledger、历史辩护或复杂持久状态。

### 5.3 判断是否需要 Human

只有真正属于用户的决定才升级给 Human，例如：

- 多个产品方向都合理且测试无法裁决；
- 需要新增真实外部承诺；
- 涉及不可逆数据或发布边界；
- 当前目标本身发生冲突。

实现细节、普通 bug、测试失败和内部结构选择不应升级。

### 5.4 停止、取消或不再继续

长周期自动循环最容易缺失的是停止能力。外层可以依据明确事实停止：

- 已达到用户验收条件；
- 当前任务已无剩余可观察结果；
- 真实依赖未满足；
- 预算上限已到；
- 用户取消；
- 连续没有实质进展。

停止不需要建立复杂的“停止决策系统”。满足条件后直接不再产生下一个 Worker turn。

### 5.5 触发一次独立外部核实

当任务有明确黑盒结果、发布边界或高成本回归时，外层可以调用一次独立核实者检查当前事实，而不是信任 Worker 自述。

核实者是一次性工具调用，不是永久节点。普通项目不默认需要第二次 review。

## 6. Orchestra 的最小可能形态

如果将来确实需要这一层，它首先应当是薄的控制逻辑，而不是 Runtime：

```text
读取 Human 当前目标
→ 判断是否已经有明确的单一任务
→ 有：交给一个完整 Worker
→ Worker 完成后检查可观察验收结果
→ 已完成：停止
→ 未完成且需求明确：继续同一目标
→ 出现真正方向选择或不可逆边界：询问 Human
```

它不需要默认拥有：

- 多 agent 团队；
- 持久化节点状态；
- 自定义事件协议；
- review 流水线；
- 长期判断记忆；
- 结构复杂度模型；
- 自动 cleanup。

在多数单任务场景中，这个“Orchestra”应退化为零：Human 直接把任务交给完整 Worker，Worker 完成后停止。

## 7. 下一步讨论问题

实验已经回答“负向 review 是否应成为 Orchestra 核心能力”：当前答案是否定的。

后续若继续讨论 Orchestra，只讨论仍未被 Worker 或 harness 覆盖的外层问题：

1. 实际系统是否真的存在多个竞争目标，需要外层选择下一项？
2. 跨会话时，哪些最小用户意图必须保留？
3. 哪些停止条件无法由当前 harness 和 Worker 直接处理？
4. 哪些决定确实必须升级给 Human？
5. 一次独立核实在什么真实风险下值得成本？

在出现具体使用场景前，不实现代码。先从真实长周期任务中找出一个 Worker 或现有 harness 无法处理的缺口，再决定是否存在最小 Orchestra 职责。

## 8. 当前停止条件

当前实验方向已结束。

不新增：

- Orchestra 数据库或状态机；
- decision schema、session 或 ledger；
- checkpoint、snapshot 或 compaction；
- review/cleanup 自动节点；
- 节点通信协议；
- 外层 subagent manager；
- 结构复杂度 gate。

除非未来出现一个独立于这些机制自身、由真实用户目标或运行故障证明的外层缺口，否则 Orchestra 保持为文档中的待讨论边界，不进入实现。
