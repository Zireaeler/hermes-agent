# orchestra 设计：间歇式项目战略层

## 0. 顶层定义

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮都从当前人类意图、项目状态、本轮事实变化和按需证据重新组装最小充分上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承对话历史、推理过程和旧策略叙事。长期存在的是 orchestra 的项目责任与持久项目状态，不是一条长期模型会话。**

架构原则：

> **连续性属于项目状态，推理属于单次决策轮；局部执行连续性属于推进面内的 worker。**

整体结构：

```text
人类
  │  长期意图、重大方向、价值取舍
  ▼
全新的 orchestra 决策轮
  │  项目级观察、路线判断、推进面调整
  ▼
弹性 worker 集合：1..N
  ├─ Codex / Claude Code worker A
  │    └─ worker 自己的子代理系统
  ├─ Codex / Claude Code worker B
  │    └─ worker 自己的子代理系统
  └─ ...
```

默认只有一个完整 worker。只有项目自然形成两个或更多低协调耦合、可独立维持局部决策循环的推进面时，orchestra 才扩展为多个 worker。

本文档是一版待验证设计，不是已批准实现的运行时规范。第一版优先使用 Hermes 已有能力、普通项目文件和独立代理会话进行手工实验，不先建设新的数据库、状态机或协议层。

### 0.1 术语

`决策轮`：一次全新的 orchestra 会话，从读取当前项目状态开始，到写回新的项目判断和调度结果结束。

`项目决策边界`：出现足以改变项目方向、推进面关系、重大假设或停止判断的新事实。它不是固定阶段，也不是每次 worker 交互。

`推进面`：一个成熟 worker 可以连续占有并完整推进的项目工作面。worker 在其中自行理解代码、规划、调用子代理、实现、测试和修复。

`项目状态`：orchestra 为了判断“项目现在应推进什么”而持有的当前项目级认识。它不是完整仓库摘要，不是历史对话，也不是冻结合同。

## 1. 为什么完整 worker 仍然不够

完整的 Claude Code 或 Codex worker 能很好地完成一个明确、有限、可验证的工程任务。它可以自行：

- 阅读项目；
- 制定局部方案；
- 使用内部子代理；
- 编码和测试；
- 修复当前失败；
- 做必要的局部重构；
- 在一个明确目标内完成并行拆分和结果整合。

因此 orchestra 不应再次把同一个明确目标拆成规划者、编码者、测试者和评审者，也不应把文件级任务分给多个外层 worker。

但一个 worker 能完成明确任务，不等于它适合长期管理自己形成的项目路线。Hermes 过去的实际循环是：

```text
人类给出远大目标
→ worker 从当前代码选择下一步
→ worker 实现并测试
→ worker 从刚建立的结构中选择下一步
→ 继续修补、加固和兼容该结构
```

这容易形成自指视野：

```text
上一轮创建的机制
→ 成为下一轮最显眼的问题
→ worker 继续补一致性、恢复和兼容
→ 新机制产生更多局部责任
→ 原始产品目标逐渐退出注意力中心
```

每个局部任务都可能正确完成，但整个项目没有产生新的端到端能力，没有消除关键不确定性，也没有更接近可交付状态。

orchestra 的必要性来自这个项目级视野缺口，而不是 worker 不会实现代码。

## 2. 旧运行时内核与评审实验分别说明了什么

旧运行时内核做对了一件重要的事：项目级连续性不能寄生在任一 worker 会话中，项目事实、全局判断和 worker 局部执行上下文应当分离。

它的问题是把项目推进过度形式化为目标合同、进展账本、目标缺口、执行图、图修订和校验器。系统随后逐渐从“推进项目”转向“维护自身运行时机制的一致性”。因此本设计保留项目级独立上下文，不继承旧内核的合同、账本、图修订和恢复协议。

三次评审实验验证的是一个更窄的问题：额外负向评审是否能稳定降低一个明确任务的后续维护成本。最终受控实验没有证明稳定净收益。因此：

- 负向清理不是 orchestra 的核心能力；
- 不建立固定评审节点；
- 不建立规划、编码、测试、评审流水线；
- 不用代码行数、实体数或复杂度门槛管理路线；
- 不介入成熟 worker 的推进面内部执行循环。

但这些实验没有覆盖长期路线选择、多个低耦合推进面、承重假设失效、需求变化和 worker 拓扑调整。因此它们不能否定项目级 orchestra。

实验归档：

- `cheap-experiment.md`
- `rule-interpreter-experiment.md`
- `controlled-stockroom-experiment.md`
- `deep-review-prompt.md`

## 3. 角色边界

### 3.1 人类

人类提供：

- 长期意图；
- 关键成功体验和可观察结果；
- 产品、安全和外部协议边界；
- 后续重大方向变化；
- 事实无法裁决的价值选择。

人类不负责：

- 持续决定每个局部下一步；
- 阅读每个 worker 交互；
- 判断 worker 是否陷入局部视野循环；
- 为 worker 编写详细实现计划；
- 在多个成熟 worker 之间做日常协调。

### 3.2 orchestra

orchestra 负责项目级战略决策轮：

- 从当前人类意图重新确认项目目的；
- 基于证据更新当前项目状态；
- 判断项目为什么仍未收敛；
- 选择、继续、调整、暂停或终止推进面；
- 判断是否存在真正可独立推进的多个工作面；
- 在协调耦合升高时收缩并行、合并或串行化推进面；
- 识别局部自洽但整体停滞的路线；
- 决定何时请求人类、等待或停止；
- 写回精简的项目状态变化和当前调度结果。

orchestra 不负责推进面内部实现，也不管理 worker 内部子代理。

### 3.3 worker

worker 接收一个有意义、相对完整、可验证的推进说明，并在该工作面内完整自治：

- 理解目标和代码；
- 决定实现策略；
- 自行拆任务；
- 调用内部子代理；
- 编码、测试和修复；
- 做工作面内必要重构；
- 返回可验证产物和会影响项目级判断的新事实。

worker 不需要把普通局部计划、命令历史、每次失败和内部子代理对话上报给 orchestra。

### 3.4 外层程序

外层程序只处理机械边界：

- 代理会话、进程和工作区生命周期；
- 人类消息和外部事件投递；
- worker 运行与推进面的映射；
- 隔离环境、权限、凭证和不可逆操作边界；
- 硬预算、超时、取消和进程恢复；
- Git、持续集成、测试、运行结果和 worker 产物的引用；
- 在项目决策边界唤醒新的 orchestra 决策轮。

外层程序不判断项目应做什么，不按固定规则拆任务，不用校验器替代战略判断。

## 4. 间歇式运行形态

### 4.1 跨决策轮不继承会话

每次 orchestra 在项目决策边界被唤醒时：

- 创建新的代理会话；
- 不恢复上一轮 orchestra 对话；
- 不携带旧助手消息、工具记录或推理链；
- 不把上一轮计划和辩护重新伪装成当前事实；
- 从持久项目状态、本轮变化和按需证据重新组装请求体。

这样避免 orchestra 自己成为第二个长期维护旧路线叙事的 worker。

### 4.2 单次决策轮内允许完整代理循环

全新会话不等于单次分类调用。一个决策轮内可以：

1. 读取当前人类意图和项目状态；
2. 检查与本轮战略判断直接相关的 Git、代码和产物；
3. 运行产品、测试或关键实验；
4. 调用少量临时探索代理；
5. 比较候选项目推进方向；
6. 读取精简历史残留并进行校正；
7. 决定推进面关系和下一步；
8. 写回项目状态变化和推进说明。

orchestra 不应在每次决策轮全量重新理解整个仓库。它先使用项目状态和证据引用，只对影响本轮战略判断的承重事实做按需核实。

### 4.3 全新会话不等于放弃前缀缓存

不能复用的是旧模型生成的对话和策略叙事，不是所有稳定输入。

可以保持稳定并由模型服务缓存的前缀包括：

- orchestra 职责和禁止项；
- 项目长期意图与硬边界；
- 项目状态各部分的含义；
- 输出要求。

每次变化的后缀包括：

- 当前项目状态；
- 本轮新增变化；
- 当前推进面状态；
- 本轮按需证据。

### 4.4 worker 会话按推进面连续

```text
orchestra：每个决策边界使用全新会话
worker：同一推进面内默认连续
项目状态：长期持久
```

同一推进面的目标、承重假设和共享边界仍然稳定时，默认继续原 worker 会话，以保留代码理解、调试状态和内部子代理结果。

以下情况可以启动新的 worker 会话，而不是机械恢复：

- 推进面被实质重定义；
- 承重假设被推翻；
- 共享边界发生重大变化；
- 原会话多轮没有实质项目增量；
- worker 持续维护已失效的局部叙事；
- 需要真正独立的验证或替代方向。

worker 会话是局部执行缓存，不是项目事实源。

## 5. 持久项目状态

持久项目状态提供长期连续性。它是可直接修订的当前状态，不是只追加的决策账本、冻结合同或需要长期兼容迁移的运行时结构定义。

但它也不能只保存“已核实事实”。全新的 orchestra 要避免随机摇摆，还需要知道当前承重假设、未闭合矛盾和推进面关系。项目状态至少包含以下内容。

### 5.1 人类意图

优先保留人类原话或忠实转述：

- 长期目的；
- 当前重大方向；
- 可观察成功结果；
- 真实约束；
- 后续明确修改和撤回；
- 已确认的非目标。

worker 或 orchestra 的实现不能反向扩张人类意图。

### 5.2 已确认的项目现实

只保存影响项目级判断的当前事实，例如：

- 已真实运行或验证的端到端能力；
- 已确认的用户流程；
- 生产、部署、持续集成、基准测试或用户反馈事实；
- 已形成的外部协议和数据承诺；
- 当前真实失败和阻塞；
- 哪些结果已经集成，哪些仍是孤立产物。

事实应能指向代码版本、测试、日志、运行结果或人类决定。代码和 Git 可直接恢复的普通细节不重复抄写。事实若因后续改动可能失效，应在使用时重新核实，而不是永久视为真理。

### 5.3 承重假设

保存一旦错误会使多个工作面失效的项目级假设，例如：

- 某现有抽象可以成为统一扩展边界；
- 某外部协议能够映射到统一任务语义；
- 某共享接口在多个推进面之间保持稳定；
- 当前反馈手段足以判断实现是否正确。

每个承重假设只需保留：

```text
假设 / 当前依据 / 失效信号
```

这不是推理历史，而是下一次全新决策轮必须能够检验的因果残留。

### 5.4 收敛缺口

保存 orchestra 当前对“项目为什么仍未成立”的精简解释，例如：

- 核心能力尚未形成端到端闭环；
- 两个已有能力尚未集成；
- 关键协议语义仍不明确；
- 目前无法观察真实失败模式；
- 一条路线局部持续成功，但没有减少项目级风险。

收敛缺口不是初始目标的机械拆分，也不是代码待办列表。它可以随新证据被重写、合并或删除。

### 5.5 活动推进面及其关系

每个活动推进面只保存项目级信息：

```text
希望产生的项目变化
当前 worker 会话与工作区
局部决策所有权
依赖的承重假设
与其他推进面的共享边界
何种变化必须通知 orchestra
当前是否仍可独立推进
```

不保存 worker 内部任务树、文件计划和子代理结构。

### 5.6 精简结果与已停止路线

每次重要结果只保存：

- 原本想产生什么项目变化；
- 实际产生了什么可验证变化；
- 哪个承重假设成立、失败或仍未知；
- 对当前收敛缺口和推进面关系造成什么影响。

只有实际成本较高、未来容易重复的失败路线才保留停止记录：

```text
路线 / 原假设 / 反证 / 当前结论
```

不保留所有候选路线和普通局部失败。

### 5.7 待人类决定事项

只保存真正等待人类的产品方向、外部承诺、不可逆风险或价值取舍。

### 5.8 再次唤醒条件

每次 orchestra 决策轮结束时，声明下一次值得被唤醒的条件，例如：

- 某推进面完成、阻塞或推翻承重假设；
- 某共享边界发生变化；
- 关键持续集成、实验或外部事件完成；
- 人类意图发生变化；
- 多个 worker 开始争用同一决策范围；
- 项目可能已经满足停止条件。

外层程序只负责投递事件，不解释事件意味着什么。

## 6. 事实、判断和决定必须区分

全新会话只有在输入没有把旧判断伪装成事实时才真正有意义。项目状态中的内容应在语义上区分：

```text
人类承诺
已观察事实
当前推断
承重假设
当前决定
开放的不确定性
```

不要求第一版建立正式结构定义，但文档和提示词必须保持这种边界。

上一轮决定可以保留为精简、可证伪的决定残留：

```text
当前方向
依赖的承重假设
预期应观察到的信号
明确的失效条件
仍未解决的风险
```

它不是权威，也不是辩护记录。改变方向应由新增证据、已触发的失效条件或独立检查发现的项目级矛盾驱动，而不是仅因新会话产生了不同措辞。

## 7. 不持久化什么

禁止把以下材料作为 orchestra 长期状态：

- 完整 orchestra 对话；
- 推理链；
- 旧工具调用历史；
- 所有候选路线的长篇比较；
- 上一轮 orchestra 的设计辩护；
- worker 的完整会话；
- worker 内部子代理对话；
- 每轮评审输出；
- 普通局部实现计划和失败记录；
- 已投入计算量或时间作为继续路线的理由；
- 阶段图、概念面或只追加的决策账本。

原则：

> **持久化当前项目状态和可证伪的决定残留，不持久化认知轨迹。**

## 8. 最小充分上下文组装

每次决策轮的上下文分为四层：

```text
稳定前缀
  orchestra 职责、长期意图、硬边界、输出要求

当前项目状态
  已确认现实、承重假设、收敛缺口、活动推进面

本轮变化
  自上次项目决策以来的新事实、人类变化和 worker 结果

按需证据
  本轮战略判断实际需要的代码、差异、测试、日志和运行结果
```

不直接拼接上一轮对话，也不全量复制 worker 对话。

### 8.1 两段式上下文揭示

两段式不是“先什么都不知道，再看完整历史”，而是：

```text
第一段：对旧策略和代理叙事盲，对当前事实不盲
第二段：揭示精简决定残留和解释性材料，进行校正
```

#### 第一段：对旧策略盲的独立检查

先提供：

- 当前人类意图；
- 项目状态中的事实部分；
- 当前产品和相关代码；
- 原始代码差异、测试、持续集成、日志和运行结果；
- 最近 worker 的实际产物引用。

暂不提供：

- 上一轮 orchestra 为什么选择当前路线；
- 上一轮计划和设计辩护；
- worker 对自己结果的总结性解释；
- worker 对下一步的建议；
- 已投入多少成本；
- 详细阶段历史。

orchestra 先形成并固定一个初步判断：

```text
当前真实完成了什么？
项目为什么仍未收敛？
哪些事实或假设最承重？
当前推进面应继续、暂停、合并、终止还是扩展？
如果今天首次接手，最有价值的下一项项目变化是什么？
```

第一段可以按需检查证据，但不应先读 worker 的叙事摘要。

#### 第二段：结合精简历史校正

随后只揭示：

- 上一轮决定残留；
- 承重假设及失效条件；
- 精简重要结果；
- 已停止路线；
- worker 对结果和下一步的解释。

orchestra 将第一段判断与历史残留和新增事实比较，最终选择：

```text
保留原方向
修正边界或假设
反转方向
先做有限判别实验
暂停、合并或终止推进面
扩展新的独立推进面
请求人类
停止项目
```

第二段的作用是校正，不是要求新的 orchestra 继承旧策略。

## 9. 推进面与多 worker

### 9.1 默认一个 worker

默认 `N = 1`，因为成熟 worker 在连续上下文中已经能完成一个明确目标下的内部拆解、并行调查、实现、测试和整合。

orchestra 不应把同一个完整推进面再次拆给多个外层 worker。

### 9.2 何时扩展为多个 worker

只有出现多个可独立维持局部决策循环的推进面时才扩容。判断重点不是目录是否不同，而是协调耦合是否足够低：

- 双方是否需要频繁共享局部推理；
- 一方的普通决策是否经常使另一方失效；
- 是否同时修改同一组承重抽象或共享协议；
- 是否能各自产生独立、可验证的项目变化；
- 是否只需在少数明确边界交换结果；
- 暂停其中一个时，另一个是否仍能有效推进。

适合多 worker 的典型情况：

- 多个已形成稳定边界的正交工作面；
- 两条互斥路线的独立原型，用于消除项目级不确定性；
- 主实现继续推进时，另一个 worker 独立调查外部协议或建立故障复现；
- 多仓库、部署环境或开发包之间边界已经明确的工作。

不适合多 worker 的情况：

- 只是因为任务很大；
- 多个 worker 需要持续修改同一核心抽象；
- 架构仍未形成，任务边界只是猜测；
- 工作主要依赖连续理解、调试和即时集成；
- 最终瓶颈是一个高度耦合的集成问题。

### 9.3 推进面关系动态变化

推进面关系不是预先冻结的有向图：

```text
发现独立工作面 → 新建 worker
协调耦合升高   → 暂停、合并或串行化
承重假设失效   → 调整、取消或替换会话
方向被证伪     → 关闭或丢弃对应路线
边界稳定       → 再次允许扩展
```

orchestra 管理的是项目级局部决策中心，不是文件级任务队列。

### 9.4 三类子代理或 worker 不应混淆

worker 内部子代理：服务于同一个推进面，由父 worker 即时整合，orchestra 不管理。

orchestra 决策轮内的临时探索代理：只为战略判断读取事实、比较路线或反证，不成为长期固定角色。

执行层 worker：由 orchestra 按项目级独立推进面动态配置，每个 worker 都是成熟编码代理。

## 10. 项目决策边界与触发条件

orchestra 不常驻，也不检查每个 worker 动作。典型触发：

- 某推进面产生候选项目级结果；
- 推进面确认阻塞、失效或推翻承重假设；
- 人类发来重大方向变化；
- 关键实验、持续集成或外部事件产生结果；
- 推进面之间的共享边界发生变化；
- 多个 worker 的协调耦合明显上升；
- 连续执行没有产生实质项目变化；
- worker 建议继续加固同一内部机制；
- 即将投入大规模或不可逆架构路线；
- 项目可能已经达到长期目标。

普通测试失败、局部实现选择、worker 内部子代理调度和普通提交不触发 orchestra。

## 11. 单次 orchestra 决策轮

### 第一步：重新确认人类意图

回答：

- 人类最终需要什么项目结果？
- 当前重大方向和外部边界是什么？
- 哪些目标来自人类，哪些只是代理自建结构？

### 第二步：检查当前项目现实

执行对旧策略盲的独立检查：

- 当前真正能运行什么；
- 哪些端到端结果已验证；
- 自上次决策后项目现实发生了什么变化；
- 当前主要收敛缺口和承重假设是什么；
- 活动推进面是否仍然独立有效。

### 第三步：生成少量候选推进动作

只产生少量候选项目动作，不生成完整路线图。候选可以是：

- 继续或调整现有推进面；
- 启动新的独立推进面；
- 暂停或合并高耦合推进面；
- 做一个有限判别实验；
- 建立当前确实缺失的反馈能力；
- 请求人类；
- 停止投入。

### 第四步：结合精简历史校正

揭示精简决定残留、停止路线和 worker 解释，检查初步判断是否遗漏历史反证、重复失败路线或误解当前边界。

### 第五步：选择当前推进组合

默认选择一个主要项目变化。只有存在真实低协调耦合时，才同时选择多个推进面目标。

不冻结长期路线图，只决定当前值得运行的工作面和下一次战略关注条件。

### 第六步：下发推进面操作

对活动推进面作出继续、调整、暂停、合并、关闭、取消或新建决定，并为需要运行的 worker 生成推进说明。

### 第七步：更新项目状态

写回：

- 新增或失效的事实；
- 新增、修正或被推翻的承重假设；
- 新增、关闭或重写的收敛缺口；
- 推进面关系变化；
- 待人类决定事项；
- 下一次唤醒条件。

然后结束本次 orchestra 会话。

## 12. orchestra 输出

单次决策轮至少产生三类逻辑输出。第一版可以用 Markdown 表达，不建立版本化结构定义。

### 12.1 项目状态修订

```text
新增或失效的事实
新增、修正或失效的承重假设
新增、关闭或重写的收敛缺口
新建、调整、暂停、合并或关闭的推进面
待人类决定事项
```

### 12.2 推进面操作与说明

项目级动作语义可以包括：

```text
新建
继续
调整
暂停
合并
关闭
取消
等待
询问人类
停止
```

这些不是固定状态机，只是清楚表达战略意图。

### 12.3 再次唤醒条件

说明下一次什么时候值得重新激活 orchestra，而不是固定时间轮询或每个 worker 交互都介入。

## 13. 推进说明

推进说明应短而完整：

```markdown
## 期望项目变化
本推进面希望让项目现实发生什么变化

## 为什么现在做
为什么这是当前有价值的项目推进面

## 相关事实
与本工作面相关的已核实事实和证据引用

## 当前工作假设
当前允许 worker 使用的承重假设及其失效信号

## 自主决策范围
worker 可以自主决定的局部范围

## 共享边界
与其他推进面或外部协议共享、不得单方面改变的边界

## 必须保留
已有能力和真实约束

## 所需证据
完成后需要返回的可复核结果

## 何时上报
哪些项目级变化需要提前通知 orchestra
```

不规定：

- 文件和类设计；
- worker 内部步骤；
- 子代理数量；
- 测试实现方式；
- 局部评审流程。

## 14. 什么算有效项目变化

下一项工作必须有项目级因果依据，但不要求每一轮都立刻产生用户可见界面或功能。

合法项目变化至少属于一类：

- 新增用户可观察能力；
- 修复真实端到端失败；
- 集成两个已经孤立存在的能力；
- 消除一个承重不确定性；
- 建立后续判断必需、当前确实缺失的反馈或验证能力；
- 建立多个推进面独立推进所必需的共享边界；
- 降低已确认的不可逆风险；
- 删除或停止已经被事实证明无价值的路线。

不能单独成为新工作理由：

- 代码已经有这个结构；
- 现有测试覆盖它；
- 上一轮留下待办；
- 继续完善会更严谨；
- 已投入很多计算量；
- 新机制自身又产生了迁移、兼容、恢复或审计责任。

对内部机制执行的反事实检查应是：

> **即使不考虑这个机制自身已经存在，它是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不把该机制的继续完善自动升级为项目目标。

## 15. 防止视野循环

### 15.1 worker 总结只作为第二阶段线索

worker 自述必须与代码、测试、运行结果和外部事实区分。orchestra 先独立观察原始证据，再读取 worker 对结果和下一步的解释。

### 15.2 连续无有效项目变化时重新理解问题

如果连续执行：

- 修改同一内部子系统；
- 增加结构定义、恢复、兼容和审计机制；
- 没有新增端到端能力；
- 没有验证关键假设；
- 没有减少真实失败或不确定性；

下一次 orchestra 必须重新理解问题，不默认沿用 worker 的下一步建议。

### 15.3 允许路线稳定，不鼓励随机反转

全新会话的目的是减少旧叙事锚定，不是让每轮随机换方向。

当前方向默认可以继续，除非：

- 新证据触发既有失效条件；
- 独立检查发现此前遗漏的项目级矛盾；
- 推进面的协调耦合、成本或价值发生实质变化；
- 人类意图已改变。

### 15.4 临时反证代理不是永久评审节点

只在连续无项目增量、即将大规模投入、存在路线锁定风险或人类重大方向变化时，临时调用独立观察者。它只回答路线问题，不做一般代码评审，也不成为固定流程。

## 16. 人类介入边界

只在以下情况询问人类：

- 多个产品方向都合理且事实无法裁决；
- 要建立新的外部兼容或产品承诺；
- 涉及不可逆发布、数据或权限风险；
- 长期目标彼此冲突；
- 价值、成本和时间取舍本身属于人类偏好。

不因内部实现、普通错误、测试失败、文件结构或代理自建合同询问人类。

## 17. 第一版实验形态

第一版不实现新的运行时内核，可以由 Hermes 现有能力和当前主会话手工承担外层程序职责：

1. 用普通项目文件维护精简项目状态；
2. 收集人类变化、Git、持续集成、运行结果和 worker 产物引用；
3. 启动全新的 orchestra，会话内执行两段式决策；
4. orchestra 输出项目状态修订、推进面操作和推进说明；
5. 默认启动或恢复一个完整 worker；
6. 出现真实低协调耦合时，允许启动第二个或更多独立 worker 会话和工作区；
7. worker 完成、阻塞或改变共享边界后，再启动新的 orchestra 决策轮。

第一版只需要一个很小的活动推进面清单，不建设通用 worker 登记系统、数据库、事件协议、检查点或决策账本。

## 18. 验证方案

真正需要验证的假设是：

> 在长期、复杂、需求会变化且人类不持续纠偏的真实项目中，间歇式 orchestra 是否比 worker 自管理更稳定地维护项目方向、正确配置 1..N 个成熟 worker，并交付更多端到端项目成果？

### 18.1 对照组

对照 A：单一 worker 自管理

```text
人类长期目标
→ worker 完成当前工作
→ worker 自己选择下一步
→ 连续推进
```

对照 B：单 worker 加间歇式 orchestra

```text
人类长期目标
→ 全新 orchestra 选择一个推进面目标
→ worker 执行
→ 全新 orchestra 重新判断
```

对照 C：弹性推进面 orchestra

```text
人类长期目标
→ 全新 orchestra 维护项目状态和推进面关系
→ 默认一个 worker，必要时扩展为多个成熟 worker
→ 全新 orchestra 根据新证据合并、暂停或调整
```

### 18.2 测试项目必须包含

- 连续 8～15 次真实需求或约束变化；
- 至少两个自然形成的低协调耦合推进面；
- 一个早期合理但最终错误的承重假设；
- 一次共享边界变化，使原并行工作应被合并或串行化；
- 一次局部任务成功但整体项目没有闭环；
- 一次需要暂停、终止或替换推进面的情况；
- 人类只在预定点提供相同重大方向变化，不持续监管。

### 18.3 主要观察

- 最终端到端项目成果；
- 旧能力保留率和回归；
- 有多少 worker 运行产生真实项目变化；
- 过时假设下产生的无效工作量；
- 需求变化后恢复正确方向的速度；
- 是否正确识别低协调耦合推进面；
- 耦合升高后是否及时收缩并行；
- 共享边界冲突和重复实现；
- 人类被迫纠偏次数；
- 总成本和总耗时。

不以代码行数、阶段数、代理数、评审数或内部测试数量作为主要成功指标。

### 18.4 否证条件

出现以下结果时，应认为当前 orchestra 设计没有证明价值：

- 只是生成更多文档、推进说明和 worker 运行；
- 下一步选择不优于 worker 自管理；
- 多 worker 主要增加同步和集成成本；
- 全新决策轮频繁随机改变路线；
- 项目状态与真实仓库持续偏离；
- 人类仍需持续告诉系统下一步做什么；
- 相同预算下单一成熟 worker 获得更好的最终项目结果。

## 19. 明确非目标

第一版不建设：

- 固定阶段类型或阶段绑定；
- 完整路线图冻结；
- 目标合同、进展账本或目标缺口归约器；
- 版本化决策结构或只追加的决策账本；
- 检查点、快照或压缩系统；
- 图修订校验器；
- 产物关系追踪和复杂来源协议；
- 概念面或依赖面；
- 自动负向评审或清理；
- 固定评审者、规划者、编码者或测试者角色；
- 文件级外层任务拆分器；
- worker 内部子代理管理；
- worker 之间的长期直接通信层；
- 持久推理历史。

只有长期对照实验出现经确认的实际缺口时，才考虑对应的最小自动化。
