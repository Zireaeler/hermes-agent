# Orchestra 编排层设计

本文档定义一个编排层的设计。它把成熟的 coding agent（Codex / Claude Code 等）作为
worker，在其之上提供长期方向控制，使一个项目可以在少量人工介入下持续推进。

本文档是这个设计的唯一规范文档。每一条设计决策都附带它的理由；说不出理由的机制不应
存在。

---

## 0. 这个系统要解决什么

已有的 coding agent 在单个明确任务上表现良好。把它们接成一个自动循环也不难：任务完成
后让它写一份阶段总结，据此生成下一个任务，如此往复。这个循环确实能自动跑下去。

问题在于这个循环**只有前进档**。它每一轮都只能问"下一步做什么"，永远不会问"上一步做的
东西该不该存在"。于是它持续做加法：每个新增机制单独看都合理，累积起来变成没人能理解的
产物。防御性代码堆积、为死路砌墙、逐渐偏离最初意图——这些都不是执行错误，是缺少否定
机制的必然结果。

**这个系统要提供的核心能力是否定。** 前进由 worker 完成，它们已经足够强。编排层存在的
理由是在正确的时刻说"停、回退、砍掉、换方向"。

一个推论：**编排层的活跃度不是成功指标。** 决策次数多、节点多、协调事件多，都不说明它
在起作用。一个几乎不介入、但在关键时刻做出了正确否定的编排层，优于一个持续忙碌的编排层。

## 1. 角色与边界

### 1.1 人

人负责三件事：

1. 给出原始意图——这个项目为什么存在、要什么。
2. 设定红线——不可越过的约束（花钱、凭证、破坏性操作、架构方向的否决权）。
3. 偶尔查看整体状态，在被升级的问题上做决定。

人**不做监管**。人不审查任务、不检查代码、不跟踪进度。这是这个系统存在的目的。

要让"人不监管"成立，前提是人偶尔看一眼的成本足够低。因此可读性不是附加要求，它是这个
角色划分能否成立的物理前提（见 §9）。

### 1.2 Orchestra

编排层。它是一个 agent，用现成的 coding agent 会话作为大脑，不自建决策引擎。

**Orchestra 的判断不受代码约束。** 它和任何自主 agent 同性质：约束它的手段是注入上下文
的原则说明（prompt / md），不是代码规则。用 validator 去裁决它的判断是错误的设计——那
会把它从判断者降级为受限组件，而这个系统需要的恰恰是它的判断。

它的能力清单见 §2。

### 1.3 Worker

完整的 Codex / Claude Code 实例。

worker 内部**自己组织工作**：它会拆解任务、派内部 subagent、并行阅读、自我纠错。这些是
它的内政，Orchestra 从不审查。理由：worker 掌握一手事实，它对内部分工的判断优于任何
外部观察者；而且任何靠近 worker 内部的监管都会把 Orchestra 的上下文灌满执行细节，使它
退化成另一个 worker。

worker 是可替换的执行后端。系统不围绕任何特定 backend 设计。

### 1.4 核实 Agent

一次性的、无利益的第三方，用于核实 worker 的交付是否属实、当前产物是什么形状。

**独立性来自利益不一致，不来自看得多细。** worker 的自述是利益相关方的自我汇报——它有
动机把自己的工作判定为完成。核实 agent 的任务就是核实，没有这个动机。这是它存在的全部
理由。

它可以用更便宜的模型：它的任务是收敛的（对照一个具体标准检查一个具体产出），不需要全局
智能。

### 1.5 代码层

代码只做两件事：**如实记账**（记录发生了什么、保证可恢复、保证幂等）和**呈现状态**。

代码不裁决判断。它可以拒绝写入结构非法的数据（schema 不合法、引用悬空、重复入账），
不可以拒绝一个它认为不明智的决策。前者是数据完整性，后者是判断——判断不归代码。

## 2. Orchestra 的能力

只有四项。每一项都需要全局视角；不需要全局视角的事情一律外包。

### 2.1 持有意图

系统里唯一持有"这个项目为什么存在"的部件。每次判断都回溯到它。人更新意图时，由它负责
把新意图翻译成对当前所有在途工作的影响。

### 2.2 反思与否定（核心）

定期后退一步，回答三个否定性问题：

1. 已经做的东西，该不该存在？
2. 我们是不是在给一条死路砌墙，而不是换路？
3. 这些工作真的服务于原始意图，还是只是看起来在推进？

配套权力：废弃、删除、回退、冻结某条工作线。

**"本轮无需任何动作"是合法且预期常见的输出。** 这一条必须明确写进 Orchestra 的原则说明，
否则模型会倾向于每次都产出一些动作。

这一项是其余三项的中心：2.1 是它的依据，2.3 是它的输出，2.4 是它的边界。

### 2.3 方向生成

反思的输出：下一个任务是什么。任务契约只有三部分——做什么、明确不做什么、什么算完成。

它同时隐式设定了自己的介入频率：任务切得小，很快会再次被唤醒；任务切得大，长时间不介入。
**任务粒度就是监管密度的旋钮**，不确定时切小，有把握时放大。

合法输出也包括"不确定方向，先派一个探索性任务"和"该停了 / 该问人了"。

### 2.4 止损与升级

**止损**：某条工作线已经投入了多少、继续还是砍掉。worker 永远倾向于"再试一次就好了"，
这个判断只能由持有全局的一方做。

**升级**：识别哪些决策不归自己——红线、花钱、意图本身的变更、多个合理方向且无依据取舍。
停下来问人，而不是替人决定。

### 2.5 明确不具备的能力

- 不写代码、不改文件
- 不持续观察 worker 的执行过程
- 不自己核实，派核实 agent 去
- 不审查 worker 的内部分工
- 不高频介入；两次唤醒之间 worker 完全自治
- 不添加机制、流程或规范，除非能两句话说清它服务什么（见 §10）

## 3. 两种运行模式

系统有两种性质不同的模式，经济学是反的。

### 3.1 探索模式（0 → 1）

**适用**：还没有确定方案的阶段。意图是模糊的，没有产物，没有历史。此时否定还没有对象，
唯一能做的是把模糊意图变成若干个可执行的赌注并比较它们。

**经济学**：稳态里浪费是病，探索期里浪费是买信息的价钱。三条路废掉两条，那两条不是失败，
是"排除了两个错误方向"这个结论的成本。

**做法**：并行派出若干独立尝试，每条走不同解法。它们互不通信、不共享上下文、不需要集成
（见 §4.1，这类并行几乎没有协调开销）。

**交付物是知识，不是产物**：每个探索节点要回答"这条路走得通吗、卡在哪、代价多大"，代码
只是副产品。这一点必须写进任务契约，否则 worker 会本能地去把功能做完，结果是三份半成品
而不是三份判断。

**比较方法**：不要在半成品上比抽象指标（效率、完成度、通过率）——不同方案卡在不同深度，
进度快的往往只是绕开了真正的难点。正确做法是**预先定一个所有方案都必须触达的具体里程碑**
（一个能跑通的最小闭环），在同一个固定点上比。

**必须真的丢弃**：选定一条后，其余整个扔掉，不合并。合并出来的东西会带着几套互相冲突的
隐含决策，比任何一条单独的路都差。"取长补短"的诱惑很大，这一条要写死。

**退出条件（必须有）**：探索模式如果不会结束，它就是另一种形态的膨胀。触发承诺的条件是
以下之一：

- 某条路已达到预设的验证里程碑；
- 探索预算耗尽，选当前最好的。

承诺时要做两件事：扔掉其余方案，**并把原本模糊的目标具体化成可验证的形式**（否则 §7 的
终止条件一(达成目标)永远是空的）。之后切换到稳态模式。

### 3.2 稳态模式（1 之后）

**适用**：方案已选定，在一条路上推进。

**本质**：监管一个已决定方案的推进，判断是否需要变枝。这里浪费是要消除的，否定是核心
工作。§2 的四项能力、§5 的上下文机制、§6 的节奏，主要都是为这个模式设计的。

## 4. 并行策略

### 4.1 竞争式 vs 协作式

**竞争式并行**：多个节点做同一件事的不同解法，最后只活一个。彼此不通信、不共享上下文、
不集成。**协调成本接近零**，因此可以放开用。探索模式用的就是这种。

**协作式并行**：多个节点做同一件事的不同部分，最后必须拼起来。需要共享契约、划分写范围、
指定集成责任。**协调成本很高**，经验上常常吃掉全部并行收益还有余。默认不用。

结论不是"并行好还是串行好"，而是：**竞争式并行几乎免费，用；协作式并行很贵，默认不用。**

### 4.2 什么时候拆节点

worker 本身就会内部并行，而且它的内部 subagent 共享同一个上下文和工作区，协调成本为零。
所以真正的对比不是"1 个节点 vs n 个节点"，而是"**1 个节点（内部已并行）vs n 个节点
（外部要协调）**"。这么一比，拆节点的吸引力小得多。

判据一句话：**这些工作能不能共享一个上下文和工作区？能，就留在一个节点里，让 worker 自己
去并行；不能，才拆。**

"不能共享"的合法情况只有三类：

1. 需要不同的权限 / 凭证；
2. 必须隔离的工作区；
3. 探索模式下**故意**不共享（要独立解法）。

以下都不是拆分理由：任务复杂、涉及文件多、理论上可以并行、计划看起来更清晰、阶段不同、
角色不同。

### 4.3 不设计节点间通信

**"需要通信"应被当成拆分错误的信号，而不是一个待实现的需求。**

两个节点如果需要互相同步契约、传递上下文、协商接口，说明它们本来共享一个上下文，不该拆开。
为这种情况建设通信机制（定向消息、协调检查点、运行中干预、邮箱），会引入这个系统里最复杂
且收益最可疑的一块。

唯一需要的"通信"是**顺序**：一个节点先完成，另一个在它的产出上继续；或一个节点作为集成方，
在明确边界收取其他节点的产出。这是排序和交付，不是通信，不需要协议。

## 5. Orchestra 的上下文

### 5.1 两个不同的要求

**推理连续性**要的是"推理 token 在场"——与位置无关。只要历史判断、否定过的东西、未消解的
怀疑还在上下文里，下一次就能接着想。

**前缀缓存**要的是"前缀逐字节相同"——完全与位置有关。从中间删掉任何内容，后面全部位置
偏移，缓存从删除点起失效。

这两个要求不同，必须分别满足。

另外要认识到：**不存在有状态的会话**。每次调用都是对整个 token 序列的一次全新计算，两次
调用之间没有隐藏状态。所谓"连续会话"物理上就是"token 序列一直在变长"。因此"连续会话 vs
每次重建"是假二分——重建不损失连续性，只要重建出的序列里推理 token 都在。

### 5.2 布局

每次唤醒时构造这样的序列：

```text
[稳定前缀：原始意图 + 本文档的核心原则]     ← 永不变
[判断记录：j1, j2, ... jN]                  ← 只追加，不修改
[当前现状快照]                              ← 只在尾部，每次整体替换
```

**关键约束：快照永远只出现在尾部，绝不写进中间的判断记录。**

这样相邻两次请求的公共前缀是 `[稳定前缀][全部判断记录]`，缓存完全命中；未命中的只有尾部
那份刚生成的快照，而它在物理上本来就不可能命中。这个布局下的缓存损失等于理论下限。

如果快照被就地留在历史里、事后再从中间删除，缓存就会从删除点起全部失效。区别不在"删不删"，
在**快照有没有被写进累积序列**。

### 5.3 现状快照

判断的主要依据是**现状**，不是叙事摘要。

理由：过度设计在摘要层面结构性不可见。每一条交付结论单独看都合理（"增加了 X 以处理 Y"永远
说得通），累积起来才是问题，而一条条压缩结论恰恰抹掉了"累积"这个维度。而且**信息贫乏的
否定者只能批准**——手上只有正面陈述的结论，唯一能得出的判断就是"看起来没问题，继续"，
这比没有编排层更坏，因为它还制造已审查过的虚假信心。

现状信息的性质：**它的大小与项目年龄无关**，因为它是当前快照，每次重拍而不是累积。所以
可以做得很厚而不引起膨胀。

快照由核实 agent 生成，内容针对要检测的病：

- **机制清单 + 每个机制一句话的存在理由**。说不出理由的即候选删除项。这是最强的过度设计
  探测器，生成成本很低。
- **规模与复杂度当前值**（模块数、文档数、抽象数、约束条目数）。
- **上一次深审以来：新增了多少东西 vs 新增了多少真实能力**。这是"复杂度增长是否与进展成
  比例"的直接读数，也是唯一需要跨周期累积的信息——但它只是几行数字。
- **新人理解测试**：把当前状态交给一个没有上下文的便宜模型，让它说这个项目在做什么、当前
  是否健康。答不上来即可读性已经崩溃。

快照是现在时的结构化测量，不是原始执行过程（diff、日志、工具调用轨迹一律不进 Orchestra
的上下文）。

### 5.4 判断记录

每次唤醒的输出要写进记录，且不能只写结论。必须包含：

- 本次判断的结论；
- 理由；
- **我在盯什么、我对什么不放心、什么情况下我会推翻这个判断。**

第三项是给未来的自己留的怀疑种子，也是"跨多次唤醒慢慢长出否定"的物质基础。由于两次调用
之间没有隐藏状态，这些东西如果不写下来，下一次就不存在。指望模型靠会话延续自己记住，是
指望一个不存在的机制。

### 5.5 压缩

判断记录会增长，最终需要压缩。**用一份 prompt md 完成，不建子系统**——这是几个月一次的
事件，不配拥有一套机制。

压缩规则只有一条：**必须活下来的是否定性知识，不是现状。**

- 保留：拒绝过什么、为什么拒绝、试过并放弃的路、尚未消解的怀疑、经验中长出的红线。
- 删除：现状类描述。

理由：现状每次都由新快照重新提供，可再生，丢了没关系。而"我们试过 X 因为 Y 放弃了"在任何
地方都不存在第二份——快照看不到（它只看得见现在有什么，看不见曾经拒绝过什么），worker 不
知道，代码里也没有。丢了就是永久丢失，然后系统会重新犯一遍同样的错。

## 6. 唤醒节奏

**频率是判断质量的旋钮，不是成本旋钮，而且方向反直觉：唤醒越频繁，否定能力越差。**

原因有两层。其一，过度设计在近距离下不可见——每次交付单独看都合理，只有拉开距离看一段
积累，形状才会显现。每次交付都唤醒，面对的永远是孤立的、看起来没问题的增量，结构上不可能
看出膨胀。其二，频繁的无事发生型唤醒会往判断记录里填满"一切正常，继续"，模型下次读到连续
批准的模式，会被带着继续批准。**判断记录必须保持信号密度高，这本身就要求唤醒稀疏。**

### 6.1 快节奏（响应式）

触发：worker 卡住、越权、需要一个它做不了的决定。

职责：解阻和路由，输出通常就是下一个任务。信息需求低，不需要完整快照，成本低。

**频率不需要制定政策**——Orchestra 通过任务粒度隐式设定它（见 §2.3）。

### 6.2 慢节奏（定期深审）

带完整现状快照，执行 §2.2 的三个否定性问题。

**必须刻意稀疏，稀疏是功能不是省钱。** 深审的成本（一次结构审计 + 一次判断）相对 worker
真正干活烧掉的量基本可忽略，所以频率完全不该由成本决定。如果开始为深审的开销心疼，说明
Orchestra 已经被做臃肿了，该回头砍它，而不是降低审查频率。

**不能由事件触发。** 事件意味着"出问题了"，而漂移和过度设计从不报错——它们表现为一切顺利、
稳步推进、测试全过。等到有事件触发时，问题已经成型。

**不能用周期边界触发。** 两个原因：

1. **周期是内生的。** 周期由 Orchestra 自己定义，一个正在漂移的判断者对"什么算一个完整
   周期"的理解也在同步漂移，于是它总能宣布本周期完成、开始下一个。用被审计者自己划的边界
   触发审计，等于让它自己决定何时接受检查。
2. **周期边界是完成时刻，带正向框架。** 刚交付完一块能跑、测试都过的东西，这个时刻问
   "是不是该把这些删掉"，几乎必然得到否定答案。刚完成的东西看起来永远像进展。

**触发器必须外生，从产物上测量：新增"有名字的东西"的数量到阈值。** 新机制、新模块、新概念、
新文档、新抽象——命名实体的增殖正是要检测的病本身。不用代码行数（大规模重构产生大量变化但
不是漂移，噪音大）。

这个触发指标和审查内容是同一个量：审查时问的就是"这 N 个新名字，每个用一句话说清服务什么"。
触发器和检查项统一，不需要两套东西。

**深审会落在周期中间，这是特性不是缺陷。** 停止的成本在事情没做完的时候最低：周期做完再
判断"这条路错了"，要扔掉一整块已完成、已测试、看起来很像成果的东西，阻力最大；干到一半时
判断，扔掉的是半成品，成本小得多。

### 6.3 加开与推迟

异常信号（反复返工、持续卡在同一处、交付与预期持续对不上）可以**提前加开**一次深审。

定期深审是地板，**不可推迟**，也不能因为"最近没出问题"而取消。

---

## 7. 终止

三个条件，满足任一即终止：

1. **达成目标**——满足最初设定的、可验证的明确目标。（要求目标已具体化，见 §3.1 的承诺
   动作。）
2. **完全阻塞**——无法继续推进，且不存在合法的解阻路径。
3. **不值得继续**——没被阻塞、还在产出、但投入产出比已经反转。

第三条最难判断也最重要。一个只有前两条的系统永远不会停：它既不会被阻塞（每一步都在顺利
推进），也不会达成目标（目标一直在往后挪），于是可以无限做下去。第三条没有客观标准，只能
在深审时被问到——关键是它必须**出现在流程里**，而不是等着谁想起来。

---

## 8. 反馈与否定的执行

### 8.1 Worker 的反馈

worker 掌握一手事实，经常比 Orchestra 更清楚任务是不是提错了。完全不给它推回的渠道，是在
浪费系统里信息最充分的判断源。

但它应该是**证据，不是请求**：worker 在交付里附上"我认为这个任务的前提有问题，理由是 X"，
作为数据进入 Orchestra 的下一次判断。不是发起一个协商流程、等待回复、双方来回。

实现上这是**交付格式里的一个字段**，不是一套协议。

### 8.2 否定的执行

Orchestra 决定"砍掉某机制"后，这本身是一件工作，作为任务派给 worker。执行是否正确不是
Orchestra 操心的事，由 worker 和常规核实负责。

一个必须防的坑：**删除类任务极容易变成新增类任务。** worker 常见的做法是加一层兼容包装、
加一个开关、加一段迁移代码——为了删掉东西反而加了更多东西。这不是偷懒，是它倾向于做"安全
的改动"。

因此否定类任务的验收不看 worker 的自述（它会说"已移除"），看 §6.2 那个已有的指标：**命名
实体数量必须真的下降**。同一个数触发深审，也用来验收否定。

## 9. 成功度量

不用活跃度衡量（决策次数、节点数、协调事件数）。真正的度量：

1. **浪费率**——被砍掉或重做的 worker 工时占比，是否随时间下降。
2. **形状**——复杂度增长是否与真实能力增长成比例。
3. **人的负担**——人每次查看需要几分钟、多久需要看一次、有没有被迫下沉到实现细节。
4. **否定的存在证明**——判断记录里必须能找到真实发生过的否定、回退、砍除。**一个从未否定
   过任何东西的编排层等于不存在。**

第 4 条是最重要的健康指标。模型天生倾向于前进、增补、把已有的东西合理化；"停下来说过去
两周的方向错了、删掉一半"是它最不擅长的动作。如果长期没有否定发生，不要当成"运行良好"，
要当成这个系统的核心功能失效。

---

## 10. 防膨胀约束

本文档是这个设计的唯一规范文档。**不要按阶段追加新的规范文档。** 一份份叠加的阶段文档会
形成只增不减的棘轮：违反约束的代价是显性的，过度约束的代价是弥散的，于是系统必然向保守和
臃肿漂移。有新结论就修改本文档，不新建。

**否决规则**：任何新机制、新字段、新节点类型、新流程，如果不能用两句话说清它服务
**方向生成 / 否定 / 可读性** 中的哪一个，不得引入。写不出这两句话即拒绝。

**唯一的总验收标准**：一个离开两周的人回来，能否在五分钟内看懂——做了什么、为什么这么做、
有没有跑偏。做不到即失败，无论其他指标多好。

## 11. 未决问题

以下尚未设计，需要在实现前或实现中确定：

1. **人的升级通道**。人不在 loop 里，如何被叫醒？什么算够格打扰人？等待人回复期间系统做
   什么（阻塞还是继续其他工作）？"人不监管"要成立，这个通道必须可靠——否则要么人被打扰
   过频，要么系统在没人的情况下替人做了红线决定。
2. **预算与成本治理**。整个项目烧多少算多，谁在盯，超了怎么办。§2.4 的止损是局部的，缺
   总量概念。
3. **模型选型**。Orchestra 需要最强的判断力，worker 需要执行力，核实 agent 可以很便宜。
   这个分配尚未确定。
4. **意图捕获**。如何从人那里得到一份足够好的原始意图和红线，尤其是在探索模式起点、意图
   本身还很模糊的时候。
5. **Orchestra 的自监管**。它自己是否在漂移，由谁判断。§5.4 的判断记录 + §6.2 的外生触发
   已经构成了这件事的基础材料（周期性回读全部判断记录，回答"这串决策连起来还朝着意图吗"），
   但尚未作为一项能力设计。
