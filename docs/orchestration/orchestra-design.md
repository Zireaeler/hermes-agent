# orchestra 设计：间歇式项目战略层

## 0. 当前结论

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮都从当前人类意图、项目事实、精简阶段结果和按需证据重新组装上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承旧对话、推理过程和策略辩护。**

首版严格采用一对一结构：

```text
人类
  │
  ▼
全新的 orchestra 决策轮
  │  选择或修正当前推进方向
  ▼
一个完整 worker
  │  自行规划、使用内部子代理、实现、测试和修复
  ▼
阶段结果
  │
  └────────→ 下一次全新的 orchestra 决策轮
```

首版只验证一个问题：

> **在长期项目中，由全新的 orchestra 在项目决策边界重新判断下一步，是否比当前 worker 持续自我选择下一步，更能维持原始方向并推动项目收敛？**

多 worker 的发现、分配、并行、协调和集成是另一组复杂问题，不属于首版，也不能与一对一监督实验捆绑验证。

架构原则：

```text
项目连续性属于持久项目状态。
orchestra 的推理只属于单次决策轮。
worker 的执行连续性只属于当前明确任务。
```

本文档是一版待验证设计，不是新的运行时规范。第一版优先使用 Hermes 已有能力、普通项目文件和独立代理会话完成手工实验。

## 1. 问题边界

完整的 Claude Code 或 Codex worker 已经能够在一个明确任务内完成：

- 阅读代码；
- 形成方案；
- 调用内部子代理；
- 拆分并行调查；
- 编码、测试和修复；
- 整合局部结果。

因此 orchestra 不应重复建立规划者、编码者、测试者和评审者，也不应把一个明确任务再次拆成多个外层 worker。

真正未被现有 worker 解决的问题是跨多个任务和阶段的长期方向：

```text
人类给出远大目标
→ worker 完成当前任务
→ worker 从自己刚建立的结构中选择下一步
→ 新机制成为新的注意力中心
→ 继续补一致性、恢复、兼容和审计
→ 原始产品目标逐渐退出注意力中心
```

每个局部任务可能都完成正确，但整个项目没有形成新的端到端能力，没有消除关键不确定性，也没有更接近可交付状态。

orchestra 的职责不是提高 worker 的局部编码能力，而是在阶段之间重新回答：

```text
项目现在真实处于什么状态？
当前路线是否仍然值得继续？
下一项工作应让项目发生什么变化？
什么时候应该停止、回退或询问人类？
```

## 2. 本文只讨论一对一监督

首版固定只有：

```text
一个 orchestra
一个当前 worker
一个当前推进任务
```

一对一不表示 orchestra 持续盯住 worker。orchestra 只在项目决策边界出现，worker 在两个决策边界之间保持完整自治。

worker 可以使用自身已有的子代理系统。它如何并行调查、拆分实现和整合结果，不属于 orchestra 的管理范围。

首版不讨论：

- 同时运行多个外层 worker；
- 识别低耦合并行任务；
- worker 之间的消息和共享状态；
- 多工作区写入和合并；
- 动态扩容、暂停和回收 worker；
- 多 worker 的集成责任；
- orchestra 自己再调用一组长期子代理。

这些能力即使未来需要，也必须作为独立研究问题逐项验证，不能被当成首版天然应有的功能。

## 3. 角色边界

### 3.1 人类

人类提供：

- 长期意图；
- 关键成功体验和可观察结果；
- 产品、安全和外部协议边界；
- 后续重大方向变化；
- 事实无法裁决的价值选择。

人类不负责持续决定每个阶段的下一步，也不需要阅读 worker 的完整执行过程。

### 3.2 orchestra

orchestra 只负责阶段之间的项目级判断：

- 重新确认当前人类意图；
- 独立检查项目事实；
- 判断上一阶段是否真正推动项目；
- 判断当前路线是否仍然成立；
- 选择下一项有项目意义的任务；
- 决定继续、调整、回退、等待、询问人类或停止；
- 更新精简项目状态并生成 worker 推进说明。

orchestra 不负责阶段内实现，不接管普通错误修复，不管理 worker 内部子代理。

### 3.3 worker

worker 接收一个相对完整、有限、可验证的推进说明，并完整负责：

- 理解代码和任务；
- 形成局部方案；
- 自行拆分工作；
- 调用内部子代理；
- 编码、测试和修复；
- 返回可验证结果和可能影响项目方向的新事实。

worker 不需要向 orchestra 上报普通局部计划、命令历史、每次测试失败和内部子代理对话。

### 3.4 外层程序

首版外层程序只负责：

- 启动全新的 orchestra 会话；
- 启动或恢复当前 worker 会话；
- 投递人类消息、阶段结果和证据引用；
- 管理基本进程、权限、预算和取消；
- 保存少量项目状态文件。

外层程序不判断下一步，不拆任务，不建立执行图和校验流程。

## 4. 运行方式

### 4.1 orchestra 跨决策轮不继承会话

每次项目决策边界到来时：

- 创建新的 orchestra 会话；
- 不恢复上一轮 orchestra 对话；
- 不携带旧助手消息、工具记录和推理链；
- 不把上一轮计划和辩护重新塞回请求；
- 从当前项目状态和本轮新增事实重新组装上下文。

长期存在的是项目状态和 orchestra 的责任，不是一条长期模型会话。

### 4.2 单次决策轮内允许完整代理循环

全新会话不等于单次分类调用。一个决策轮内，orchestra 可以：

- 阅读项目状态；
- 检查与当前判断相关的代码和差异；
- 运行产品、测试或关键实验；
- 查看最近 worker 产物；
- 比较少量候选方向；
- 形成下一项任务或停止判断。

首版不要求 orchestra 调用额外子代理。先验证单个战略代理本身是否有价值，避免把多代理能力混入结果。

### 4.3 worker 在当前任务内保持连续

```text
orchestra：每个项目决策边界使用全新会话
worker：当前明确任务内保持连续会话
项目状态：跨阶段持久
```

如果 orchestra 判断下一项任务仍是原任务的自然延续，可以继续原 worker 会话。若任务方向被实质改变、核心假设被推翻或原会话已经明显陷入旧路线，可以启动新的 worker 会话。

任何时刻仍然只有一个当前 worker。

## 5. 持久项目状态

持久项目状态只服务于下一次 orchestra 判断。它不是完整历史，不是冻结合同，也不是新的运行时数据库。

首版只保留以下内容。

### 5.1 人类意图

- 长期目的；
- 当前重大方向；
- 可观察成功结果；
- 真实约束；
- 已确认的非目标；
- 后续明确修改和撤回。

worker 或 orchestra 自己建立的机制不能反向扩张人类意图。

### 5.2 已确认的项目事实

只保存会影响项目方向的事实：

- 当前真正可运行的端到端能力；
- 已验证的用户流程；
- 当前真实失败和阻塞；
- 已形成的外部协议或数据承诺；
- 已集成结果与仍然孤立的产物；
- 对应的代码版本、测试、日志或运行结果引用。

代码和 Git 可直接恢复的普通细节不重复抄写。

### 5.3 承重假设

只保存一旦错误会改变后续路线的项目级假设：

```text
假设
当前依据
什么事实会证明它失效
```

承重假设不是事实，也不是上一轮推理历史。

### 5.4 当前收敛缺口

保存 orchestra 当前对“项目为什么还没有成立”的精简解释，例如：

- 核心能力尚未形成端到端闭环；
- 两个已有能力尚未集成；
- 关键协议语义仍不明确；
- 缺少判断真实失败所需的反馈；
- 当前路线局部持续成功，但没有减少项目级风险。

它不是代码待办列表，可以随新证据直接改写或删除。

### 5.5 精简阶段结果

每个阶段只保存：

- 原本想产生什么项目变化；
- 实际产生了什么可验证变化；
- 哪个承重假设成立、失败或仍未知；
- 当前路线应继续、调整还是停止。

不保存完整阶段推理、候选争论和设计辩护。

### 5.6 已停止路线

只保留成本较高且未来容易重复的失败路线：

```text
路线
原假设
反证
当前停止结论
```

### 5.7 待人类决定事项

只保存真正属于产品方向、外部承诺、不可逆风险或价值取舍的问题。

## 6. 事实、判断和决定必须分开

全新 orchestra 只有在输入没有把旧判断伪装成事实时才真正有意义。项目状态应明确区分：

```text
人类意图
已观察事实
当前推断
承重假设
当前决定
开放的不确定性
```

上一轮决定最多保留为可证伪的精简残留：

```text
当前方向
依赖的承重假设
预期信号
明确失效条件
尚未解决的风险
```

它不是权威，也不是要求新 orchestra 继续维护旧路线的理由。

## 7. 最小充分上下文

每次 orchestra 决策轮的输入由四部分组成：

```text
稳定前缀
  orchestra 职责、人类长期意图、硬边界、输出要求

当前项目状态
  已确认事实、承重假设、收敛缺口

本轮变化
  最近阶段结果、人类变化、外部变化

按需证据
  与本轮判断直接相关的代码、差异、测试、日志和运行结果
```

不直接拼接上一轮 orchestra 对话，也不全量复制 worker 对话。

### 7.1 两段式揭示是独立待验证设计

两段式上下文有合理动机，但它不是一对一 orchestra 的成立前提，也不应与首个长期实验捆绑成不可分割的整体。

候选做法是：

```text
第一段：先看当前事实和原始证据，不看旧策略与 worker 建议
第二段：再看精简决定残留、停止路线和 worker 解释，校正初步判断
```

它需要单独与一次性完整输入比较，验证是否真的减少锚定，而不是直接假定有效。

## 8. 项目决策边界

orchestra 不常驻，也不检查每个 worker 动作。典型触发：

- 当前任务完成并产生候选结果；
- worker 确认阻塞或核心假设失效；
- 人类发来重大方向变化；
- 关键实验或外部事件产生结果；
- 连续执行没有产生实质项目变化；
- worker 建议继续加固同一内部机制；
- 即将投入大规模或不可逆路线；
- 项目可能已经达到长期目标。

普通测试失败、局部实现选择、worker 内部子代理调度和普通提交不触发 orchestra。

## 9. 单次 orchestra 决策轮

### 第一步：重新确认人类意图

回答：

- 人类最终需要什么项目结果？
- 当前重大方向和外部边界是什么？
- 哪些目标来自人类，哪些只是代理自建结构？

### 第二步：检查项目现实

独立检查：

- 当前真正能运行什么；
- 哪些端到端结果已经验证；
- 上一任务实际改变了什么；
- 当前主要收敛缺口是什么；
- 原路线依赖的承重假设是否仍成立。

### 第三步：生成少量候选动作

候选可以是：

- 继续当前任务；
- 调整当前任务边界；
- 结束当前路线并选择新任务；
- 做一个有限判别实验；
- 建立当前确实缺失的反馈能力；
- 等待真实外部依赖；
- 请求人类；
- 停止项目。

不生成完整长期路线图。

### 第四步：选择一个当前任务

首版始终只选择一个当前任务，交给一个完整 worker。即使发现多个可能方向，也只选择当前最值得推进的一项，或先做能够区分方向的有限实验。

### 第五步：更新项目状态并下发任务

写回：

- 新增或失效的事实；
- 新增、修正或失效的承重假设；
- 新增、关闭或重写的收敛缺口；
- 当前战略决定；
- 待人类决定事项；
- 下一次 orchestra 唤醒条件。

然后生成 worker 推进说明并结束本次 orchestra 会话。

## 10. worker 推进说明

推进说明应短而完整：

```markdown
## 期望项目变化
本任务希望让项目现实发生什么变化

## 为什么现在做
为什么这是当前最有价值的一步

## 相关事实
与本任务相关的已确认事实和证据引用

## 当前工作假设
允许 worker 使用的承重假设及其失效信号

## 自主决策范围
worker 可以自主决定的实现范围

## 必须保留
已有能力和真实约束

## 所需证据
完成后需要返回的可复核结果

## 何时提前上报
哪些项目级变化需要在任务完成前通知 orchestra
```

不规定文件、类、实现步骤、子代理数量、测试写法或局部评审流程。

## 11. 什么算有效项目变化

下一项任务必须有项目级因果依据，但不要求每一轮都立刻产生用户可见界面或功能。

合法变化包括：

- 新增用户可观察能力；
- 修复真实端到端失败；
- 集成已经孤立存在的能力；
- 消除一个承重不确定性；
- 建立后续判断必需且当前确实缺失的反馈能力；
- 降低已确认的不可逆风险；
- 删除或停止已经被事实证明无价值的路线。

不能单独成为新任务理由：

- 代码已经存在这个结构；
- 已有测试覆盖它；
- 上一轮留下待办；
- 继续完善会更严谨；
- 已投入很多时间或计算量；
- 新机制自身又产生迁移、兼容、恢复或审计责任。

反事实检查：

> **即使不考虑这个机制已经存在，它是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不把继续完善该机制自动升级为项目目标。

## 12. 实验必须拆开进行

首版不能直接运行一个包含所有设计点的综合项目演示。那样无法判断结果来自 fresh orchestra、一对一监督、项目状态、两段式揭示，还是多代理调度本身。

应按以下顺序逐步验证。

### 12.1 实验一：固定决策点判断

目的：先验证全新上下文是否能减少旧路线锚定，不执行编码任务。

从 Hermes 历史和至少另一个项目中选择若干真实决策点。每个决策点只提供当时可见的代码、项目事实和人类意图，未来结果只供评估者使用。

比较：

```text
A：延续原长期会话后判断下一步
B：全新 orchestra 根据重新组装的最小上下文判断下一步
```

观察：

- 是否继续修补代理自建机制；
- 是否回到原始项目目标；
- 是否识别应停止或重定向的路线；
- 是否提出可由事实验证的下一步；
- 不同决策点上的稳定性。

该实验不需要 worker，不需要多代理，也不需要新的运行时。

### 12.2 实验二：一对一长期闭环

目的：验证 orchestra 到 worker 的一对一监督本身是否有价值。

至少选择数个独立的长任务或历史回放，而不是只做一个特制项目。每个任务包含若干自然决策边界，但不强制塞入所有故障和设计点。

比较：

```text
A：worker 完成当前任务后，自行决定下一项任务
B：worker 完成当前任务后，由全新 orchestra 决定下一项任务
```

两组保持一致：

- 相同 worker 模型和工具；
- 相同预算；
- 相同初始人类意图；
- 相同外部需求变化；
- 同一时刻都只有一个 worker；
- worker 都可使用自身原生子代理能力。

唯一核心差异是：谁在项目决策边界决定下一步。

主要观察：

- 最终端到端项目成果；
- 有多少任务产生真实项目变化；
- 有多少任务只修补代理自建机制；
- 错误路线持续了多久；
- 人类被迫纠偏次数；
- 总成本和总耗时。

### 12.3 实验三：上下文组装方式

只有在一对一闭环显示出基本价值后，再比较上下文设计：

```text
一次性完整输入
对旧策略盲的第一段 + 精简历史校正的第二段
不同大小的项目状态
是否保留上一轮决定残留
```

该实验回答“怎样构建 orchestra 上下文”，不能和“orchestra 是否有价值”混成同一个结论。

### 12.4 后续独立研究：多 worker

多 worker 是另一条研究线。它至少包含：

- 如何判断两个任务是否适合并行；
- 如何管理独立工作区；
- 如何处理共享边界变化；
- 如何决定合并、暂停和取消；
- 谁承担最终集成责任；
- 并行收益是否大于协调成本。

在一对一 orchestra 尚未证明价值前，不应实现或评估这些能力，也不应让其进入首版文档的核心运行流程。

## 13. 否证条件

出现以下结果时，应认为首版 orchestra 没有证明价值：

- 全新 orchestra 的下一步判断不优于 worker 自管理；
- 只是生成更多文档和任务说明；
- 频繁随机改变路线；
- 项目状态持续偏离真实仓库；
- 人类仍需持续告诉系统下一步做什么；
- 相同预算下，worker 自管理获得更好的最终项目结果；
- 两段式揭示没有改善判断，却增加明显成本。

## 14. 首版明确非目标

首版不建设：

- 多 worker 调度和管理；
- 外层任务并行；
- worker 登记系统；
- 多工作区合并机制；
- worker 间通信层；
- 固定角色团队；
- orchestra 长期子代理团队；
- 完整路线图冻结；
- 目标合同、进展账本和执行图；
- 图修订校验器；
- 检查点、快照和压缩系统；
- 复杂产物关系追踪；
- 自动负向评审或清理；
- 持久推理历史。

只有一对一实验出现经确认的实际缺口时，才考虑对应的最小自动化。
