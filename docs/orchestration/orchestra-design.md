# orchestra 设计：间歇式项目战略层

## 0. 当前结论

> **orchestra 是运行在项目决策边界上的间歇式战略代理。每次决策轮都从当前人类意图、项目事实、精简结果和按需证据重新组装上下文；单次决策轮内允许完整代理循环，但跨决策轮不继承旧对话、推理过程和策略辩护。**

首版严格采用一对一结构：

```text
人类
  │
  ▼
全新的 orchestra 决策轮
  │  选择或修正当前推进方向
  ▼
一个持续工作的完整 worker
  │  自行规划、使用内部子代理、实现、测试和修复
  ▼
阶段结果
  │
  └────────→ 下一次全新的 orchestra 决策轮
```

本设计把以下现象作为已经观察到的工程前提，不在首版重复证明：

> **在长期项目中，让同一个 worker 在自己的连续上下文里不断维持远大目标并自行选择下一步，容易使目标逐渐涣散，注意力转向自己刚建立的结构，最终形成局部持续完成、整体不再收敛。**

这不是关于所有模型和所有项目的普遍定理，而是 Hermes 已经真实出现、且本系统明确要解决的问题。

因此首版不再设计“worker 自管理是否会漂移”或“orchestra 是否比没有 orchestra 更好”的总体验证。首版真正需要研究的是：

```text
orchestra 应掌握哪些上下文？
什么事实足以重建当前项目判断？
什么时候值得重新激活 orchestra？
orchestra 应检查到什么深度？
怎样下发任务，既能纠偏又不微操 worker？
怎样保存长期连续性，又不重新长出一套运行时协议？
```

多 worker 的发现、分配、并行、协调和集成是另一组复杂问题，不属于首版。

架构原则：

```text
项目连续性属于持久项目状态。
orchestra 的推理只属于单次决策轮。
worker 的执行连续性属于当前持续会话。
项目状态是可直接重写的材料，不是运行时协议。
```

本文档是一版待校准设计，不是新的运行时规范。第一版优先使用 Hermes 已有能力、普通项目文件和独立代理会话进行手工调试。

## 1. 问题边界

完整的 Claude Code 或 Codex worker 已经能够在一个明确任务内完成：

- 阅读代码；
- 形成方案；
- 调用内部子代理；
- 拆分并行调查；
- 编码、测试和修复；
- 整合局部结果。

因此 orchestra 不应重复建立规划者、编码者、测试者和评审者，也不应把一个明确任务再次拆成多个外层 worker。

真正未被现有 worker 解决的是跨多个任务和阶段的长期方向：

```text
人类给出远大目标
→ worker 完成当前任务
→ worker 从自己刚建立的结构中选择下一步
→ 新机制成为新的注意力中心
→ 继续补一致性、恢复、兼容和审计
→ 原始产品目标逐渐退出注意力中心
```

每个局部任务可能都完成正确，但整个项目没有形成新的端到端能力，没有消除关键不确定性，也没有更接近可交付状态。

orchestra 的职责不是提高 worker 的局部编码能力，而是在项目决策边界重新回答：

```text
项目现在真实处于什么状态？
项目为什么仍未成立？
当前路线是否仍然值得继续？
下一项工作应让项目发生什么变化？
什么时候应该停止、回退或询问人类？
```

## 2. 首版只讨论一对一关系

首版固定只有：

```text
一个 orchestra
一个当前 worker
一个当前推进任务
```

一对一不表示 orchestra 持续盯住 worker。orchestra 只在项目决策边界出现，worker 在两个决策边界之间保持完整自治。

worker 可以使用自身已有的子代理系统。它如何并行调查、拆分实现和整合结果，不属于 orchestra 的管理范围。

首版不讨论：

- 同时运行多个外层 worker；
- 识别低耦合并行任务；
- worker 之间的消息和共享状态；
- 多工作区写入和合并；
- 动态扩容、暂停和回收 worker；
- 多 worker 的集成责任；
- orchestra 自己维护长期子代理团队。

这些能力即使未来需要，也必须作为独立研究问题逐项调试，不能被当成首版天然应有的功能。

## 3. 角色边界

### 3.1 人类

人类提供：

- 长期意图；
- 关键成功体验和可观察结果；
- 产品、安全和外部协议边界；
- 后续重大方向变化；
- 事实无法裁决的价值选择。

人类不负责持续决定每个阶段的下一步，也不需要阅读 worker 的完整执行过程。

首版校准期间，人类还承担一个临时职责：作为熟悉项目的判断基准，指出 orchestra 漏掉的关键事实、错误路线和不合适的任务边界。这个职责用于调试设计，不应成为最终产品的长期依赖。

### 3.2 orchestra

orchestra 只负责阶段之间的项目级判断：

- 重新确认当前人类意图；
- 独立检查与战略判断相关的项目事实；
- 判断上一阶段是否真正推动项目；
- 判断当前路线和承重假设是否仍然成立；
- 选择下一项有项目意义的任务；
- 决定继续、调整、回退、等待、询问人类或停止；
- 更新精简项目状态并生成 worker 推进说明。

orchestra 不负责阶段内实现，不接管普通错误修复，不管理 worker 内部子代理。

### 3.3 worker

worker 接收一个相对完整、有限、可验证的推进说明，并完整负责：

- 理解代码和任务；
- 形成局部方案；
- 自行拆分工作；
- 调用内部子代理；
- 编码、测试和修复；
- 返回可验证结果和可能影响项目方向的新事实。

worker 不需要向 orchestra 上报普通局部计划、命令历史、每次测试失败和内部子代理对话。

### 3.4 外层程序

首版外层程序只负责：

- 启动全新的 orchestra 会话；
- 恢复当前 worker 会话；
- 投递人类消息、阶段结果和证据引用；
- 管理基本进程、权限、预算和取消；
- 保存一份精简项目状态材料。

外层程序不判断下一步，不拆任务，不建立执行图和校验流程。

## 4. 运行方式

### 4.1 orchestra 跨决策轮不继承会话

每次项目决策边界到来时：

- 创建新的 orchestra 会话；
- 不恢复上一轮 orchestra 对话；
- 不携带旧助手消息、工具记录和推理链；
- 不把上一轮计划和辩护重新塞回请求；
- 从当前项目状态和本轮新增事实重新组装上下文。

长期存在的是项目状态和 orchestra 的责任，不是一条长期模型会话。

### 4.2 单次决策轮内允许完整代理循环

全新会话不等于单次分类调用。一个决策轮内，orchestra 可以：

- 阅读项目状态；
- 检查与当前判断相关的代码和差异；
- 运行产品、测试或关键实验；
- 查看最近 worker 产物；
- 比较少量候选方向；
- 形成下一项任务或停止判断。

orchestra 默认只读取和检查项目，不修改业务代码。否则它会逐渐成为第二个 worker。它只修改项目状态材料和推进说明。

首版不要求 orchestra 调用额外子代理。先把单个战略代理的上下文和判断边界调通，避免引入新的混杂因素。

### 4.3 首版固定使用一个持续 worker 会话

首版中，连续任务默认交回同一个 worker 会话。除以下情况外，不替换 worker：

- 进程或会话无法恢复；
- 达到模型上下文硬上限；
- 人类明确要求更换。

即使 orchestra 改变下一项任务，也先把新的推进说明交给原 worker。

这样做不是断言长期永远不应刷新 worker，而是避免首版同时引入第二个控制问题。若新的 orchestra 任务无法把原 worker 从旧路线中纠偏，应记录为独立问题，后续再研究何时刷新 worker 会话。

### 4.4 全新 orchestra 不等于放弃前缀缓存

不能复用的是旧模型生成的对话和策略叙事，不是所有稳定输入。

稳定的职责说明、人类长期意图和硬边界仍可作为固定请求前缀。每轮变化的项目事实、阶段结果和证据放在动态部分。

## 5. 持久项目状态

持久项目状态只服务于下一次 orchestra 判断。它不是完整历史，不是冻结合同，也不是新的运行时数据库。

本节列出的是 orchestra 需要考虑的信息类别，不是首版固定字段、固定章节或可校验结构。

首版最多使用一份可整体重写的自由格式 Markdown 文档，并遵守：

- 整体覆盖更新，不追加运行日志；
- 不做字段校验；
- 不做版本协议；
- 不做迁移；
- 不做新旧格式兼容；
- 不做自动合并或修复；
- 不要求 worker 读取或维护该文档；
- Git 只负责普通历史追溯；
- 任何内容都可以直接改写或删除。

如果这份状态材料开始产生自己的结构兼容、迁移、恢复或校验责任，应立即收缩，而不是继续建设配套机制。

### 5.1 人类意图

保留：

- 长期目的；
- 当前重大方向；
- 可观察成功结果；
- 真实约束；
- 已确认的非目标；
- 后续明确修改和撤回。

worker 或 orchestra 自己建立的机制不能反向扩张人类意图。

### 5.2 已确认的项目事实

只保留会影响项目方向的事实：

- 当前真正可运行的端到端能力；
- 已验证的用户流程；
- 当前真实失败和阻塞；
- 已形成的外部协议或数据承诺；
- 已集成结果与仍然孤立的产物；
- 对应的代码版本、测试、日志或运行结果引用。

代码和 Git 可直接恢复的普通细节不重复抄写。

### 5.3 承重假设

只保留一旦错误会改变后续路线的项目级假设：

```text
假设
当前依据
什么事实会证明它失效
```

承重假设不是事实，也不是上一轮推理历史。

### 5.4 当前收敛缺口

保留 orchestra 当前对“项目为什么还没有成立”的精简解释，例如：

- 核心能力尚未形成端到端闭环；
- 两个已有能力尚未集成；
- 关键协议语义仍不明确；
- 缺少判断真实失败所需的反馈；
- 当前路线局部持续成功，但没有减少项目级风险。

它不是代码待办列表，可以随新证据直接改写或删除。

### 5.5 精简结果和已停止路线

重要阶段只保留：

- 原本想产生什么项目变化；
- 实际产生了什么可验证变化；
- 哪个承重假设成立、失败或仍未知；
- 当前路线应继续、调整还是停止。

只有成本较高且未来容易重复的失败路线，才保留原假设、反证和停止结论。普通局部失败不进入长期状态。

### 5.6 待人类决定事项

只保留真正属于产品方向、外部承诺、不可逆风险或价值取舍的问题。

### 5.7 当前决定残留

上一轮决定最多保留：

```text
当前方向
依赖的承重假设
预期信号
明确失效条件
尚未解决的风险
```

这不是决策账本，也不是要求下一轮继续维护旧路线的理由。

## 6. 事实、判断和决定必须分开

全新 orchestra 只有在输入没有把旧判断伪装成事实时才真正有意义。项目状态在语义上应区分：

```text
人类意图
已观察事实
当前推断
承重假设
当前决定
开放的不确定性
```

不要求首版建立对应字段，但组织材料时必须保留这些边界。

worker 的总结也不能直接变成项目事实。它只是线索；涉及项目方向的结论应由 orchestra 结合代码、测试、运行结果或人类输入核实。

## 7. 最小充分上下文

每次 orchestra 决策轮的输入由四部分组成：

```text
稳定前缀
  orchestra 职责、人类长期意图、硬边界、输出要求

当前项目状态
  已确认事实、承重假设、收敛缺口、当前决定残留

本轮变化
  最近阶段结果、人类变化、外部变化

按需证据
  与本轮判断直接相关的代码、差异、测试、日志和运行结果
```

不直接拼接上一轮 orchestra 对话，也不全量复制 worker 对话。

首版需要重点校准的不是上下文越少越好，而是哪些内容对于项目级判断是必要的，哪些内容只会把 orchestra 拉回旧路线。

### 7.1 两段式揭示不是首版固定流程

候选做法是：

```text
第一段：先看当前事实和原始证据，不看旧策略与 worker 建议
第二段：再看精简决定残留、停止路线和 worker 解释，校正初步判断
```

它有合理动机，但先作为上下文设计的一个候选变量，不写成首版强制流程。只有实际校准表明它稳定减少锚定，才考虑采用。

## 8. 项目决策边界

orchestra 不常驻，也不检查每个 worker 动作。典型触发：

- 当前任务完成，并产生可能改变下一步的结果；
- worker 确认阻塞或承重假设失效；
- 人类发来重大方向变化；
- 关键实验或外部事件产生结果；
- 连续执行没有产生实质项目变化；
- worker 建议继续加固同一内部机制；
- 即将投入大规模或不可逆路线；
- 项目可能已经达到长期目标。

普通测试失败、局部实现选择、worker 内部子代理调度和普通提交不触发 orchestra。

首版不自动判断所有边界。先由人工主会话或简单脚本显式触发，观察哪些触发过早、哪些触发过晚，再决定是否需要自动化。

## 9. 单次 orchestra 决策轮

### 第一步：重新确认人类意图

回答：

- 人类最终需要什么项目结果？
- 当前重大方向和外部边界是什么？
- 哪些目标来自人类，哪些只是代理自建结构？

### 第二步：检查项目现实

独立检查：

- 当前真正能运行什么；
- 哪些端到端结果已经验证；
- 上一任务实际改变了什么；
- 当前主要收敛缺口是什么；
- 原路线依赖的承重假设是否仍成立。

### 第三步：生成少量候选动作

候选可以是：

- 继续当前方向；
- 调整当前任务边界；
- 结束当前路线并选择新任务；
- 做一个有限判别实验；
- 建立当前确实缺失的反馈能力；
- 等待真实外部依赖；
- 请求人类；
- 停止项目。

不生成完整长期路线图。

### 第四步：选择一个当前任务

首版始终只选择一个当前任务，交给一个完整 worker。即使发现多个可能方向，也只选择当前最值得推进的一项，或先做能够区分方向的有限实验。

### 第五步：更新项目状态并下发任务

只写回：

- 新增或失效的关键事实；
- 新增、修正或失效的承重假设；
- 新增、关闭或重写的收敛缺口；
- 当前决定及其失效条件；
- 待人类决定事项；
- 下一次 orchestra 唤醒条件。

然后生成 worker 推进说明并结束本次 orchestra 会话。

## 10. worker 推进说明

推进说明应短而完整：

```markdown
## 期望项目变化
本任务希望让项目现实发生什么变化

## 为什么现在做
为什么这是当前最有价值的一步

## 相关事实
与本任务相关的已确认事实和证据引用

## 当前工作假设
允许 worker 使用的承重假设及其失效信号

## 自主决策范围
worker 可以自主决定的实现范围

## 必须保留
已有能力和真实约束

## 所需证据
完成后需要返回的可复核结果

## 何时提前上报
哪些项目级变化需要在任务完成前通知 orchestra
```

不规定文件、类、实现步骤、子代理数量、测试写法或局部评审流程。

首版需要重点观察推进说明的粒度：过细会重复 worker 的规划能力，过粗则无法把项目级判断落实成可执行任务。

## 11. 什么算有效项目变化

下一项任务必须有项目级因果依据，但不要求每一轮都立刻产生用户可见界面或功能。

合法变化包括：

- 新增用户可观察能力；
- 修复真实端到端失败；
- 集成已经孤立存在的能力；
- 消除一个承重不确定性；
- 建立后续判断必需且当前确实缺失的反馈能力；
- 降低已确认的不可逆风险；
- 删除或停止已经被事实证明无价值的路线。

不能单独成为新任务理由：

- 代码已经存在这个结构；
- 已有测试覆盖它；
- 上一轮留下待办；
- 继续完善会更严谨；
- 已投入很多时间或计算量；
- 新机制自身又产生迁移、兼容、恢复或审计责任。

反事实检查：

> **即使不考虑这个机制已经存在，它是否仍然由人类意图、真实外部约束、已确认失败或承重不确定性直接要求？**

若答案是否定的，不把继续完善该机制自动升级为项目目标。

## 12. 首版研究的真正问题

首版不研究“单 worker 会不会长期漂移”，也不研究“orchestra 是否在抽象意义上必要”。这些已经不是当前最缺的信息。

首版研究以下未知问题：

### 12.1 上下文是否充分

- orchestra 能否从精简材料恢复当前项目局面？
- 哪些项目事实必须直接提供？
- 哪些内容只需要给出引用，按需读取？
- 是否必须保留承重假设和已停止路线？
- worker 总结会提供有效线索，还是造成新的锚定？

### 12.2 检查深度是否合适

- orchestra 只看项目状态是否会过度依赖摘要？
- 每轮全量阅读仓库是否会退化成第二个 worker？
- 哪些承重事实值得亲自运行或检查？
- 怎样限制一次决策轮的调查范围？

### 12.3 决策边界是否合适

- 每个任务结束都唤醒是否过于频繁？
- 等到多个任务后再唤醒是否已经太晚？
- 哪些 worker 信号真正代表项目级变化？
- 哪些只是阶段内部噪声？

### 12.4 推进说明是否能有效纠偏

- worker 能否理解 orchestra 给出的项目级方向？
- 同一持续 worker 会话能否接受路线重定向？
- 推进说明是否过细、过粗或包含过多旧叙事？
- worker 返回的材料是否足以支持下一次全新判断？

### 12.5 项目状态是否能长期保持轻量

- 状态是否持续贴近真实项目？
- 是否开始堆积过时结论？
- 是否出现固定字段、兼容和迁移冲动？
- 全新的 orchestra 是否频繁重做已证伪路线？
- 不继承旧推理后，是否出现随机摇摆？

## 13. 首版校准方式

首版不是一次综合项目演示，也不是一套正式基准。它是对上下文、决策边界和推进说明的反复调试。

### 13.1 使用 Hermes 历史决策点校准上下文

从旧运行时内核演化过程中选择若干真实项目快照。选择标准不是覆盖所有机制，而是每个快照都存在一个人类已经明确知道的项目级问题，例如：

- 应停止继续完善自建运行时机制；
- 当前路线已经远离原始产品目标；
- 某个承重假设已经被现实推翻；
- 下一步应回到端到端能力，而不是补内部一致性；
- 某项工作虽然局部合理，但没有真实项目依据。

在运行 orchestra 前，由熟悉历史的人类先独立写出：

```text
本次必须注意的事实
已经失效的关键假设
明显不可接受的继续方向
可以接受的项目级动作范围
```

这不是要求 orchestra 猜中唯一答案，而是为上下文调试提供判断基准。

历史回放不再比较“长期 worker”和“全新的 orchestra”谁更好，也不用于证明 orchestra 必要。它只用于回答：当前组装的上下文是否足以让全新的 orchestra 看见人类已经知道的项目问题。

每轮只改变一个主要上下文变量，例如：

- 是否提供承重假设；
- 是否提供已停止路线；
- 是否先提供 worker 总结；
- 是否提供原始代码和测试引用；
- 状态摘要的大小；
- 是否使用两段式揭示。

记录 orchestra 漏掉了什么、被什么误导、读取了哪些不必要材料，据此收缩或补充上下文。

### 13.2 在真实项目中先进行影子判断

上下文初步稳定后，在真实项目的自然决策边界运行全新的 orchestra，但暂时不让它直接控制 worker。

流程：

```text
项目产生新的阶段结果
→ 人类先独立判断下一步
→ 全新的 orchestra 独立判断下一步
→ 比较两者差异
→ 人类选择实际动作
→ 根据差异调整上下文和提示词
```

orchestra 在看到人类判断前必须先固定自己的输出，避免事后合理化。

差异至少区分为：

- 漏掉关键事实；
- 把推断当成事实；
- 延续已失效路线；
- 随机反转仍有效路线；
- 过度深入局部实现；
- 任务过大或过小；
- 把代理自建机制当成项目目标；
- 正确发现人类忽略的问题。

影子阶段的目标不是追求一次性高分，而是发现设计中稳定重复的错误类型。

### 13.3 再进行有限的一对一接管

只有当影子判断能够较稳定地重建项目局面后，才允许 orchestra 直接生成下一项 worker 推进说明。

首版接管遵守：

- 始终只有一个当前 worker；
- 始终继续同一个 worker 会话；
- orchestra 不修改业务代码；
- 人类只在明显重大错误方向、不可逆操作或价值选择时阻止；
- 每次只调整一个主要设计变量；
- 不把一次项目结果包装成体系优越性的证明。

这一阶段重点观察：

- 全新的 orchestra 是否能在连续结果后稳定恢复项目方向；
- 同一 worker 是否能被新的推进说明有效纠偏；
- 推进说明是否留下足够执行自由；
- 项目状态是否保持轻量且贴近现实；
- 人类纠偏是否逐渐减少；
- 项目是否持续产生有效项目变化。

它是一段工程试运行，不是与“无 orchestra”进行形式化胜负比较。

### 13.4 每轮校准只改变一个主要变量

不得同时更换：

- orchestra 模型；
- worker 模型；
- worker 会话策略；
- 项目状态格式；
- 上下文揭示方式；
- 推进说明结构；
- 决策边界规则。

否则无法知道问题来自哪里。

## 14. 后续独立研究

以下问题不属于首版，但可在一对一设计稳定后单独研究。

### 14.1 worker 会话刷新

研究什么时候继续原 worker，什么时候启动全新 worker。它不能与首版 orchestra 上下文设计同时调试。

### 14.2 两段式上下文

比较一次性输入与先看事实、后看精简历史，确认它是否稳定减少锚定，而不是只增加调用成本。

### 14.3 多 worker

多 worker 至少包含：

- 如何判断两个任务是否适合并行；
- 如何管理独立工作区；
- 如何处理共享边界变化；
- 如何决定合并、暂停和取消；
- 谁承担最终集成责任；
- 并行收益是否大于协调成本。

多 worker 是独立且复杂的研究线，不能从一对一结构直接推导，也不能作为首版演示功能。

## 15. 首版最小实现

首版只需要：

```text
一份可整体重写的自由格式项目状态材料
一个启动全新 orchestra 的脚本或人工主会话
一个持续的 Codex 或 Claude Code worker 会话
少量代码、测试、日志和阶段结果引用
人工显式触发的项目决策边界
```

单次 orchestra 只做：

1. 检查必要事实；
2. 判断当前项目缺口和路线；
3. 选择一个当前任务；
4. 写一份短推进说明；
5. 整体更新项目状态材料；
6. 结束会话。

首版不需要：

- 状态数据库；
- 固定字段解析器；
- 决策结构定义；
- 状态校验器；
- 自动上下文组装器；
- 自动边界检测；
- worker 替换策略；
- 两段式提示词；
- 反证代理；
- 多 worker；
- 独立评审流水线。

## 16. 首版判断标准

首版不是通过一次最终演示判定成功或失败，而是看反复校准后是否出现以下趋势：

- 全新的 orchestra 能从精简状态恢复人类认可的项目局面；
- 不需要把完整历史和完整 worker 对话重新塞入上下文；
- 能识别已失效假设和代理自建工作；
- 能提出粒度合适、具有项目意义的下一项任务；
- 同一 worker 能依据推进说明改变方向；
- 不因全新会话而频繁随机反转；
- 项目状态保持短、可改写、没有形成新协议；
- 人类在项目决策边界需要做的纠偏逐渐减少。

若持续出现以下情况，说明当前设计需要修正：

- 人类每轮仍需重新讲解整个项目；
- orchestra 只是复述 worker 的总结；
- 缺少完整历史就无法作出稳定判断；
- 为避免摇摆开始保存越来越多旧推理；
- 项目状态长成字段、校验、迁移和兼容系统；
- orchestra 过度阅读和修改代码，成为第二个 worker；
- worker 无法从旧上下文中接受新的项目方向；
- 人类纠偏没有减少。

这些结果首先用于定位上下文、边界或接口问题，不急于推导“orchestra 整体无效”。

## 17. 首版明确非目标

首版不建设：

- 用对照实验再次证明单 worker 长期会漂移；
- 用一个综合项目演示证明完整体系优越；
- 多 worker 调度和管理；
- 外层任务并行；
- worker 登记系统；
- 多工作区合并机制；
- worker 间通信层；
- 固定角色团队；
- orchestra 长期子代理团队；
- worker 自动刷新；
- 完整路线图冻结；
- 目标合同、进展账本和执行图；
- 图修订校验器；
- 检查点、快照和压缩系统；
- 复杂产物关系追踪；
- 自动负向评审或清理；
- 持久推理历史。

首版的任务只是把一对一 orchestra 的上下文、决策边界和推进说明调通。只有实际运行暴露出明确缺口时，才增加对应的最小能力。
