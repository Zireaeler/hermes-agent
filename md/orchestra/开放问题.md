# Orchestra：开放问题

本页收集尚未形成稳定结论的问题。它们是讨论入口，不代表已经决定的设计要求。

## 战略监督与死胡同识别

- 人类如何区分正常困难、暂时僵局和结构性死胡同？
- 进展停滞、预测误差、重复失败、复杂度增长等信号如何组合？
- 如何识别“局部成功掩盖整体失败”？
- 如何找到最早导致后续路径失效的关键判断？
- 哪些信号可由运行器客观采集，哪些需要模型结合上下文判断？

## 全局重审

- 重审应由 Orchestra 自己完成，还是委派一个全新的 Worker？
- 新 Worker 应看到多少旧历史，才能既获得证据又不被旧方案锚定？
- 如何确保重审真的重新构建问题，而非为原路线生成新辩护？
- 重审产物应如何影响下一轮任务分配？
- 如何衡量一次重审是否有效？

## 策略切换

- 如何判断应当局部修正、调整方法、切换路线或重构问题？
- 何时值得先做判别实验，而不是直接换线？
- 如何考虑替代路线的未知风险和切换成本？
- 如何保留已有可复用成果，同时摆脱沉没成本？

## 能力边界

- 如何从最终目标推导隐含能力需求？
- 如何判断模型的输入信息是否足以支持它要做的评价？
- 能力探针怎样覆盖真实任务，而不只是简单代理测试？
- 如何逐步积累跨领域能力边界知识？
- 未知未知是否存在可行的发现机制，还是只能依赖外部知识、异常反馈和多视角检查？

## 证据与实验

- 人类元认知和问题解决研究中，哪些发现可迁移到 Agent？
- 哪些 Agent 实证研究直接验证了策略监控、策略切换和独立监督？
- 如何设计对照实验，比较有无战略监督时的最终任务质量、无效投入和错误路线持续时间？
- 如何避免只用模型自评来证明监督机制有效？

## 实施边界

- 哪些内容适合写入基础 Prompt？
- 哪些应作为按需调用的知识文档？
- 哪些需要运行器提供客观事件或证据？
- 哪些目前不应实现，应该等待更多真实案例？

## 当前约定

- 不因一个 PET 案例就宣称发现通用规律。
- 不把人类认知理论直接当作 Agent 效果证据。
- 不把提示词中出现某项要求等同于模型已经具备该能力。
- 先积累案例、提出可检验假设，再决定是否增加系统机制。
- 讨论文档与正式设计分开；只有经过讨论和验证的结论才迁移到正式设计。
